# Online payments: providers

How Brygge charges a checkout order through a payment service, and the decisions taken for adding card payments with Stripe. For Vipps settlement reconciliation and GL posting, see [`backend/internal/accounting/README.md`](../../backend/internal/accounting/README.md); for testing Vipps locally, [vipps-local-testing.md](vipps-local-testing.md).

## The model

Everything a payer can pay online is an **order** (`orders`): a faktura pay link (with `order_sources` rows pointing at the invoices it settles), a harbor QR guest payment, or a checkout with ad-hoc catalog lines (`order_lines`). An order is durable; a **payment attempt** (`payment_attempts`) is one short-lived payment at a provider to pay it. A payer who abandons an attempt clicks again and gets a fresh one on the same order; the earlier attempt keeps its row and reference, so if the payer completes it after all, its webhook still finds the order. The newest attempt with a provider reference is the order's **current** one.

```
/betal/{token} page, /qr/{token} page   payer picks a method (PayMethodButtons)
  POST /checkout/{token}/pay, POST /qr/{token}/pay {provider}
  (GET /api/v1/betal/{token}: one provider → mints; several → the /betal page)
        │  gate: providers.Configured(); provider: the payer's choice or defaultProvider()
        ▼
mintOrderPayment(ctx, providerName, orderID, cancelURL)   handlers/order_pay.go
        │  amount cap + imported-receivable gate, orderTotal, guest? member email
        │  payment_attempts row inserted (created)
        ▼
payments.Provider.CreatePayment(Request) → Result   vipps / stripe .PaymentProvider
        │  reference stored on the attempt (and orders.vipps_reference for Vipps),
        │  payer redirected; on error the attempt is marked failed
        ▼
payer returns to /betal/{token}/kvittering           polls GET /checkout/{token}
        ▼
provider webhook (signature verified, event stored)  handlers/{vipps,stripe}_webhook.go
        │  reference (or metadata attempt id) → attempt → order, provider-only facts
        ▼
orderSettlement: authorizeAttempt / markAttemptCaptured / markAttemptFailed
                                                     handlers/order_settle.go
```

### `internal/payments`

The provider-neutral seam ([`payments.go`](../../backend/internal/payments/payments.go)):

- **`Provider`** — `Name()` and `CreatePayment(ctx, Request) (Result, error)`. Refunding is not part of it (below).
- **`Canceller`** — optional; voids an authorized, uncaptured payment.
- **`Refunder`** ([`refunder.go`](../../backend/internal/payments/refunder.go)) — optional; `Refund(ctx, RefundRequest) (RefundResult, error)` and `FindRefund(ctx, reference, requestKey) (RefundResult, found, error)`. A provider without it (Vipps, until BRY-14) has no refund button and the refund endpoint answers 409 `not_supported`. `Refund` is idempotent on the request key and is never re-sent under another key; a `*RefundRejectedError` means the provider certainly did not refund, any other error is uncertain, and `FindRefund` is how the caller learns what became of it. `Registry.RefunderFor(name)` and `RefundProviders()` ask whether a registered provider can.
- **`MinimumAmount`** — optional; `MinAmountOre(currency) (int64, bool)` is the provider's smallest charge, false when it has none for that currency. `CheckMinimum(provider, currency, amountOre)` returns a `*BelowMinimumError` (provider, `MinOre`, currency; `errors.Is(err, ErrAmountBelowMinimum)`) when the amount is under it, nil otherwise, including for a provider without the interface.
- **`Request`** — order id, attempt id (unique per attempt, usable as an idempotency key), amount in øre, currency, the full description (the provider shortens it to its own limit), whether the order is a guest order, the linked member's email (empty for guests), the return URL (the order's receipt page) and the cancel URL (the page the payer came from). **`Result`** — the redirect URL and the provider's reference.
- **`Registry`** — the providers this deployment has credentials for. `Get(name)`, `Names()` and `Configured()`. A nil registry is valid and empty, which is how an instance without payment credentials runs.

The package holds no database code. Deciding what is owed, enforcing the club's cap, and recording the outcome stay in the handlers so every provider gets the same rules.

### Provider adapters

`vipps.PaymentProvider` ([`internal/vipps/provider.go`](../../backend/internal/vipps/provider.go)) wraps the ePayment client. It owns what is specific to Vipps:

- the `chk-<32 hex>` reference, which is also the idempotency key (Vipps rejects a reused reference, so each attempt is new);
- the 100-character `paymentDescription` limit, cut by rune so æ, ø, å and emoji are never split into invalid UTF-8;
- asking guests (and only guests) for their name via profile sharing;
- `WEB_REDIRECT` user flow.

It does not implement `Refunder`: Brygge cannot issue a Vipps refund yet (BRY-14). `CancelPayment` implements `Canceller`. It ignores the attempt id, cancel URL and payer email: Vipps returns to the receipt page on abort too.

`stripe.PaymentProvider` ([`internal/stripe/provider.go`](../../backend/internal/stripe/provider.go)) wraps a hand-rolled client ([`internal/stripe/client.go`](../../backend/internal/stripe/client.go): form-encoded calls with the secret key as Bearer and `Stripe-Version` pinned to `stripe.APIVersion`, no stripe-go dependency; the webhook endpoint should be created on the same version). It creates a hosted Checkout Session:

- `mode=payment`, `payment_method_types[]=card` only (Apple Pay and Google Pay ride on card), one line item with the øre amount and the description cut to 120 runes (the PaymentIntent description to Stripe's 1000);
- `customer_email` for a member whose email parses as a bare address (Stripe rejects the whole session on an invalid one); otherwise, and for a guest, the payer types it on the Stripe page;
- `payment_intent_data[capture_method]=manual`, so a completed session is an authorization;
- `metadata` and `payment_intent_data[metadata]` = `attempt_id`, `order_id`, `club_slug` (never the order token: it is the pay link's capability);
- `success_url` = the receipt page, `cancel_url` = the page the payer came from, `expires_at` = now + 60 minutes;
- the attempt id as `Idempotency-Key`, so a retried create returns the same session.

Stripe will not charge less than a per-currency minimum ([Stripe's table](https://docs.stripe.com/currencies#minimum-and-maximum-charge-amounts)); below it the create answers 400 `amount_too_small`. The adapter implements `MinimumAmount` from its own copy of the table (NOK and SEK 300, DKK 250, EUR, USD and CHF 50, GBP 30, in minor units; any other currency has no local minimum and is left to Stripe), refuses a request under it before any HTTP call, and maps Stripe's own `amount_too_small` (its minimum follows the account's settlement currency, so it can be higher) to the same `*BelowMinimumError`. Vipps does not implement the interface: ePayment rejects amounts under 1 kr, a floor below anything Brygge prices, so the adapter does not model it.

The reference is the session id (`cs_…`). `CancelPayment` retrieves the session: an authorized PaymentIntent (`requires_capture`) is cancelled, an open session is expired, a captured one returns `ErrNotCancellable`. `Refund` and `FindRefund` implement `Refunder` ([`stripe/refund.go`](../../backend/internal/stripe/refund.go)): the session is read for its PaymentIntent, then `POST /v1/refunds` carries `payment_intent`, `amount`, `reason=requested_by_customer`, `metadata[refund_request_key|order_id|attempt_id|club_slug]` and `Idempotency-Key: refund-<request key>`. A parseable Stripe error object answered with a 4xx (a closed charge, `charge_disputed`, a key without Refunds Write) is a `*RefundRejectedError`; a 5xx, a timeout, a 408, 409 or 429, an idempotency refusal, a 4xx whose body is not a Stripe error (a proxy's) or an answer that does not decode is returned as it is, uncertain (PAY-12). `FindRefund` lists the PaymentIntent's refunds (`GET /v1/refunds?payment_intent=…&limit=100`) and matches `metadata.refund_request_key`; the list is followed with `starting_after` for up to ten pages, and a longer one is an error, never a shorter answer. The client also lists a charge's refunds (`?charge=`) for the webhook.

Payment creation goes through the registry, and each webhook voids a stale authorization through its adapter's `Canceller`. Settlement sync (`AccountingHandler`) and the Vipps webhook's other calls (capture on AUTHORIZED, `GetPayment` for a guest's name) keep the concrete `*vipps.Client`, and the Stripe webhook captures through `*stripe.Client`, because those are provider-specific operations with no neutral equivalent yet.

### Choosing the provider

`InvoiceHandler.defaultProvider()` is Vipps when it is configured, otherwise the one provider that is, so a Stripe-only deployment works end to end. `availableProviders()` lists the configured ones in display order: the default first, then the rest by name (`Registry.Names()` is alphabetical, so the order is set here, not by the registry). Stripe is registered only when both `STRIPE_SECRET_KEY` and `STRIPE_WEBHOOK_SECRET` are set; one without the other logs a startup warning and registers nothing, because a payment Brygge never hears back about is never marked paid.

The payer chooses on the page they are already on; there is no separate choice page:

- **`/betal/{token}`** (SPA, `PayInvoiceView`) is the itemised faktura page. `GET /api/v1/checkout/{token}` returns `providers` (display order; empty when none is configured or the order is blocked) and `online_blocked` (an unpaid source is over the cap, forced off, or an imported receivable not yet in the GL). Two or more providers show one button each, one shows a single labelled button, none shows the bank-transfer box (`bank_account` and `kid_number` are filled whenever `providers` is empty). The button posts `{"provider": …}` to `POST /checkout/{token}/pay`.
- **`/qr/{token}`** (SPA, `QrCheckoutView`) gets the same `providers` from `GET /api/v1/qr/{token}` (no blocking rule applies to a guest order) and posts `provider` to `POST /qr/{token}/pay`. Card leads there, since guests are often visitors without Vipps.
- **`GET /api/v1/betal/{token}`** (`HandleOrderPayRedirect`) is the one-tap link in faktura emails sent before the checkout page existed. A paid order goes to its receipt; with one provider it mints at once and 302s to the provider; with several it 302s to the `/betal/{token}` page rather than choosing for the payer; with none it answers 503 with a plain-text message.
- **The payables page** (`/betal/bruker/{token}`) routes each invoice's Pay button to its `/betal/{token}` page in the SPA.

**Minimum charge.** A provider is only offered for a total it will charge. `providersFor(amountOre)` is `availableProviders()` without the providers whose `MinimumAmount` refuses the amount (in `paymentCurrency`, rounded to øre exactly as the payment request is):

- The checkout GET lists `providersFor(total)`, so a faktura or order under 3 kr on a Stripe-only deployment gets `providers: []` and the bank-transfer box, and with Vipps too only the Vipps button.
- The QR GET keeps `providers` unfiltered, because the payer changes the total with the unit stepper, and adds `provider_min_amount` (kroner per provider with a minimum, e.g. `{"stripe": 3}`; `{}` when none). `QrCheckoutView` hides (not disables) a provider while the total is under its minimum, shows "Card payment from 3 kr" while card is hidden, and, when nothing is left, says the amount is too small to pay online (not the "unavailable" text, which means nothing is configured).
- `mintOrderPayment` checks the minimum before recording the attempt, so an amount that can never be charged leaves no failed attempt behind. `POST /checkout/{token}/pay` and `POST /qr/{token}/pay` answer 409 `amount_below_minimum` for it, and for Stripe's own `amount_too_small`; the QR POST checks before it inserts the order, so no stray order is left either. `PayInvoiceView` reloads on that 409 (like `online_payment_over_limit`), and if the provider the payer pressed is still offered after the reload (Stripe's own minimum is above the table) it says the amount can't be paid that way; `QrCheckoutView` shows the card minimum when the total is under it, and otherwise that card was refused for this amount. `GET /api/v1/betal/{token}` with that one provider redirects to the `/betal/{token}` page, which then shows the bank-transfer box.
- `ensureFakturaOrderToken` issues no pay link when no configured provider charges the invoice's amount (read in the same query as the cap check, `invoiceOnlineGate`, before the reuse), and the email's methods line names only the providers that charge it (`emailPayMethods(payURL, amount)`). The admin copy-link route (`GET …/pay-link`) answers 409 `amount_below_minimum` for such an invoice, and `useCopyPayLink` shows why.

The minimum is checked against `paymentCurrency` (NOK), the currency every payment request is made in.

**Currency (BRY-452, PAY-13).** Brygge charges in NOK only. `mintOrderPayment` reads `orders.currency` (`NOT NULL DEFAULT 'NOK'`; a blank or lower-case value reads as NOK) right after it finds the provider (before the online-blocked and minimum checks) and refuses anything else with `errUnsupportedCurrency`, so no provider is called and no attempt is recorded. `POST /checkout/{token}/pay` and `POST /qr/{token}/pay` answer 409 `unsupported_currency` (the QR POST checks the price item's currency before it inserts the order, so no stray order is left), `GET /api/v1/betal/{token}` answers a plain-text 409, and `PayInvoiceView` says online payment is only available in kroner (pay by bank transfer or ask the treasurer), and `QrCheckoutView` says the target can only be paid in kroner here and to ask the harbor master, instead of asking the payer to retry. Both providers' reconciliation and the ledger assume NOK, so a non-NOK charge would be booked at the wrong value.

`POST` with a provider name that is not registered answers 400 `unknown payment provider`; no name uses the default. The buttons are one shared component, `frontend/src/components/pay/PayMethodButtons.vue`: it maps provider names to methods (`vipps` → Vipps, `stripe` → card, labelled "Kort · Apple Pay · Google Pay"), takes an optional `emphasis` to put one method first, and skips names it has no method for. There is no club setting for the order. The labels are `text-xl font-bold` on purpose: white on Vipps orange (`#ff5b24`) only meets WCAG AA contrast as large text. The visible label is each button's accessible name (icons are `aria-hidden`). If a pay POST answers 409 `online_payment_over_limit` (the order became blocked after the page loaded), `PayInvoiceView` reloads the checkout so the bank-transfer box replaces the buttons.

Faktura and reminder emails link to `/betal/{token}` with a "Betal nå" button and a line naming the methods beneath it, built from the providers that charge the faktura's amount by `emailPayMethods` / `email.PayMethodsLabel`: "Vipps", "Kort" or "Vipps eller kort", and no line when there is no pay link. The emails are Norwegian only.

### Returning to the receipt page

Every provider returns the payer to `/betal/{token}/kvittering` (QR orders too, through their own order token), and `GET /betal/{token}` sends an already-paid order there. The page polls `GET /api/v1/checkout/{token}` with backoff (2, 3, 5, 8, then 10 s; at most 15 polls or about 90 s, inside the endpoint's per-IP limit) and shows the receipt (`paid_amount`, the faktura and lines), the pending spinner, a failed state with a link back to `/betal/{token}`, or, when no verdict arrives in time, that the payment is recorded as soon as the confirmation arrives and the payer can open the link again later to see the receipt (Brygge sends no receipt email of its own). It never assumes success: Vipps returns there on abort as well.

### Marking an order paid

`orderSettlement` ([`handlers/order_settle.go`](../../backend/internal/handlers/order_settle.go)) is the only code that changes an order's payment state, and it is only called from a signature-verified webhook (see the invariants "Only the payment provider can mark an order paid" and "A payment attempt that is not needed is never captured" in [reference/invariants.md](reference/invariants.md)). It works per attempt:

- `attemptByReference(ctx, clubID, provider, reference)` — the attempt (with its status, amount and currency), its order and whether the order is a guest order. `attemptByID(ctx, clubID, provider, id)` does the same from an attempt id a provider echoes back in metadata.
- `authorizeAttempt(ctx, attempt)` — one transaction holding the order row decides: skip (this attempt is already `captured` or `cancelled`: a replay), cancel (the order is paid or refunded, or another attempt is `authorized` or `captured`), or capture. The answer is written in the same transaction: `authorized` for capture, `cancelled` for a void, so no later event can read a voided attempt as payable. On cancel the webhook then voids the payment through `payments.Canceller`, best-effort (a failed void is logged; the authorization lapses at the provider). On capture it captures, and `releaseAuthorization` returns the attempt to `created` if the capture fails, so it doesn't block a retry (Stripe first asks where the PaymentIntent stands, see below). Only one of two concurrent authorizations is captured; if that capture then fails, the payer whose authorization was voided retries. Without the provider's credentials (no client, no `Canceller`) its webhook neither captures nor voids and leaves the attempt as it is; the authorization lapses at the provider.
- `markAttemptCaptured(ctx, attempt, capturedAt, payerName)` — the attempt becomes `captured`; the order becomes `paid` from `pending` or `failed` (a warning when from `failed`) with `paid_at = capturedAt` (zero: now) and `provider` set to the attempt's. If another attempt already paid the order, the order is left alone and the double payment is logged at error level for a refund. `guest_name = payerName` only on a guest order with no name (Vipps looks the name up for guest orders only). Each source invoice with no marker yet gets `online_paid_at = capturedAt` and `online_paid_provider`, and for Vipps also `vipps_paid_at`. It never sets `payment_id`, posts to the GL, sends email or writes audit: the settlement import owns those.
- `markAttemptFailed(ctx, attempt)` — the attempt becomes `failed` (from `created` or `authorized`); the order becomes `failed` only if the attempt is its current one (newest with a reference) and it is still `pending`.
- `backfillGuestEmail(ctx, attempt, email)` — the email a provider collected, on a guest order with none.

### Stripe events

`POST /api/v1/stripe/webhooks` ([`handlers/stripe_webhook.go`](../../backend/internal/handlers/stripe_webhook.go), [`stripe_webhook_dispatch.go`](../../backend/internal/handlers/stripe_webhook_dispatch.go)) verifies `Stripe-Signature` (HMAC-SHA256 over `"<t>.<body>"`, any `v1`, 300 s tolerance, 1 MiB cap; an empty secret rejects everything with 401) before decoding, stores the event in `payment_webhook_events` under the session id (or PaymentIntent id for `payment_intent.*` / `charge.*`), and dispatches it even when it was already stored. The club comes from the attempt, else the instance club; for a dispute event it comes from the payment the dispute is about (below). It answers 5xx only when the event, or a dispute, could not be stored.

| Event | Action |
|-------|--------|
| `checkout.session.completed`, `checkout.session.async_payment_succeeded` | Session `complete` with a PaymentIntent: compare `amount_total` and currency with the attempt (mismatch: error log, void, `markAttemptFailed`), then `authorizeAttempt`. Capture: capture the PaymentIntent (key `capture2-<attempt id>`, versioned with the call's parameters; already captured counts as success; a key Stripe refuses with `idempotency_error` / `idempotency_key_in_use` re-reads the PaymentIntent and, if it is still authorized, captures under `capture2-<attempt id>-retry` instead of failing), then `markAttemptCaptured` (now, payer name from `customer_details`) and `backfillGuestEmail`. A failed capture retrieves the PaymentIntent: still `requires_capture` → cancel it (the card hold is released at once) and `markAttemptFailed`; `succeeded` with the full amount → `markAttemptCaptured`; anything else, or a failed lookup or void → `releaseAuthorization` (the hold lapses; a later intent event settles it). Cancel: attempt already `cancelled` by `authorizeAttempt`, then `CancelPayment` best-effort. |
| `checkout.session.expired`, `checkout.session.async_payment_failed` | `markAttemptFailed`, unless the attempt is already `captured` or `cancelled`. |
| `payment_intent.canceled` | Attempt from `metadata.attempt_id`; `markAttemptFailed` unless already `captured` or `cancelled` (Brygge's own void arrives here too and must not fail an order another attempt pays). |
| `payment_intent.succeeded` | Attempt from `metadata.attempt_id`; `markAttemptCaptured` at the event time only when `amount_received` and currency equal the attempt's (a partial capture is logged at error level and pays nothing). A safety net for a capture whose answer was lost. |
| `payout.paid`, `payout.failed`, `payout.canceled` | With accounting on, `IngestStripePayout` runs in the background once the event is answered (at most 2 minutes, waiting for a sync of the club already running); it refreshes the payout in `stripe_payouts` and links the balance transactions it paid out, or releases them when it failed (see [Stripe accounting](#stripe-accounting)). Never books. |
| `charge.dispute.created`, `.updated`, `.closed`, `.funds_withdrawn`, `.funds_reinstated` | Upserts `payment_disputes` (status, reason, amount, evidence deadline, the attempt) and, on the dispute's first event only, emails the club's treasurer. Writes nothing else: no order, faktura or ledger state; the loss is booked from the balance by the booking pass. See [Disputes](#disputes). |
| `charge.refunded`, `charge.refund.updated` | Upserts `payment_refunds` for every refund of the charge (Stripe is asked for the list, so the state is current whatever order the events arrive in): found by Stripe's refund id, else by the request key the refund button put in the refund's metadata, else a refund made in the Stripe Dashboard gets a new row with no person, the reason "Stripe Dashboard" and no outcome. Stripe's `pending` and `requires_action` are `requested`, `failed` and `canceled` are `failed` (with Stripe's failure reason), `succeeded` is `succeeded`; a finished refund is never put back to `requested`. Writes nothing else: no order, faktura or ledger state. The attempt is found as for a dispute (below), and a payment that cannot be placed because Stripe cannot be asked, or a refund list that cannot be read, answers 5xx so the event is delivered again. See [Refunds](#refunds). |
| anything else | Stored only. |

The mint records the provider's answer (the reference, or `failed`) on a context detached from the payer's request, so a dropped request can't lose a reference to a payment the provider created.

Each write is guarded and runs on its own, so a redelivered or out-of-order event is a no-op and one failed write does not undo the others.

### Data model

- `payment_attempts` — `order_id`, `provider`, `provider_reference` (unique per provider once set), `status` (`created`, `authorized`, `captured`, `failed`, `cancelled`), `amount`, `currency`. The source of truth for provider references. `card_brand` / `card_wallet` (000118) say how a Stripe payment was made — Stripe's lowercase brand (`visa`, `mastercard`, …) and wallet type (`apple_pay`, `google_pay`, `link`, …) from the charge's `payment_method_details`; never last digits or country. Written best-effort, first value kept (`WHERE card_brand IS NULL`), from the capture answer (`latest_charge` expanded), from the PaymentIntent read after a failed capture, and by the Stripe balance sync whenever it lists a charge tied to the attempt (backfill and repair). A failure to read or store them is logged and never touches settlement.

  **Repairing historic card payments.** The sync only reads charges it lists again: those after its watermark (`stripe_sync_state.listed_through`, less a small overlap) and the members of payouts it refreshes. Card payments captured before 000118 whose payouts are already settled therefore keep NULL and show as a plain card. To fill them, move the club's watermark back to its Stripe go-live date and run **Synk Stripe** once (`/admin/accounting/bank-imports`, or `POST /accounting/stripe/sync`):

  ```sql
  UPDATE stripe_sync_state SET listed_through = '<go-live date>' WHERE club_id = '<club id>';
  -- or DELETE the row: the cursor then starts at the club's first Stripe attempt
  ```

  This is safe to repeat. Balance rows are upserted on their Stripe id, so nothing is inserted twice; a stored row is reclassified only while it waits for review on an ingest reason, as on any sync; booked, unbooked, dismissed and held rows are left as they are. The card fill writes only attempts with no brand yet. The watermark moves forward again (`GREATEST`) when the run completes. The run lists every balance transaction since go-live, so it takes a few Stripe calls longer than a nightly sync. Vipps attempts leave them NULL: the ePayment `paymentMethod.type` only echoes `WALLET`. The harbor overview (`GET /harbor/recent-payments`) derives `method` from them: `vipps` for a Vipps order, `apple_pay` / `google_pay` for those wallets, else `card`.
- `payment_refunds` — refunds of a captured attempt (`requested`, `succeeded`, `failed`), with the request key the refund button sends, the reason and person (none for a Dashboard refund) and the outcome chosen for a full refund (`credit` / `recollect`; NULL is credit). Written by the refund button, the Stripe webhook and the refund sweep; the booking pass reads it (and makes the row for a refund it books that has none). See [Refunds](#refunds).
- `payment_disputes` — a card dispute Stripe reports (`provider_dispute_id` unique, `status`, `reason`, `amount`, `evidence_due_by`, and the `attempt_id` / `order_id` it concerns when Brygge can tell). Written only by the Stripe webhook; see [Disputes](#disputes).
- `refund_documents` — what a booked card refund did to each faktura: the credit note it issued, the faktura it reopened to collect again, or (for a failed refund) the debit faktura it issued. See [the accounting README](../../backend/internal/accounting/README.md#card-refunds).
- `payment_webhook_events` — raw events for providers other than Vipps, deduplicated on `(club_id, provider, event_id)`. The Stripe webhook writes it. Vipps keeps `vipps_webhook_events`.
- `invoices.online_paid_at` / `online_paid_provider` — the "received, awaiting settlement" marker for any provider. `invoices.online_payment_opt_in` and `clubs.online_max_amount` — the per-faktura override and the club's cap, for every provider. `clubs.payment_fee_account` — fees for every provider (default 7700). `clubs.stripe_clearing_account` — 1580, the card balance until payout.

- `stripe_balance_transactions`, `stripe_payouts` — the Stripe balance mirrored for the books; see [Stripe accounting](#stripe-accounting).

The legacy columns `invoices.vipps_paid_at`, `invoices.vipps_payment_link_opt_in`, `clubs.vipps_max_amount` and `clubs.vipps_fee_account` are still written with the same values and read by nothing; BRY-450 drops them. `orders.vipps_reference` is still written on every Vipps mint and is not legacy: the settlement reconciliation in `internal/accounting` matches Vipps charges on it until BRY-445.

### Stripe accounting

Stripe accounting is in place: ingest, the charge and fee postings, refunds, disputes and payout clearing. `accounting.SyncStripeBalance` mirrors Stripe's balance transactions into `stripe_balance_transactions`, classifying each one (a charge is tied to its attempt through `metadata.attempt_id`), and the payouts into `stripe_payouts`, linking every transaction an automatic payout paid out. It posts nothing. It runs nightly, from `POST /api/v1/admin/accounting/stripe/sync`, and for one payout on the `payout.*` webhooks. `accounting.BookStripeBalance` then books each ready charge from its checkout order (DR 1580 gross / CR 1500 per faktura or revenue per line, with DR 7700 / CR 1580 for Stripe's fee) and each fee transaction, posted on creation. Booking needs an acting user, so it runs from the sync endpoint (after the ingest), at the end of **Synkroniser** (bank sync) and after a bank upload, never from the cron or a webhook. Right after it, in the same paths, `accounting.ClearStripePayouts` matches each paid automatic payout to its bank deposit (the club's payout descriptor, the amount to the øre, a date from a day before Stripe's arrival date to three days after, one to one) and, once every transaction in the payout is booked or dismissed, books the deposit DR bank / CR 1580. A manual payout, an ambiguous match or a payout whose transactions are still open is reported with the reason, and the Tildel row says the same; a deposit no sweep will clear is cleared by the treasurer from Tildel (**Avstem mot Stripe-utbetaling**, `POST /api/v1/admin/accounting/stripe/payouts/{id}/clear`), which relaxes only the automatic-payout, date-window and members-sum checks; a deposit carrying the descriptor is never booked by a mapping rule, auto-assign or a price-item suggestion. A charge whose faktura is no longer open, is imported without an opening balance, or whose order does not add up is held for review instead; the **Stripe-transaksjoner til gjennomgang** list on the bank page (`GET /api/v1/admin/accounting/stripe/review`) shows every row in review. A refund (made with the refund button or in the Stripe Dashboard) is booked by the same pass once it shows in the balance: a credit note per faktura for the refunded share, booked and sent to the payer after the commit, and DR 1500 / CR 1580; or, for a full refund the treasurer asked to collect again, the faktura reopens. A refund failure brings the money back with a new faktura. A dispute is booked as a loss on the club's dispute account (default 7830 Tap på fordringer, `clubs.stripe_dispute_account`) with its fee, and reversed if the club wins, leaving the faktura paid (ACC-4; [Disputes](#disputes)). The webhook never books (ACC-5). The pipeline, the classification table and the review reasons are in [the accounting README](../../backend/internal/accounting/README.md#the-stripe-balance-pipeline).

The webhook endpoint in the Stripe Dashboard must send, besides the Checkout and PaymentIntent events above, `payout.paid`, `payout.failed` and `payout.canceled`. Without them payouts are still picked up by the nightly sync, a day later. For disputes it must also send `charge.dispute.created`, `charge.dispute.updated`, `charge.dispute.closed`, `charge.dispute.funds_withdrawn` and `charge.dispute.funds_reinstated`, and the API key needs read access to disputes; without the events the loss is still booked by the nightly sync, but the treasurer is not told and `payment_disputes` stays empty. For refunds it must send `charge.refunded` and `charge.refund.updated`, and the API key needs **Refunds: Write** (the refund button creates refunds; a restricted key without it is refused 403 and the button reports that Stripe declined) and **Disputes: Read** (the balance listing expands each dispute's source); without the events a refund made in the Dashboard reaches the books through the balance (the booking pass makes its `payment_refunds` row), but the pending state of a refund the bank has not finished is not tracked.

**Operations (BRY-447).** Set the statement descriptor for payouts in the Stripe Dashboard to a text the club's bank shows on the deposit, and set `stripe_payout_descriptor` in **Økonomiinnstillinger → Betalingskonti** to a regular expression matching it as the bank exports it (description or counterpart; the default `(?i)stripe` matches Stripe's own text). Register the `payout.paid`, `payout.failed` and `payout.canceled` events on the webhook endpoint. Keep payouts automatic: a manual payout is never cleared by the sweep, and the treasurer has to clear it from Tildel against its deposit.

The settings are `clubs.stripe_clearing_account` (default 1580, an active asset account) and `clubs.stripe_payout_descriptor` (a Go regular expression for the payout's bank text, default `(?i)stripe`), both in **Økonomiinnstillinger → Betalingskonti**.

### Refunds

The refund button ([`handlers/order_refunds.go`](../../backend/internal/handlers/order_refunds.go), service in [`payments/refunds.go`](../../backend/internal/payments/refunds.go); decisions PAY-6, PAY-10 and PAY-11 in [`docs/adr/payments.md`](../adr/payments.md), ACC-1 to ACC-9 in [`docs/adr/accounting.md`](../adr/accounting.md)) returns money for a captured card payment. It starts the refund and keeps its state; it books nothing. The booking pass books a refund, issues its credit note and updates the order and faktura once Stripe's balance lists it ([the accounting README](../../backend/internal/accounting/README.md#card-refunds)).

| Endpoint | Gate | |
|---|---|---|
| `POST /api/v1/admin/orders/{orderID}/refund` | treasurer or admin, fresh TOTP (`RequireFreshTOTPDefault`), accounting feature | Starts a refund. Audited `order.refund_requested`. |
| `GET /api/v1/admin/orders/{orderID}/refunds` | treasurer or admin | The order's captured payments with what is left on each, its refunds and disputes, `can_refund`, `recollect_allowed` and the Stripe Dashboard link to the payment. Looks up stale requests first (below). |

**The request.** Body: `attempt_id` (required: a duplicate capture is a separate attempt), `amount` (kr, at most two decimals; omitted refunds all that is refundable), `reason` (required, at most 500 characters, kept on the row, not sent to Stripe), `outcome` (`credit` or `recollect`, only for the full refund of the payment that paid a faktura) and `request_key` (a UUID the dialog makes when it opens and repeats on every retry). The first transaction locks the order, then the attempt, so two requests over the same money cannot both pass, and then:

- a request key already stored returns its row (`replayed`) when the attempt and amount match, else 409 `request_key_reused`; a repeated click never reaches Stripe for a row Stripe has, and a row still waiting for an answer is looked up (`FindRefund`) and, when Stripe has nothing and the row is under 23 hours old, sent again under the same key (PAY-12; a row the provider already has an id for, or a failed look-up, sends nothing); the replay also needs the same outcome and reason;
- the attempt must be `captured` (409 `not_captured`) with a provider that implements `Refunder` (409 `not_supported`), have no open dispute (`payments.OpenDisputeForAttempt`; 409 `disputed`), and the amount must be within the attempt's amount less the requested and succeeded refunds (409 `amount_exceeds_refundable`);
- an `outcome` is accepted only for a refund that completes the payment of an order with fakturas, and not for a duplicate capture (400); `recollect` also needs that nothing was refunded of it before, no credit note among its fakturas' refund documents (409 `recollect_after_partial`);
- the row is stored (`requested`, with the person, reason, key and outcome) and the transaction commits.

Only then is Stripe called, on a context that outlives a client that gave up. Stripe's answer is stored on the row: the refund id and refs, and the status only while the row is still `requested`, so a slower answer never undoes what the webhook settled. A refund Stripe refused (`RefundRejectedError`: only a parseable Stripe error object answered with a 4xx other than 408, 409 or 429) marks the row `failed`, frees its amount and answers 502 `refund_failed` with Stripe's code as `reason`; the request key is then spent. An uncertain error leaves the row `requested`, looks for the refund once with `FindRefund` (found: stored), and otherwise answers 202 `awaiting_confirmation`. The response is 200 otherwise, with the refund's status (a refund the bank has not finished stays `requested`).

**The sweep.** A `requested` row older than ten minutes is resolved by `FindRefund`: found, it takes Stripe's state; not found and under 23 hours old, it is sent again under its own key (the request may never have left; never a new key); not found after 24 hours (Stripe forgets an Idempotency-Key by then) it is marked `failed`. It runs for the order on every `GET …/refunds` and for the whole club in the nightly Stripe job (`RefundService.SweepRequested`). A row nobody swept is also settled by the webhook and, once booked, by the balance.

**The webhook** keeps `payment_refunds` current for refunds made elsewhere (above); the refund button's rows are matched by the request key Stripe carries in the refund's metadata.

**Where the button shows.** The payment overview (`GET /api/v1/harbor/recent-payments`, `can_refund` per payment) and the faktura list (`GET /api/v1/admin/financials/invoices`, `refund_order_id` per card-paid faktura) mark the payments the signed-in treasurer or admin can refund (`RefundService.RefundableOrders`: a captured payment of a provider that can refund, money left, no open dispute); other roles never get the flag. The frontend's `RefundOrderButton` asks for the TOTP step-up at click time and opens `RefundOrderDialog`, which reads the order's refunds endpoint, preselects a duplicate capture (labelled *dobbeltbetaling*) or else the first refundable payment, prefills the refundable amount, requires a reason, and for a full refund of a faktura's payment offers **Krediter** (default) or **Krev inn på nytt** (hidden when `recollect_allowed` is false).

**Dashboard link.** The dialog links to the payment in the Stripe Dashboard (`stripe.DashboardURL`, PAY-11: `/payments/<pi_…>`, `/test` for a test key, never the account id) so the treasurer can look into it there. The PaymentIntent id comes from an earlier refund of the payment or from the stored charge, so the link appears once the balance sync has listed the charge.

**Where refunds and disputes show (BRY-498).** The payment overview lists orders that are `paid` or `refunded` and gives each `refund_state` (`none` / `partial` / `full`) and `refunded_amount` from the refunds Stripe confirmed against the attempt that paid the order, and `dispute_status` / `dispute_due_by` from the latest dispute of the order's attempts; the chips are *Refundert*, *Delvis refundert* and *Omstridt* (*Tvist tapt* / *Tvist vunnet* once decided). The faktura list gives each faktura the same from the credit notes the booking pass issued (`refund_documents`), so it follows the books, not Stripe: a fully refunded faktura has `credit_state` `refunded` and lists its credit notes, and *Ny faktura* (`can_reissue`) issues a replacement. A treasurer or admin also gets Dashboard links built with `stripeDashboardURL`: the payment (`/payments/<pi_…>`) on the refund chip, the dispute (`/disputes/<dp_…>`) on the dispute chip, and, in the payment overview while any dispute waits for an answer, `/disputes?statuses[0]=needs_response&statuses[1]=warning_needs_response&statuses[2]=appeal_needs_response&sort=evidence_due_by&order=asc`. The member portal shows a fully refunded faktura as *Refundert*, a partly refunded one as *Betalt* with the amount paid back, and a refund's credit note as *Kreditnota – refusjon*, with the credit notes' numbers and PDFs; never the reason, the links or a dispute. The rules are in [`invariants.md`](reference/invariants.md).

### Disputes

A card dispute (the cardholder asks the bank to take the payment back) is two separate things, kept apart on purpose (ACC-4, ACC-5):

- **The books** follow the balance. The `dispute` balance transaction (money withdrawn, plus a dispute fee) is booked by the booking pass DR the dispute account / CR 1580 and DR 7700 / CR 1580; the `dispute_reversal` (the club won) books the mirror. The faktura stays paid. See [the accounting README](../../backend/internal/accounting/README.md#card-disputes).
- **The state** follows the webhook: `payment_disputes`. `charge.dispute.*` events carry no metadata of Brygge's, so the attempt is found through the dispute's `payment_intent`: the PaymentIntent is fetched and its `metadata.attempt_id` names the attempt, and with it the club, so the event is stored under the right club rather than the instance's. When that fails (no metadata, the lookup failed) the stored charge is found by its charge id, and failing that the dispute is stored for the instance's club with no attempt. A PaymentIntent whose `metadata.club_slug` names another deployment (the Stripe account is shared) is left alone, unless its `attempt_id` is an attempt of ours (a club slug can be renamed). If Stripe cannot be asked at all (a 5xx or a timeout, not a 404) and the charge row does not place the dispute either, the event is answered 5xx so it is delivered again, rather than guessed to be ours. The dispute object is decoded leniently, field by field: what is missing or of the wrong type is left out and nothing fails the event. An upsert is idempotent, takes the status forward only (an old event never reopens a finished dispute; an inquiry escalating to a chargeback under the same id is forward) and keeps fields a later event leaves out. A dispute that cannot be stored answers 5xx so Stripe delivers the event again.
- **The treasurer** is emailed once for each phase the dispute is open in: when it is first stored as an inquiry or a chargeback, and again when an inquiry becomes a chargeback (a new deadline). A guarded update on `payment_disputes.notified_phase` claims the notice, so a redelivery, a later event or a dispute that arrives already closed tells nobody: the amount, the faktura or order, Stripe's reason, the evidence deadline and a link to the dispute in the Stripe Dashboard. No card data and no payer name. It is best effort: no `clubs.treasurer_email`, no SMTP, or a failed send is logged and never fails the event. The answer to the dispute (the evidence) is given in the Stripe Dashboard.
- **Dashboard links** are built by `stripe.DashboardURL(secretKey, path)` (`handlers.stripeDashboardURL(cfg, path)`): `https://dashboard.stripe.com/<path>`, with `/test` after the domain when the configured key is a test key (`sk_test_` / `rk_test_`), and never an `acct_` id.
- **Refunds** cannot be made while a dispute stands in the way: `payments.OpenDisputeForAttempt(ctx, q, clubID, attemptID)` returns the dispute that blocks refunding an attempt (Stripe's `is_charge_refundable` when the events gave it; otherwise a chargeback awaiting a response or under review, or a lost one. An inquiry does not block: refunding is how it is settled). The refund endpoint calls it before it asks Stripe (409 `disputed`, `can_refund` false) and still handles Stripe's `charge_disputed` refusal as a failed refund, since this state can lag Stripe's.

## Adding a provider

1. Implement `payments.Provider` (and `Canceller` if it can void) in the provider's own package, next to its API client.
2. Register it in `cmd/api/main.go` when its credentials are present. Secrets go in `/etc/brygge/env` (see the env layering rules in [configuration.md](configuration.md)).
3. Add its webhook handler: verify the signature, persist the event in `payment_webhook_events`, resolve the attempt with `attemptByReference` (or `attemptByID`), then call `authorizeAttempt` (if the provider authorizes before capturing) / `markAttemptCaptured` / `markAttemptFailed`. Do not write order or invoice payment state anywhere else.
4. Let the payer choose it: the pay routes resolve a requested name with `resolveProvider` and pass it to `mintOrderPayment`; `availableProviders()` lists it to the pages. Give it a method in `PayMethodButtons.vue` (`METHOD_BY_PROVIDER`, a label under `pay.methods.*` in all locales) and in the email label (`emailPayMethods` / `email.PayMethodsLabel`); until then the pages skip it.
5. Book its fees and clearing balance with the accounting owner before going live (Stripe's: [Stripe accounting](#stripe-accounting)).
