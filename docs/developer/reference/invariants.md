# Invariants

The things that must never be violated. Agents respect what's explicit and invent what's not — these are the implicit rules that get silently broken otherwise.

Each invariant lists the **rule**, then the **failure mode** it prevents. When proposing code that touches the relevant subsystem, this is the first doc to consult.

---

## Accounting

### Closed fiscal periods are immutable

**Rule:** no journal entry can be created in, posted to, or voided into a period whose `fiscal_period_status` is `closed` or `locked`. The guard sits inside the service functions themselves, not only in their callers: `CreateJournalEntry` and `PostJournalEntry` refuse a non-open period, and so does `VoidJournalEntry` (BRY-333), all with `ErrPeriodClosed`. Handlers map that error to 409 with `code: "period_closed"`.

A void is **refused**. Its reversal never moves to a later open period instead, because a closed year's figures have been reported. To correct it, either reopen the period deliberately, or book a new correcting entry (e.g. a credit note) in the current period. Callers rely on that guard rather than a period pre-check of their own, which `ClosePeriod` could race. Callers that act on a group of entries (`ReverseInvoice`, `UnassignBankRow`) void them all in one transaction through `voidJournalEntryTx`; one entry in a closed period rolls back the voids before it, so the group is reversed completely or not at all.

Closing is serialised against writers. `CreateJournalEntry`, `PostJournalEntry` and `VoidJournalEntry` hold the period row `FOR SHARE` until they commit. `ClosePeriod` takes it `FOR UPDATE` before it counts drafts, so it waits for in-flight writers and then sees what they committed. A reference period (below) skips the draft count: its drafts can never be posted, so closing it strands them on purpose.

**Failure mode:**
* Silent corruption of a balance sheet that has already been reported to the styre or filed with Skatteetaten (a bokføringsloven §13 violation).
* Before BRY-333, `VoidJournalEntry` wrote its reversal into closed periods unchecked.
* A draft created while the period was being closed could land in it for good.

### A reference period books only costs and carries nothing forward

**Rule (BRY-418, ACC-12):** a fiscal period marked `reference_only` is a year whose books of record live in another system. Its data stays (nothing is voided or deleted) and its reports still open when it is picked, but Brygge does not book it, and it feeds no queue, count, automatic pass or carried balance.

- **One shape of booking is allowed.** An entry may be created in, posted in or voided from a reference period, **or dated in one whatever period it targets**, only when every line is on a cost account (`accounts.account_type = 'expense'`) or a bank account, and at least one line is on a cost account. A bank account is the cash range (`inCashRange`: 1900, 1920–1949) plus every `bank_imports.bank_account_code` and `club_bank_accounts.gl_code` of the club (`bankAccountCodesIn`). The club's provider clearing accounts (`clubs.vipps_clearing_account`, the Stripe clearing account, and 2900) are never bank accounts here, even inside the range. That allows an outgoing bank row booked to a cost account (DR cost / CR bank), a cost moved between cost accounts, a supplier refund (DR bank / CR cost) and a manual bilag of any of those shapes; it refuses revenue, 1500, 2400, equity, the clearing accounts, bank-to-bank transfers, `opening_balance`, every `invoice_sync` / `invoice_resplit`, every Vipps and Stripe posting, the KID cascade, bank auto-assign and every faktura assign.
- **The guard is in `journal.go`.** `createJournalEntryTx`, `postJournalEntryTx` and `voidJournalEntryTx` apply it (`refuseNonExpenseShapeTx`, `ErrReferencePeriod`, 409 `reference_period` with a Norwegian message). It keys on the entry date as well as the period (`dateInReferenceIn`): otherwise a 2025 deposit booked into the 2026 period (a manual match, a rule, an import override) would become 2026 income. Every journal entry is inserted there, and `TestJournalWritesOnlyThroughTheGuard` fails when any other non-test file inserts or updates `journal_entries` or `journal_lines` (allowlist: the attachment link, and the bank-account reassign, which refuses reference periods itself). A new path that writes journal rows must go through the guard or be added to that test with a reason.
- **Concurrency.** A writer holds its period `FOR SHARE`; `dateInReferenceIn` takes the date's period `FOR SHARE` too. `SetPeriodReference` takes the period `FOR UPDATE`, so the flag cannot flip under an in-flight booking.
- **A row belongs to the period of its own date**, not of an import's override: a bank row by `row_date`, a Vipps row by `COALESCE(booking_date, tx_at::date)`, a Stripe balance transaction by `stripeBookingDate`. Queues, counts and automatic passes exclude a reference year with `referenceDateSQL(clubExpr, dateExpr)`. The columns must be qualified with their table (`bank_import_rows.club_id`): in the predicate's subquery a bare `club_id` resolves to the fiscal period's own column and is always true, which would make another club's reference year hide this club's rows.
- **Left out.** `tildelScope` (the Tildel list, its badge and the year counts); the Vipps queue, the unreconciled Vipps charges, the missing-settlement list and the pending-refund list, count and outbound candidates; the KID cascade (`kidCascadeEligibleSQL`); bank auto-assign; intra-bank transfers; mapping-rule auto-match; Vipps auto-assign and `AutoReconcileOrderCharges`; the Vipps payout sweep (deposits and payout rows dated in a reference year are not candidates, and a refusal by the guard is reported as skipped, never failed); the legacy Vipps reconcile; the 3900 reclassification of Vipps charges (`loadFallbackCharges`, its closed-period count, the plan's period check and the transaction's re-read all exclude reference years); the Stripe booking pass (`StripeDeferReferencePeriod`) and payout clearing; and the payment backfills (`backfillUnlinkedPayments`, `backfillInvoiceNumberPayments`: they would mark fakturas paid from a reference year's bookings). The three passes that delete a draft and rebook it (`ResyncVippsBilags`, the Vipps cutover regeneration, bank sync's `healStrandedKIDDrafts`) skip reference drafts, so those stay. Whole-period operations (`SyncPayments`, `SyncInvoices`, `ResplitInvoiceBilags`, `PostVippsDraftBacklog`, `AutoMatchImport`) refuse a reference period up front with `ErrReferencePeriod`, and `UnassignVippsCharge` refuses every charge dated in one (before the cleared-settlement guard), whatever its entry's state, because the unassign reopens the fakturas the charge settled and a reference-year faktura must not reappear as open; the ledger void refuses such a charge's entry through the guard before it releases anything. Not covered: the Stripe lists (they date a row by `stripeBookingDate`, in the process's zone, not by a UTC date) and the per-import detail list, which is a record, not a queue. The outgoing rows of a reference year are listed only under Tildel's `kind=reference` (a mode switch, not a filter that ANDs with the others); `kind=reference,dismissed` lists the dismissed ones, which `POST /bank-rows/{rowID}/undismiss` (`UndismissReferenceBankRow`, fresh TOTP, audited `bank_row.undismissed` with the prior reason, who and when) returns to the list. A `superseded` or `duplicate` dismissal is final (`finalDismissalSQL`): it stands for money booked once already, so undoing it would count a cost twice in a filed momskompensasjon, and such rows are left out of the dismissed list. No other dismissal can be undone. Stripe deposits dated in a reference year stay waiting by design (`StripeClearReferencePeriod`). Its incoming rows appear nowhere.
- **Reports.** `BalanceSheet` is the only cumulative report and skips every reference period except the selected one (`fp.id = $3 OR NOT fp.reference_only`), so 1500 and the bank balance carried into a later year come from the opening balance alone. The cash-flow chart leaves reference years out (it counts drafts). Momskompensasjon reads a reference year as any other; its "has drafts" warning counts only drafts the guard's own rule would let post (`referenceExpenseDrafts`), and its MVA sums follow each line's side (`mva_amount * SIGN(debit - credit)`), since a void's reversal copies `mva_amount` onto swapped sides; a journal line's `mva_amount` is therefore never negative (`ErrNegativeMVA`, 400 `negative_mva`). The income statement, balance sheet, trial balance, general ledger and momskomp responses carry `reference_only`, and the income statement and balance sheet PDFs print a "Referanseår" line.
- **Marking.** `POST /accounting/periods/{id}/reference` (treasurer/admin, fresh TOTP) is refused for the year covering today (`reference_current_year`) and for a year holding any non-voided `opening_balance` entry, drafts included (`reference_has_opening_balance`); unmarking needs the period open (`period_closed`). A faktura booked in a reference year cannot be voided or credited there (`ReverseInvoice` answers `ErrInvoiceReferencePeriod`), so the mark dialog warns about the year's posted `invoice_sync` entries for fakturas still open.
- **Closing a reference year skips the draft check** (above) and is how cost bookings stop once the year's momskompensasjon is filed.
- **A provider settlement in flight at year-end is carried in the opening balance.** Its charges and fee stay as reference-year entries the guard never lets post. The opening balance (dated 1 January: a 31 December date is refused by the date rule) carries the amount as a debit on the clearing account (DR 2900), and what the new-year deposit does depends on its state:
  - **Already booked** (a posted DR bank / CR clearing in the new year): nothing more is needed. The sweep never touches a booked deposit.
  - **Unbooked, and every charge of the settlement posted** (they were posted before the year was marked): `ClearVippsPayout` may proceed. A settlement with a fee has its fee entry (DR 7700 / CR clearing, dated in the reference year) refused by the guard, which the sweep reports as skipped with a reason pointing to the opening balance, never as failed; one without a fee clears like any deposit.
  - **Unbooked, and a charge is only a draft** (`chargePostedSQL`, BRY-555: a charge counts toward a clearing only when its entry is posted): the settlement can never become ready. `ClearReadyVippsPayouts` reports it as skipped with the same reason, not as waiting (`vippsSettlementIsReference`: the payout row is dated in a reference year).
  - In the two unbooked states that are skipped, the deposit is booked by hand with a bilag DR bank / CR clearing (`refuseProviderPayouts` blocks the Tildel assigns) and its bank row is dismissed. The payout's own Vipps row is dated in the reference year, so `payoutsWithoutOpenDeposit` leaves it out.
  See [migrating-from-previous-system.md](../../user/migrating-from-previous-system.md).
- **Rollout.** The flag defaults to false and nothing backfills it, so every part of the change ships on its own and changes nothing until a year is marked. The operator marks a year only after the guard, the queue filters, the bank-sync and import passes and the SPA toggle are all deployed: a year marked earlier would refuse bookings its queues still offer. Marking is a UI action (`Admin → Regnskap → Bilag`), never SQL.
- **Repairs that touch a reference year's rows** must not go through `UnassignBankRow`: it voids the entries, which the guard refuses unless they are expense-shaped. A scan that looks for rows to repair (BRY-557) must exclude reference periods itself.

**Failure mode:**
- 2025's −115,979.50 kr on 1500 carried into 2026's balanse, so receivables and the bank balance disagree with the opening balance.
- A payout sweep or a KID cascade failing on every sync over deposits of a year nobody books.
- Momskompensasjon for the reference year permanently "incomplete" because of its Vipps drafts.
- A 2025 deposit booked into 2026 as income by naming the open period (an import override or a manual match).

### Posted journal entries cannot be edited

**Rule:** once `journal_status` is `posted`, the only legal write is `VoidJournalEntry`. It marks the original `voided` and adds a balanced, posted reversal, and both stay in the GL. A posted entry is never updated or deleted: corrections are new entries (reversals, `invoice_resplit` reclassifications, credit notes). Only `draft` entries may be edited or deleted, and only drafts that no bank or Vipps row links to (`DeleteDraftJournalEntry`). Unassigning a row deletes its draft and voids its posted entry. A person voids through `VoidLedgerEntry`, which refuses an entry sourced to a Stripe balance transaction (see "A Stripe booking is undone only from its Stripe row").

**Failure mode:** historical reports start disagreeing with themselves, and an auditor finds the GL doesn't tie back to the printed annual report.

### Accounting reads and writes are club-scoped

**Rule:** every service function that acts on an id from a request also takes the caller's club id and filters on it. This covers journal entries (get, post, void, delete-draft), accounts (update, deactivate, get), fiscal periods (close, reopen) and bank rows (assign, unassign). Another club's id is reported as not found (`ErrEntryNotFound`, `ErrAccountNotFound`, `ErrBankRowNotFound`, mapped to 404), so a foreign id reveals nothing. The "already booked" subqueries in KID matching also join on the faktura's club.

**Failure mode:** an admin or treasurer of one club posts, voids, reopens or renames another club's records by guessing a UUID (BRY-367). This was harmless while every deployment ran one club, but not in a multi-tenant one.

### An order-linked charge is booked from its order

**Rule (BRY-337, BRY-454):** a provider charge that names its checkout order is booked from that order and nothing else, for every provider:
- CR 1500 for each `order_sources` faktura, with a payment back-link (`linkInvoicePayment`, after the commit);
- CR the category revenue account for each catalog line.

A Vipps `belastning` whose `order_id` equals an `orders.vipps_reference` is booked only by `AssignVippsChargeToOrder`; a Stripe charge row with its attempt's `order_id` only by `BookStripeBalance`. Both build the split with `orderChargeSplit` and check it with `checkOrderChargeSplit`: it is refused when the split differs from the charge amount, when a faktura on the order is already paid, voided or credited (`finance.OpenReceivableSQL`), or when one is imported without its receivable in the GL by the booking date (`finance.ImportedReceivableOpenSQL`). The Vipps path (`AssignVippsChargeToOrder`) first locks the order's fakturas in id order and re-checks each as a manual assign does (`lockInvoicesForManualAssign`: `lockInvoiceForAssign` in `lockManual` mode, so a credit note, a faktura with a booked row recorded against it (`invoiceBookedRowSQL`) and the cases above are refused), all inside its booking transaction; the Stripe path (`bookStripeChargeTx`) locks them with `lockSplitInvoicesTx` and runs only `checkOrderChargeSplit`, so it does not check for a booked row (open item). Vipps reports a refusal in `skipped_details` ("already paid, voided or credited — book the charge by hand", the specific cause kept for `errors.Is`); Stripe holds the row in `needs_review` (`split_mismatch`, `receivable_not_open`, `imported_no_opening_balance`) and retries it on the next booking pass. Such a charge is never classified by amount or payer name. Stripe's fee rides in the same entry (DR payment fee / CR clearing).

Every other settle path treats a faktura such a booked charge pays as booked (`invoiceBookedRowSQL`, through `order_sources`), so a bank or Vipps assign is refused even before the charge's payment back-link lands. A Stripe charge a person booked by hand (BRY-466) settles only the faktura in its `invoice_id`, never its order's: the order clause counts a Stripe row only while its `review_reason` is NULL, which holds for every row the booking pass booked and for none a person booked. Both Stripe clauses, and `stripeSettledInvoiceSQL`, count a row only while `stripeChargeSettlesSQL` holds (see "A card charge settles its fakturas through one predicate").

**Failure mode:** before BRY-337 nothing read the order reference. Pay-link payments stayed "betaling mottatt, venter oppgjør" for weeks: the money had been paid out, but the faktura never settled and the payout could not clear. A second rule per provider would drift: one provider crediting 1500 for a faktura the other refuses.

### Vipps charges are auto-booked only when unambiguous, and only on opt-in

**Rule (BRY-340):** `AutoAssignVippsCharges` runs after every Vipps CSV upload, operator Report API sync and **Synk Vipps**, but books nothing unless `clubs.vipps_auto_assign` is on. It books a charge in one of two cases. Anything else is left in Tildel.
- **Member faktura:** the payer resolves to one member by a strong pass (taught alias, KID, or the exact normalized full or first+last name; never last-name-only, fuzzy or email), and `decideMemberInvoice` settles it — see "A payment goes to a member's faktura only when it is the only one it can be" below.
- **Price item:** the amount fits active price items in one category. Several categories count as a tie. The club's `vipps_auto_assign_tie_category` resolves a tie only when every match is a per-unit (night, day or hour) price, for example guest slip versus motorhome at the same nightly rate. If the amount is also an exact one-off price in any tied category (a season, slipping, slip rent), the charge stays manual, so the tie category never absorbs amounts it can't explain. The chosen category must then fit the amount as a single unit: an amount that fits only as several nights (2,700 = 9 × 300) stays manual (BRY-398), so the tie rule only ever settles single-unit amounts. A members-only item also needs a strong member match. A member who has an open faktura for the exact amount is never price-classified. That includes an imported faktura (`import_source` set): an open imported faktura of the same amount sends the charge to review rather than to a price item or another faktura.

Charges naming a checkout order are left to `AutoReconcileOrderCharges`. Each booking is audited (`vipps_charge.auto_assigned`) and can be undone with `UnassignVippsCharge`.

**Auto-booking requires a faktura or an exact single-unit price match (BRY-398).** Every path that books without a human — `decideVippsCharge` (auto-assign and the `PostVippsDraftBacklog` rebook) and `matchVippsAmountToPriceArticle` (the legacy cascade and resync) — treats an amount that fits a per-night/day/hour price only as a multiple as undecided. Multiples stay suggestions: `priceItemAccountSuggestions` shows them, never above `svak`.

**Failure mode (multiples):** 2,700 kr fits 9 × 300 kr a night, so it was booked to motorhome revenue, but it was season rent no price item lists. A multiple is a guess at how many nights were paid for, and nothing in the charge confirms it.

**Failure mode:** guessing on a weak name match or a cross-category amount books a member's dues as walk-up revenue, or the reverse. The member is then chased for a faktura they paid, or revenue lands on the wrong account. With no opt-in, a club that never chose this would find bookings it didn't make.

### KID-less bank deposits are auto-booked only when unambiguous, and only on opt-in

**Rule (BRY-366):** `AutoAssignBankDeposits` runs at the end of every bank import (upload and both reimports) and as pass 4c of `BankSync`, but books nothing unless `clubs.bank_auto_assign` is on. That switch is separate from `vipps_auto_assign`. Candidates are incoming rows that are unbooked, undismissed, not refund-paired, not a provider payout deposit (Vipps settlement or Stripe payout, see "A provider payout deposit is booked only by its clearing") and not provisional (`partnerEligibleSQL` plus `providerPayouts`), carry none of our KIDs (`isBryggeKID`) and are not a bounced transfer. A row stays in Tildel, with the first reason it fails:
- `has_reference`: the description carries a KID or an invoice number; the KID cascade owns it.
- `no_payer`: no `Fra:` name in the description and no counterpart.
- `no_period` / `period_closed`: its date (or the import's chosen period) is not in an existing open fiscal period. The rule never creates a period. Checked after the row-only reasons, so a row that could never be auto-booked is counted as such.
- `own_club`: the payer is the club's own account, or its name when no account is known.
- `no_strong_member`: no taught alias and no unique exact name.
- the `decideMemberInvoice` reasons (see below).
- `has_partner`: the row has a strong BRY-380 partner.
- `possible_double_payment`: two or more rows in the run reach the same faktura; none is booked.

A booking goes through `assignBankRowToInvoice` with the faktura locked (`lockInvoiceForAssign`: `FOR NO KEY UPDATE`, held until the row is linked and posted). Under the lock it re-checks that the faktura is still owed, sent, not imported, has nothing booked against it and equals the amount, so a racing manual assign or a second run books at most once. The single-row and split-payment manual assigns (`AssignMultipleBankRowsToInvoice`) and the Vipps assign (`AssignVippsChargeToInvoice`, used by Vipps auto-assign) take the same lock and refuse a faktura another booked bank row or Vipps charge already points at, or that a booked Stripe or Vipps order charge pays (`invoiceBookedRowSQL`), so a Vipps and a bank payment can't both settle one faktura. The same `lockManual` mode refuses a **credited** faktura (`ErrInvoiceCredited`, `finance.CreditedSQL`: a live credit note linked by `credits_invoice_id`, or `refund_documents` credit notes adding up to the faktura total), because the credit note already cleared its receivable and a payment credited on top would credit 1500 twice (BRY-508), and a **credit note** itself (`ErrInvoiceNotDebt`, a total that is not positive: money the club owes back, never a receivable). Both are checked under the faktura lock, in the same transaction as the booking, for the bank-row, split-payment, Stripe and Vipps assigns alike. Partial refunds do not count as credited: their credit note is offset on 1500 by the refund payout, so the faktura stays assignable while it is still open. Auto-assign and the KID cascade keep their own `!owed` and `errInvoiceNotOpen` refusals. The lists that offer fakturas to assign (`potentialInvoicesByAmount`, `rankIncomingInvoices` and both `suggestion_count` hints) filter on `assignableInvoiceSQL` (`OpenReceivableSQL` and no booked row), so the UI does not offer a faktura the lock would refuse as cleared. An **imported faktura without an opening balance stays listed on purpose**: the assign is refused with `imported_no_opening_balance`, whose message tells the treasurer to wait for the opening balance, whereas hiding it would make the deposit look orphaned and invite booking it to revenue. The KID cascade (`ImportBankRows`, `syncKIDMatches`) takes it too and records `invoice_id` on its row, so every path that settles a faktura takes the lock (see "An auto-match posts or leaves nothing"). The entry is described `Automatisk tildeling: …`, records `invoice_id`, and keeps `auto_matched = false` like every Tildel booking: `healStrandedKIDDrafts` only releases KID drafts, so an `auto_matched` rule booking stranded between link and post would never be healed. Provenance is the `bank_row.auto_assigned` audit row. There is no unattended bank sync; without an acting user the rows are reported as `no_actor`. Undo is `UnassignBankRow`, and the next sync books the row again if it is still unambiguous.

While `bank_auto_assign` is off, the KID cascade's third step (`findInvoiceByCounterpartAndAmount`: full name + amount, no aliases or other guards) still runs at import and sync. When it is on, that step is skipped and this rule replaces it. `GET /admin/accounting/bank-rows/auto-assign/preview` projects the rule as if on, writes nothing and returns no names.

**Failure mode:** the ungated name+amount step booked a deposit to whichever member's faktura matched, with no opt-in, no aliases and no check for a payment made before the faktura, a partly paid faktura or a member with two open fakturas. Turning a replacement on at deploy would have changed live bookings before anyone saw what it would do.

### A payment goes to a member's faktura only when it is the only one it can be

**Rule (BRY-340, BRY-366):** every rule that books a payment to a member's faktura without a human (Vipps auto-assign and bank auto-assign) goes through two shared steps in `auto_assign_member.go`:
- **One member.** A name pass (`matchMemberName`, passes full name and first+last) is strong only when the normalized name belongs to exactly one member. A name two members share is no strong match; resolution falls through to the weak passes, which the auto-assign rules never act on. A taught alias wins over every name pass. For Vipps, a KID in the message that resolves to a member wins over the alias, because it names the faktura being paid; when the KID and the alias name different members, `resolveCustomerToMemberPass` returns `memberPassConflict` with no member, and Vipps auto-assign leaves the charge in the queue rather than booking it to either member or classifying it by amount (BRY-383). The other callers of `resolveCustomerToMember` see the same uniqueness: the legacy payout cascade (`ReconcileVippsPreview`) books a member match to 1500 for a human to reconcile, so a shared name there now falls to the weak passes too, and the read-only `vippsaudit.go` report matches the same way.
- **One faktura** (`decideMemberInvoice`). Candidates are the member's sent fakturas still owed (`finance.OwedByMemberSQL`). The payment is booked only when exactly one candidate was issued on or before the payment date, nothing is booked against it yet (no booked bank row with its `invoice_id` or its KID, no booked Vipps charge with its `invoice_id`), and its total equals the amount in integer øre. Imported fakturas (`import_source` set) are never targets, because they have no GL receivable; an imported open faktura of the same amount leaves the payment for a human. Reasons: `no_open_faktura`, `several_open_fakturas`, `amount_mismatch`, `faktura_after_payment`, `faktura_partly_paid`, `imported_faktura`.
- For Vipps, a member with an open faktura of the same amount that the rule could not settle (`SameAmount > 0`) is never price-classified either.

**Failure mode:** before BRY-366 the first of two same-named members took the payment, a payment made before the faktura existed settled it, and a second payment to a partly paid faktura was booked as if it covered all of it.

### A payer alias never takes a name from another member unasked

**Rule (BRY-383):** payer aliases (`vipps_customer_aliases`, unique per club and lowercased name) are taught from two places, and both auto-assign rules resolve them first:
- **Tildel.** Assigning an incoming bank row (single or split) to a member's faktura with `remember_payer` saves the row's payer (`bankRowPayer`: the `Fra:` name, else the counterpart, the same name auto-assign resolves) for the faktura's member. `teachPayerAlias` runs inside the faktura-lock transaction before any entry is created: it re-checks the conflict, inserts the alias, and only then are the rows linked and posted, so a refused or failed booking saves no alias. It saves nothing when there is nothing to learn: a faktura without a member, an empty payer, the club's own payer (`partnerScoring.isOwn`), split rows with different normalized payers, or a payer that already resolves to that member.
- **Vipps queue.** `POST /vipps/customer-aliases` (treasurer/admin, fresh TOTP) refuses a `user_id` that is not in the club. `DELETE` is gated the same way.

A **conflict** is a payer whose normalized name equals *any* other member's full name or first+last (not only a unique match), or is already another member's alias. Tildel refuses it with 409 `alias_conflict` and books nothing unless the request carries `confirm_alias_override`. No response names or identifies another member: the suggestions' `payer_alias` carries only `payer`, `pass`, `own_club` and `taken` (the name is some member's own name or alias), and which candidate faktura the payer already resolves to is a per-candidate `payer_resolves_here` on the suggested and amount-matched fakturas, computed server-side from one resolution per request. Both sources audit `payer_alias.taught` / `payer_alias.removed` without the payer name. An alias never outranks a Vipps KID that names another member (see "One member" below).

**Failure mode:** an alias silently pointing a member's own name at someone else sends that member's future payments to the wrong faktura through auto-assign, with no human in the loop. An ungated alias write did the same from any board session.

### A Vipps payout clears as soon as its settlement's charges are booked

**Rule (BRY-340):** on the per-charge model, `ClearReadyVippsPayouts` clears every unbooked bank deposit carrying `Utb. <settlement> Vippsnr <msn>` whose settlement has no `belastning` (same MSN + booking date) left that is undismissed and not posted (unbooked, on a draft or on a voided entry). It runs at the end of `BankSync`, after auto-assign in each operator Vipps path (CSV upload, Report API sync, **Synk Vipps**) and after a `PostVippsDraftBacklog` apply — all behind the money gate. The nightly Report sync has no acting user and does not clear.
- Clearing is `ClearVippsPayout`: a posted fee entry for the settlement's unbooked fee rows, then a posted bank entry, so the settlement nets the clearing account to 0.
- The whole clearing runs in one transaction that first locks the settlement's payout rows (`lockSettlementPayoutsTx`: `FOR UPDATE`, MSN + booking date), re-reads the deposit and the payout row under that lock, and holds it to the commit. The fee rows and the bank row are each linked with a guarded update; a clear that links fewer fee rows than it read lost a race and rolls back rather than posting the fee twice, and a failure anywhere leaves neither entry behind. The lock is what makes "every charge is booked" stay true until the clearing commits (see "A charge in a cleared Vipps settlement is not unbooked").
- A deposit without a parseable reference is never matched by amount. An imported payout no deposit names is reported as skipped with a reason, as is a deposit naming a settlement that was never imported.
- A deposit clears only if it equals the imported net payout to the øre; otherwise it fails with a reason and nothing is posted.
- A settlement clears once. A second deposit naming a settlement whose payout row is already linked to a standing entry, or that another booked deposit names, is skipped ("allerede avstemt"), never booked.
- Charges and fees carry only MSN + booking date, so when two payouts share both, neither is cleared automatically.
- Both the fee and the bank period are checked before either entry is created; a period that is not open refuses the whole clear.
- A sweep failure never fails the sync or import that ran it: callers use `ClearReadyVippsPayoutsReported`, which logs and sets the result's `error`.

**Failure mode:** before this, Stage 2 ran only from the per-row Tildel action, so a sync reported "Vipps-avstemt: 0" and the clearing account kept the full gross of every settlement while the bank deposits sat unbooked.

### A charge in a cleared Vipps settlement is not unbooked on its own

**Rule (BRY-555, ACC-11):** a posted booking of a Vipps charge cannot be taken back (unassigned, or voided from the ledger) while its settlement has a posted clearing. What a posted charge books can only be replaced atomically, with the same clearing debit (`rebookVippsChargeTx`). A charge counts as booked for a settlement's clearing only when its entry is posted.
- **Booked means posted.** `ClearVippsPayout` gates on `chargePostedSQL`: a charge linked to a draft, or to a voided entry, is not in the ledger, so the settlement waits ("N belastninger er ikke bokført"). Clearing around such a charge would leave the clearing account (2900) holding the settlement's fee and payout credits with no charge debit against them.
- **Cleared** means `postedSettlementClearing` holds for a payout row with the charge's MSN and booking date: the payout row is linked to a posted entry, or a booked deposit naming the settlement (`Utb. <n> Vippsnr <msn>`) is on a posted entry. A draft payout or deposit is not a clearing, so the charge may still be unbooked. `settlementClearedElsewhere`, which refuses a second clearing of a settlement, counts any non-voided entry and is separate.
- **Refusal.** `UnassignVippsCharge` (the charge's Angre, the auto-assign undo) and `VoidLedgerEntry` on a charge entry (an order-booked charge is undone there) return `*ChargeInClearedSettlementError` (`errors.Is(err, ErrVippsChargeInClearedSettlement)`). The handlers answer 409 `charge_in_cleared_settlement` with `settlement_number`, `msn` and `bank_row_id` (the deposit that carries the clearing entry; absent when no bank row does). Nothing is voided, unlinked or reopened.
- **Undo the clearing, then correct.** Angre of the deposit (`UnassignBankRow(bank_row_id)`, `POST /bank-rows/{id}/unassign`) voids the payout entry and releases the deposit and the payout row; the fee entry stays booked on its fee rows. The deposit is then in Tildel, the charge can be unbooked and booked again, and the next sweep clears the settlement with a new payout entry, so the fee is booked once and 2900 nets to 0. The SPA offers it as "Angre innbetalingen" wherever the refusal shows (`ClearedSettlementRefusal`), behind a fresh TOTP and a confirmation. The refusal does not do it itself: undoing a payout is a bank-ledger action on a deposit that then returns to Tildel.
- **Replacing a booking atomically is allowed.** `rebookVippsChargeTx(ctx, tx, clubID, actorID, rowID, credits, invoiceID)` voids the charge's entry (or deletes a draft), posts the replacement through `postChargeTx` on the old entry's date, relinks `journal_entry_id` and `invoice_id` and reopens the old faktura, in the caller's transaction. It requires the old entry's clearing-account debit and the new lines' credits to equal the charge amount (`ErrRebookClearingDebit` otherwise, and the caller's transaction rolls back), so the settlement's clearing account is the same before and after and the payout clearing is never touched. A replacement line on the clearing account is refused with the same error. The new faktura's payment back-link is the caller's after the commit (`vippsRebook.InvoiceID`, `linkInvoicePayment`). `reclassifyFallbackCharge` (BRY-557, a posted charge's revenue moved off 3900) uses it too and is the other exception to the refusal above: it unlinks a charge from a posted entry in a cleared settlement without the cleared-settlement check, which is safe because the replacement debits the clearing account by the same amount in the same transaction (the helper asserts it), so the settlement's fee and payout credits still net to 0; it records its prior entries in its batch audit row, not per charge. `applyBacklogReclass` uses it and audits `prior_journal_entry_id` and `prior_invoice_id` in `vipps_charge.auto_assigned`.
- **Only a posted entry is guarded.** A draft charge entry is not in the ledger, so releasing it leaves 2900 as it was; a charge still linked to a voided entry is just released by `UnassignVippsCharge` (and the fakturas its order paid are reopened). A legacy settlement's charge (entry shared with a bank row) keeps `ErrVippsChargeInSettlement`, checked first.
- **The ledger void releases the charge.** `VoidLedgerEntry` on a Vipps charge entry (the undo of an order-booked charge) unlinks the charge from the voided entry (`journal_entry_id`, `invoice_id`, `auto_assign_rule` cleared, so it is back in the Vipps queue and its settlement waits for it) and reopens the fakturas it settled (`invoice_id` plus the order's `order_sources`, each only when no other booked row settles it: `reopenUnbookedFakturasTx`), in the same transaction, after locking those fakturas and the settlement's payout rows. A charge left linked to a voided entry would be in no queue (all select `journal_entry_id IS NULL`) and would hold its settlement back for ever.
- **A settlement's fee or payout entry is not voided from the ledger.** `VoidLedgerEntry` refuses an entry a `vipps_import_rows` fee or payout row points at (`VippsSettlementEntryError`, 409 `vipps_settlement_entry`; a payout entry is also bank-linked, 409 `bank_entry`). Voiding a fee entry would leave its fee rows linked to a voided entry, and neither the sweep nor a re-clearing books the fee again. There is no in-app undo of a fee entry on its own; it is corrected with a new manual bilag.
- **Concurrency.** The check and `ClearVippsPayout` serialise on the settlement's payout rows (`lockSettlementPayoutsTx`, `FOR UPDATE`). The unbook and the rebook lock in the order faktura(s), charge, payout rows, entry; the clearing and the backlog posting of a settlement's drafts take the payout rows first; the ledger void takes the fakturas and the payout rows before the entry; `UnassignBankRow` takes the payout rows of the settlements its entry clears (`lockBankRowSettlementsTx`) before it locks any entry. Whichever comes second sees the other's committed state: a clear that wins refuses the unbook, an unbook that wins makes the clear see an unposted charge and wait, and a rebook never fails against a clear.
- **A backlog run posts a settlement's fee and payout drafts only when every charge of the settlement is posted** (`backlogPostSettlement`): the check and the posting of the settlement's drafts run in one transaction under the payout-row lock, after the period's charge drafts were posted or rebooked; otherwise the drafts stay and `Refused` says how many charges are not posted. An apply reads the database for that: only a preview uses its own prediction of the charges it would post. The preview therefore counts every reclassified charge as booked; if the treasurer unticks one, the apply leaves its settlement's drafts as drafts (the checklist label says so). A legacy settlement bilag (charges linked to the same entry) posts as it stands.

**Failure mode:** unbooking a charge after its settlement cleared, or clearing around a charge that is only a draft, leaves the fee and payout credits on 2900 with no charge debit against them until the charge is booked again.

### The Stripe balance ingest only mirrors; it never books or overrides a decision

**Rule (BRY-453):** `SyncStripeBalance` and `IngestStripePayout` write only `stripe_balance_transactions` and `stripe_payouts`, never the journal. A stored balance transaction is reclassified only while it is `needs_review` for an ingest reason; `unbooked`, `booked` and `dismissed` rows, rows the booking pass holds for review (`split_mismatch`, `receivable_not_open`, `imported_no_opening_balance`, and the refund reasons `refund_unlinked`, `refund_charge_unbooked`, `refund_origin_dismissed`, `refund_legacy`, `refund_failure_settled`, `refund_failure_reissued`, `refund_split`, and `dispute_account_missing` for a dispute) and rows a person holds (`unassigned`, BRY-467) are skipped. One list, `stripeHeldReviewReasons`, drives both ingest sites (the pre-read skip and the upsert's guard); the booking pass retries only its own reasons (`stripeBookingReviewReasons`), never `unassigned`. Booking is `BookStripeBalance`'s alone, and it needs an acting user, so the nightly job and the payout webhooks never book. A payout's status never moves back (`failed` and `canceled` are final, `paid` gives way only to `failed`), and a failed payout releases its members only while it is not cleared in the books. Every write is a single upsert or guarded update with no transaction open, and Stripe is never called while a lock is held. The listing cursor comes from the `stripe_sync_state` watermark, which only a complete, error-free sync advances; one ingest runs per club at a time.

**Failure mode:** a re-sync that rewrote classified rows would undo a person's dismissal or re-point a booked charge, and one that reclassified an unassigned row (or a pass that retried it) would book again what a person just undid, and a stale `in_transit` answer arriving after `payout.failed` would re-link transactions that are about to be paid out again in another payout. A cursor taken from the newest stored row skipped the older pages of a run that failed part-way, and a payout ingest storing a new row could jump it the same way.

### A Stripe row in review is settled by a person only as its review reason allows

**Rule (BRY-466):** a Stripe balance transaction in `needs_review` is booked or set aside by hand only through `AssignStripeTxnToInvoice`, `AssignStripeTxnToAccount` and `DismissStripeTxn`, and only as `stripeAllowedActions` allows for its category, currency and review reason (the matrix is in the accounting README); the server enforces it, the UI only mirrors `allowed_actions`.
- Each action runs in the club's Stripe slot (5 s bounded wait, else 409 `busy`) and in one transaction that locks the row first, then (faktura assign) the faktura with `lockInvoiceForAssign` (`lockManual`, booking date = the row's), and does everything through that transaction; `linkInvoicePayment` runs after the commit.
- A faktura assign needs the charge to equal the faktura total to the øre, posts DR Stripe clearing / CR 1500 the charge plus the fee lines, and records `invoice_id` on the row in the guarded mark that books it, so every later settle path sees it (`invoiceBookedRowSQL`). `invoice_id` on a Stripe row is set only there.
- An account assign never goes to 1500, 2900, a provider clearing account, 19xx or a bank account the club uses; it is signed (money in DR clearing / CR account, money out the reverse) with the fee lines, so what stays on clearing is the row's net, as when the booking pass books it.
- Unlike the booking pass, a manual booking resolves its period with `resolvePeriodIn`, which may create the fiscal year: a person decided to book on that date. A closed or locked period is refused (`period_closed`).
- A manually booked row keeps its `review_reason` (the marker that it was booked by hand); the booking pass and ingest never touch a `booked` row.
- A row whose payout is cleared in the books is never assigned or undismissed (`payout_cleared`); only dismiss remains.
- A dismissal posts nothing and keeps the review reason. The payout that carried the row still takes its net off the clearing account when it clears (dismissed members count as done), so the clearing account is off by that net until it is booked another way; the dialog says so. Undismiss returns the row to `needs_review` with its reason (or `unbooked` without one), and is refused once its payout is cleared in the books (`payout_cleared`), since that clearing counted the row as done.

A faktura assign's payment back-link (`linkInvoicePayment`) runs after the commit but still in the club's Stripe slot, so an unassign cannot slip between the two and leave the faktura marked paid by a voided entry.

**Failure mode:** a faktura assign without the faktura lock and `invoice_id` would let a bank payment of the same faktura credit 1500 a second time; an order clause that counted a hand-booked row would mark the order's fakturas paid although the money went to an account (or another faktura); an undismiss after the payout cleared would leave a cleared payout with an open member.

### A Stripe booking is undone only from its Stripe row, and the row is then held for the person

**Rule (BRY-467):** an entry sourced to a Stripe balance transaction (`source_table = 'stripe_balance_transactions'`: a charge or fee the booking pass booked, or a manual assign) is undone only by `UnassignStripeTxn`; the ledger's void (`VoidLedgerEntry`, the `POST /journal/{entryID}/void` path) refuses it with `ErrStripeSourcedEntry` → 409 `stripe_entry`, read under the entry's lock. Internal paths call `voidJournalEntryTx` / `VoidJournalEntry` directly and are not refused. For the same reason the ledger refuses an entry a bank row or a Stripe payout points at (`bank_import_rows.journal_entry_id`, `stripe_payouts.journal_entry_id`; `ErrBankLinkedEntry` → 409 `bank_entry`): payout clearings, KID matches and every Tildel booking are undone with `UnassignBankRow`, which releases the row, its faktura and the payout. Vipps charge entries are refused only once the charge's settlement is cleared (`ErrVippsChargeInClearedSettlement` → 409 `charge_in_cleared_settlement`, see "A charge in a cleared Vipps settlement is not unbooked"); otherwise `UnassignVippsCharge` sends an order-booked Vipps charge to the ledger void.
- The unassign runs in the club's Stripe slot (5 s bounded wait, else 409 `busy`) and one transaction, locking the row, then the fakturas the entry settled (in id order, `lockInvoicesTx`), then the entry and its period through `voidJournalEntryTx`. Row before fakturas is the booking pass's and the manual assign's order; nothing uses the pool while those locks are held.
- The fakturas it settled are those `invoiceBookedRowSQL` counts for the row (`stripeSettledInvoiceSQL`): `invoice_id` (a manual faktura assign), and the order's `order_sources` fakturas only when `review_reason` is NULL (booked by the pass from the order). A row a person booked to an account never reopens its order's faktura, which may since have been paid by the bank.
- Each such faktura is reopened with `reopenInvoicePaymentTx`, the helper the bank and Vipps unassigns use: `payment_id` cleared, the `payments` row it pointed at deleted. `online_paid_at` stays: the card money did arrive, and the marker keeps the faktura off bank and Vipps matching (`finance.OwedByMemberSQL`) while the row is held, so a bank deposit of the same amount is not booked against it. The order booking path ignores the marker (`finance.OpenReceivableSQL`), so a rebook still settles it. The downside: if the card payment really belonged to another faktura (the person then books the row there), the original faktura keeps its "paid online" marker, so reminders and bank matching keep skipping it although it is unpaid; clearing the marker is tracked separately.
- The row becomes `needs_review` / `unassigned` with no entry and no `invoice_id`. A posted entry is voided with a reversal in its own period; a closed or locked period refuses the whole unassign (`period_closed`). An entry already voided (in the ledger before this refusal existed) is tolerated: no second reversal, the fakturas and the row are still released.
- Refused: a `payout` / `payout_reversal` row (`use_bank_unassign`), a row whose payout is cleared in the books (`payout_cleared`: the clearing counted it; undo the deposit first), and a row not `booked` or whose entry is not its own (`not_allowed`).
- A held row allows `rebook` (a charge with an order, or a fee: back to `unbooked`, review reason cleared by a guarded update, then the booking pass books that row at once in the same hold of the slot and re-checks everything), and the manual assigns and dismiss as for any row in review (only a charge goes to a faktura). It is never booked again without a person.

**Failure mode:** a ledger void left the Stripe row `booked` against a voided entry and its fakturas paid with no 1500 credit behind them, and nothing would ever re-book the charge. Releasing the row to `unbooked` instead of holding it would let the next pass book it straight back, undoing the person's decision; reopening the order's fakturas for a row booked to an account would erase a bank payment.

### A card charge settles its fakturas through one predicate

**Rule (BRY-446):** whether a booked Stripe row settles a faktura is decided by `stripeChargeSettlesSQL` alone: the row is a `charge`, it is booked, and its `recollected_at` is NULL. Every clause that asks (both Stripe clauses of `invoiceBookedRowSQL`, `stripeSettledInvoiceSQL` for the unassign, the refund booking and the transaction list) uses it. A refund, dispute or refund failure never settles a faktura (they carry `origin_txn_id`, never `order_id`, `attempt_id` or `invoice_id`), and a charge refunded in full with the choice to collect again (`recollected_at` set) has given its fakturas back, so a bank KID payment or a new card payment may settle them.

**Failure mode:** a clause that only checked "booked" would keep a recollected faktura reading as settled, so the treasurer's "collect again" would leave a faktura nobody can pay (every assign refused with "already booked") while reminders chase the member.

### A card refund is booked only by the booking pass, against its charge, with documents

**Rule (BRY-446, ACC-2, ACC-5, ACC-8, ACC-9):** a Stripe refund or refund failure is booked only by `BookStripeBalance`, once Stripe's balance shows it; the refund button and the webhook write only `payment_refunds` (next rule). In the pass's row transaction it locks the refund (or failure) row, then the row it books against (`origin_txn_id`: a refund's charge by `charge_id`, a failure's refund by the refund id), then the charge, then the fakturas in id order (`lockInvoicesTx`); every statement runs on that transaction, including the credit notes (`CreateInvoiceTx`, `bookInvoiceEntryTx`, `invoiceRevenueCreditsIn`) and any payment link (`linkInvoicePaymentIn`). A case that turns out not to divide exactly rolls back to a savepoint and holds the row (`refund_split`).
- A refund of a charge that settled an order or a faktura (pass-booked, or assigned to a faktura by hand) issues a credit note per faktura (one per order with no faktura) for its share, dated the refund's booking date, booked at once (DR revenue / CR 1500) and marked sent, and books DR 1500 / CR clearing. Shares are proportional for a partial refund and "what is left" for the refund that completes the charge, so partials add up to each faktura's total to the øre. The faktura keeps its payment; it reads as credited (`finance.CreditedSQL`) only once its refund credit notes add up to its total. A full refund turns the order `refunded`.
- A full refund the treasurer asked to collect again (`payment_refunds.outcome = 'recollect'`, only before any partial was credited) issues no credit note: the faktura's payment and online marker are cleared, its `order_sources` row is deleted (`detached_order_id`), and the charge gets `recollected_at`.
- A refund of a charge booked to an account by hand books against that account; a duplicate capture (a charge held as `receivable_not_open`, `amount_mismatch` or `no_attempt`) refunded in full is booked with its refund as a pair through `clubs.stripe_suspense_account` (default 2900), the charge keeping its review reason so nothing reads it as settling its order.
- What a refund did is `refund_documents`; refund failures and unassigns read it, never re-derive it. A refund credit note is linked to its faktura there, never through `credits_invoice_id` (that link and `idx_invoices_credits_once` keep meaning a manual credit of the whole faktura). It is never voided (409 `refund_document`), linked, unlinked or deleted by hand, and never offered as a credit candidate; a faktura card refunds issued credit notes for takes no manual credit note either (409 `refund_credited`), and a faktura with a `refund_documents` row cannot be deleted (409 `refund_document`). A refund failure never voids it either: it issues a new debit faktura for the returned money, settled by it in the same transaction.
- A refund that issued credit notes is never unassigned (409 `credit_note_issued`), nor is a charge with a booked refund (`refunded_ore` > 0, 409 `refund_booked`); a recollect refund is unassigned only while its faktura is still open (409 `faktura_settled_since`).
- The document's PDF and email are produced after the commit, by the delivery worker (`deliveries`, kind `invoice_refund_document`, queued in the booking transaction), never while the pass holds its locks or the club's Stripe slot.
- A replayed capture never marks a faktura again: `markInvoicesPaidOnline` skips an order that is `refunded` and a faktura with a `refund_documents` row from that order.

**Failure mode:** a bare ledger entry for a refund leaves revenue overstated with no document (ACC-1); voiding the credit note on a failed refund withdraws an issued sales document; linking a partial refund's credit note through `credits_invoice_id` would read as a full credit; and a credit note issued with a pool connection while the refund and its fakturas are locked deadlocks once the pool is full of bookings waiting on them.

### A card refund is stored before Stripe is called, sent once, and never re-sent under another key

**Rule (BRY-497, PAY-6):** `POST /admin/orders/{orderID}/refund` is treasurer/admin with a fresh TOTP (`RequireFreshTOTPDefault`), and `RefundService.Request` runs in two steps. First one transaction locks the order, then the attempt (`FOR UPDATE`, in that order), applies every refusal (`not_captured`, `not_supported`, `disputed`, `amount_exceeds_refundable`, `recollect_after_partial`, `request_key_reused`) and stores the refund as `requested` with the person, reason, `request_key` and outcome; the refundable amount is the attempt's amount less its `requested` and `succeeded` refunds, so two requests over the same money cannot both pass. Only after the commit is the provider called, with an `Idempotency-Key` derived from the request key (`refund-<key>`), on a context that outlives the client. A request key that is already stored returns its row (only when the attempt, amount, outcome and reason all match, else 409 `request_key_reused`) and a row the provider already has is never sent again; a row still `requested` is looked up first (`Refunder.FindRefund`, which matches `metadata.refund_request_key` and reads the whole refund list or fails), and only when the provider has nothing and the row is under 23 hours old is it sent again, under the same key (PAY-12). A definite refusal (`payments.RefundRejectedError`: a parseable Stripe error object answered with a 4xx other than 408, 409, 429, an idempotency error or a key in use, or a request that never left) marks the row `failed`; anything else, including an unparseable 4xx body, leaves it `requested`. The sweep (`SweepRequested`, on each `GET …/refunds` and in the nightly Stripe job) asks the provider after ten minutes, sends a request it has nothing for under its own key while the key is young, and marks the row `failed` after 24 hours with nothing found (Stripe forgets the key by then). A refund is never sent under a new key. The status of a stored row only moves forward: an answer or an update never puts a `succeeded` or `failed` row back to `requested`. Neither the endpoint nor the webhook books anything: the booking pass books the refund from the balance and reads the row's `outcome` (matched by Stripe's refund id, else by the request key).

**Failure mode:** calling Stripe before the request is stored, or from inside the transaction that holds the order lock, leaves a refund with no record after a crash, or a lock held across a network call; sending a timed-out refund under a new key refunds the payer twice, and reading a proxy's 4xx as Stripe's refusal fails the row so the person tries again under a new key; and a status written without the guard lets a delayed `pending` update undo a finished refund.

### The refund webhook records state for every refund of the charge, whoever made it

**Rule (BRY-497):** `charge.refunded` and `charge.refund.updated` are handled by listing the charge's refunds from Stripe (`GET /v1/refunds?charge=`), not by trusting the payload, and upserting `payment_refunds` through `payments.UpsertProviderRefund`: by Stripe's refund id, else by the request key in the refund's metadata (the button's row learns its refund id), else a new row for a Dashboard refund (no person, reason "Stripe Dashboard", no outcome). It keeps what a person entered (reason, outcome, who) and writes no other table. The payment is placed like a dispute's (PaymentIntent metadata, then the stored charge); a payment that cannot be placed because Stripe cannot be asked, or a refund list that cannot be read, answers 5xx so the event is delivered again.

**Failure mode:** acting on the event's own payload applies a late `pending` over a finished refund; a webhook that also touched the order or ledger would double-book what the balance pass books.

### A card dispute is booked only by the booking pass, as a loss; the webhook only records it

**Rule (BRY-446, ACC-4, ACC-5):** a Stripe `dispute` or `dispute_reversal` is booked only by `BookStripeBalance`, once Stripe's balance shows it, in its own row transaction: DR the club's dispute account (`clubs.stripe_dispute_account`, default 7830) / CR the Stripe clearing account for the amount, plus the dispute fee DR payment fee / CR clearing; a reversal books the mirror, the fee only when Stripe returned one. The faktura, its order, `refunded_ore` and the charge row are never changed, and booking needs no booked charge (`origin_txn_id` is informational, set without locking the charge). An account that is not an active account in the club's chart holds the row as `dispute_account_missing` instead of failing (retried by every pass). The entry's side follows the sign of the amount (negative: money out); a row whose sign disagrees with its category is held as `dispute_direction`, and a row that moved no money is marked booked without an entry. The `charge.dispute.*` webhook writes only `payment_disputes` (`payments.UpsertDispute`): forward-only in status (an inquiry may escalate to a chargeback; a finished dispute is final), idempotent under redelivery, tolerant of any payload shape, and the treasurer email is claimed with a guarded update on `notified_phase`, once per open phase. A dispute event for a payment of another deployment (`club_slug` in the PaymentIntent's metadata, and no attempt of ours) is ignored, so its dispute is neither stored nor mailed here; when Stripe cannot be asked and nothing else places the dispute, the event is answered 5xx instead. Whether a refund may be made reads `payments.OpenDisputeForAttempt` (Stripe's `is_charge_refundable` when known), never the booking; the refund endpoint answers 409 `disputed` and still handles Stripe's `charge_disputed` refusal as a failed refund.

**Failure mode:** booking a dispute from the webhook, or holding it until its charge is booked, loses the loss from the books whenever the event or the charge arrives in the wrong order; booking it against 1500 or reopening the faktura chases a member who paid; an upsert that took the last event's status let a late `needs_response` reopen a lost dispute and a retry resend the treasurer's email.

### Refunds and disputes show in the lists from the provider's state or the booked documents, and "Ny faktura" is once-only

**Rule (BRY-498, ACC-8):** the lists read two sources and say which, so the treasurer is never told the books are ahead of Stripe.
- **The payment overview** (`GET /harbor/recent-payments`) takes `refund_state` and `refunded_amount` from `payment_refunds` rows the provider confirmed (`status = 'succeeded'`) on the attempt that paid the order (the earliest captured one), so it does not wait for the booking pass; an order already `refunded` counts as fully refunded even without a refund row. A refund of a duplicate capture says nothing about the order and does not mark it. Orders with status `paid` or `refunded` are listed (a refunded order keeps its capture `paid_at`), so a refund never removes the payment from the view or from the "Alle" filter. `since` and `until` are dates (`YYYY-MM-DD`) and both include their whole day: `until` is bound as the day after, so `since` = `until` is one day. `limit` defaults to 50 and is capped at 200; the query fetches one row more and answers `has_more` when it was cut, so a truncated list is never silent. `dispute_status` is the latest `payment_disputes` row of the order's attempts, in Stripe's words.
- **The faktura list and the member list** take them from `refund_documents` (kind `credit`, live credit notes), so a faktura reads refunded only once the booking pass has issued the credit notes: net of the debit fakturas failed refunds issued in their place (`refail_invoice`), `none` when nothing is left, `partial` below the total, `full` at it. A full refund gives the faktura `credit_state = 'refunded'`; a refund's credit note keeps `credit_state = 'refund'` and is never `credit_owed`. The member list sends the refund state and the credit notes (number, amount, whether a PDF exists), a flag marking a refund's credit note, and nothing of the reason, the actor, the dispute or Stripe.
- **Who sees what.** The refund states (`refund_state`, `refunded_amount`, the credit notes) go to every role that can read the list. Everything about a dispute (`dispute_status`, `dispute_due_by`, `dispute_url`, and the count `open_disputes` / `open_disputes_url`) and every Stripe Dashboard link (`payment_url`) is for a treasurer or admin only, because a dispute names a member who charged back and the harbor master and board read these lists too; for any other role the fields are null or absent, and the faktura list does not even query disputes. The links are built on the server with `stripeDashboardURL`. The faktura list reads only the page's fakturas (their ids), never the whole club's refund documents or disputes. A dispute belongs to a faktura through its order id or, when that is empty, through its attempt's order (the overview places it the same way).
- **"Ny faktura" (`POST /admin/financials/invoices/{invoiceID}/reissue-after-refund`)** is `moneyGate` (treasurer/admin plus `RequireFreshTOTPDefault`) and audited `invoice.reissued_after_refund`. One rule, `accounting.ReissueEligible(total, credited, replaced)`, decides it for the endpoint and for the list's `can_reissue`: the faktura's live `credit` documents equal its total and no `refail_invoice` document exists. A faktura whose failed refund was billed again is never offered, even when a later refund credited it once more and the net equals the total (the safer reading: the payer already paid the debit faktura). `accounting.ReissueAfterRefund` locks the credited faktura (`FOR NO KEY UPDATE`, then reads its state in a second statement so a request that waited sees the link the one before wrote) and refuses when the rule fails or the faktura is voided (409 `not_refunded`; a recollect faktura, a partially refunded one, and a credit note all fail it) or when `invoices.reissued_as_invoice_id` names a faktura that is not voided (409 `already_reissued`). A voided new faktura no longer blocks: the link is overwritten by the next one, and deleting the new draft clears it (`ON DELETE SET NULL`), so the list stops naming either. It copies the lines as they were issued (quantity and unit price kept) except that an exemption is folded into the item it reduced, which then becomes one unit of the net amount; a fully exempt pair is dropped; an exemption with no item to fold into is **not copied** (nothing says what it reduces), so the new faktura is the items at what they cost the member, which can exceed the credited total. The payer is the member as they are now: their current name and email (the credit note, by contrast, mirrors the original document), except that an organisation's own recipient address is kept. It goes through `CreateInvoiceTx` (numbered under the per-club lock), is stored as a draft and recorded in `reissued_as_invoice_id` in the same transaction. The PDF, email, `sent_at` and booking then follow the single create form's path (`ensureInvoicePDF`, `emailNewInvoice`), after the commit; a payer with no address, no mail service or a PDF that failed leaves the faktura a draft and says so in the response. The credit notes are never touched (ACC-9).

- **A refund that credited a faktura fails after "Ny faktura"** (BRY-498): the booking pass holds the `refund_failure` as `refund_failure_reissued` (not retried; `assign_account` or `dismiss`) and writes nothing, because a debit faktura for the returned money would bill the payer twice (the new faktura already collects it). It reads `invoices.reissued_as_invoice_id` under the faktura's lock, which "Ny faktura" also takes. A voided new faktura does not hold it: the failure books as usual.

**Failure mode:** counting a refund of a duplicate capture against the order, or listing only `paid` orders, hides the refunded payment the treasurer is looking for; reading the faktura's refund state from `payment_refunds` shows a faktura as refunded before its credit note exists; a double click or two treasurers issuing a second faktura bills the member twice; copying a faktura's exemption lines as they are bills the member more than they paid; and sending a refund's reason or Stripe link to a member leaks staff-only information.

### Faktura numbers come from one path, under a per-club lock

**Rule (BRY-446):** every path that creates an invoice (the single faktura form through `CreateInvoiceTx`, bulk issuing, the previous-system import, "Ny faktura" after a refund, and the booking pass issuing credit notes and debit fakturas) takes its number from `accounting.NextInvoiceNumberTx`, which holds `pg_advisory_xact_lock(hashtext('invoice_number:' || club_id))` until the faktura is committed and reads `MAX + 1` in a statement after the lock. `(club_id, invoice_number)` is unique (`idx_invoices_club_number`), the last line of defence. The KID and the PDF print the number, so both are made inside that transaction.

**Failure mode:** `MAX + 1` read outside a lock gave a treasurer's faktura and a refund's credit note, created at the same moment, the same number and the same KID.

### A Stripe payout clears once every balance transaction in it is booked

**Rule (BRY-457):** `ClearStripePayouts` books a Stripe payout's bank deposit, DR the import's bank account / CR `stripe_clearing_account` for the payout amount on the bank date (`source = 'stripe'`, sourced to the bank row, posted on creation), only when all of this holds:
- The payout is `paid`, automatic, in NOK, not yet cleared (`journal_entry_id` and `bank_row_id` NULL) and its members are listed (`members_listed_at`). A manual payout is never cleared by the sweep (Stripe cannot list what it paid out): it is reported `skipped`, "avstem manuelt", and a person clears it (below). `failed` and `canceled` payouts are ignored; `pending` and `in_transit` ones have not arrived.
- Exactly one bank row matches it, and that row matches no other payout (manual payouts included). A row matches when it is incoming, unbooked, undismissed, not refund-paired, not provisional, carries the club's `stripe_payout_descriptor` in its description or counterpart, equals the payout to the øre and is dated from one day before Stripe's arrival date to three days after it. Anything else is `skipped` ("flere Stripe-utbetalinger passer", "flere bankrader passer").
- Its members (every balance transaction with its `payout_id` other than `payout` and `payout_reversal` rows, which are Stripe moving the payout itself) add up, by `net_ore`, to the payout amount. Otherwise the stored membership is not the payout's (a member kept on an earlier cleared payout, a failed payout's funds carried in) and the payout is `skipped`.
- Every member is `booked` or `dismissed`. Otherwise it is `waiting`, with what blocks it ("2 kortbetalinger venter på bokføring", "1 tvist til gjennomgang").
- The bank date's fiscal period exists and is open (`existingPeriodIn`; the sweep never creates one). Otherwise `waiting`.

The clearing runs in one transaction: lock the bank row, then the payout, then the members `FOR SHARE`, re-check all of the above, create the entry, link the bank row (`journal_entry_id IS NULL`, `auto_matched = true`) and the payout (`journal_entry_id IS NULL AND bank_row_id IS NULL`) with guarded updates, mark the payout's own `payout` balance row `booked` with the entry, post, commit. A lost guard or a failed post rolls everything back; there is never a draft. `UnassignBankRow` on a cleared deposit releases the payout (its `bank_row_id`, `journal_entry_id`, and its `payout` row back to `unbooked`) in the transaction that voids the entry, so the payout is cleared afresh, never left pointing at a voided entry. Tildel offers no faktura or account booking for an undismissed Stripe deposit (and the server refuses one, see the next section). Afterwards the clearing account movements of the members' entries and the clearing entry are summed and a non-zero remainder is logged (a dismissed member). The sweep runs after the Stripe booking pass in every path with an acting user (the Stripe sync endpoint, bank sync, bank import) in the same hold of the club's Stripe slot, and never fails that work.

**Manual clearing (BRY-465).** A deposit no sweep will clear (a manual payout, an ambiguous match, members that do not add up, a date outside the window) is cleared by a person with `ClearStripePayoutManually`: the same transaction, locks, entry, guarded links and payout-row booking, through `clearStripePayout` with `manualStripeClear` instead of `automaticStripeClear`. The person has chosen the pair, so three checks are dropped: the payout need not be automatic, the bank date need not be in the arrival window, and the members need not add up to the payout (the funds of a failed payout carried into a later one, BRY-460, are the case that needs it). Everything that keeps the books right stays: the deposit is incoming, unbooked, undismissed, not refund-paired, not provisional and carries the club's descriptor (re-checked under the lock, since a person can name any row); it equals the payout to the øre; the payout is `paid`, NOK and uncleared; every member is `booked` or `dismissed`; the bank date's period exists and is open, and is never created. "Every member booked" must not hold vacuously: an automatic payout must have its members listed (`members_not_listed`), and a manual payout, which Stripe never lists, needs every balance row that could have funded it booked or dismissed, i.e. every row linked to no payout, other than `payout` / `payout_reversal`, with `COALESCE(available_on, created_at::date)` on or before its arrival date (`balance_open`, those rows taken `FOR SHARE` after the members). The deposit's `auto_matched` stays false. The clearing account remainder is returned (`clearing_balance_ore`, also audited) rather than only logged, because it is expected to be non-zero when the members do not net to the payout; a payout without members omits it, since it would only be the payout itself. It waits up to 5 s for the club's Stripe slot, then answers 409 `busy`. `UnassignBankRow` releases it like an automatic clearing, and it can be cleared again.

**Failure mode:** clearing on amount alone would book a deposit against the wrong payout when two payouts are equal, or against a payout whose charges were never booked, leaving the clearing account wrong in both directions. Without a manual path, a deposit the sweep could not clear was booked by hand in the ledger and then dismissed, which left the payout uncleared for ever and the deposit with no link to its entry.

### A provider payout deposit is booked only by its clearing

**Rule (BRY-457):** a bank row carrying a provider's payout, a Vipps settlement (`Utb. <n> Vippsnr <msn>`) or a Stripe payout (an incoming row whose description or counterpart matches `clubs.stripe_payout_descriptor`, once the club uses Stripe), is booked only by that provider's clearing. `providerPayouts` is the one predicate, and partner hints, mapping rules (`AutoMatchImport`), bank auto-assign candidates and price-item account suggestions all ask it. The descriptor alone decides, not an open payout of the same amount, so a deposit that arrives before its payout is synced is still kept out. The Vipps half also exists as SQL (`vippsPayoutRowSQL`); the Stripe half is a per-club Go (RE2) regular expression and is never evaluated in Postgres, whose ARE dialect is not RE2 (embedded flags such as `(?i)` only at the very start, locale-dependent classes like `\d`, back-references RE2 rejects): SQL sites select with the Vipps fragment and filter the loaded rows in Go. A club with no Stripe payment attempt, payout or balance row has no Stripe half, so a deposit that merely mentions Stripe stays bookable there. An outgoing row is never a Stripe payout.

The manual assigns refuse such a row on the server too, with no override: `AssignBankRowToInvoice` (and the bank auto-assign, which shares `assignBankRowToInvoice`), `AssignMultipleBankRowsToInvoice` (`loadMultiAssignRows`), `AssignBankRowToAccount` and `AssignBankRowsToAccountGroup` (`loadGroupRows`) call `refuseProviderPayouts` once the rows are loaded, before any lock or entry, reading the descriptor on the assign's connection (its transaction where it has one; the group assign holds no lock and uses the pool), so a holder never waits for a second connection. The refusal is `*ProviderPayoutDepositError` (`errors.Is(err, ErrProviderPayoutDeposit)`, with the row and the provider); the handlers answer 409 `{code: "provider_payout", provider, bank_row_id}`. The clearings (`ClearVippsPayout`, the Vipps sweep, `clearStripePayout`) and the KID cascade never pass through those functions. A deposit that is genuinely not a payout is dismissed, or the club's descriptor corrected.

**Failure mode:** a mapping rule on "STRIPE", a price item of the same amount or a name match would book the payout's money to revenue a second time, after the charges already credited it. The same through a stale Tildel page or a direct API call to an assign endpoint.

### A provisional bank row gives way to its settled row

**Rule (BRY-378):** a statement exported while a transfer is in flight carries it as a provisional row (`provisionalRowSQL`). That means description exactly `Overførsel` or `Bokført på vei`, no counterpart, no KID, dated on its statement's last day (`bank_imports.period_to`, recorded at import and widened by the reimport paths; the latest surviving row only for an import older than that column), and `reseen_at` unset. A later export carries the settled row (for a Vipps payout, `Utb. <settlement> Vippsnr <msn>`).
- **Same bank reference (the usual case):** the arkivref dedup in `ImportBankRows` would skip the settled row. Instead `refreshProvisionalByReference` updates the existing row in place: date, description, counterpart, KID, `from_account`/`to_account` and `row_hash`. It does so only when exactly one row carries the reference, that row is provisional, unbooked, undismissed, not refund-paired and on the importing bank account, the incoming row is not bare, the amounts agree to the øre, the settled date is the same day or up to two days later, no other row already holds the new hash, and there is an actor to audit it. A refresh is audited as `bank_row.refreshed` (with the old and new date when it moved) and counted as `refreshed`. The same pair with another amount or a bigger gap is reported as a `reference_mismatches` entry and left alone. Everything else with a known reference is skipped as before.
- **A bare row seen again:** when a later statement that runs past the row's date carries the same bare row again, still bare (same reference, or the same hash without one), the row is a settled transfer with a terse text. It gets `reseen_at` and is never provisional again, so it is never superseded or refreshed.
- **Different reference:** both rows exist. `SupersedeProvisionalBankRows` (each import, and pass 0b of `BankSync`) dismisses the provisional row as `superseded` when it pairs one to one with a non-bare, undismissed row of another import on the same bank account, date and amount. Any other shape is reported as ambiguous and left alone. Booked rows are never touched.
- A refreshed row is not KID-matched at import; the next bank sync (KID pass, payout sweep) picks it up.

**Failure mode:** the settled row was skipped as already imported, so the deposit stayed a bare `Overførsel` in Tildel and its Vipps payout could never clear. Matching such a row to a payout by hand would have booked the provisional row, and the settled row would then arrive later as an unbooked duplicate.

### Provider postings are posted on creation; no period closes with drafts

**Rule (BRY-339, BRY-454):** every payment-provider posting path posts its entry right away. For Vipps: per-charge charge→faktura and charge→account, the order-linked split, auto-assign, the payout's fee and bank entries, and the legacy `ReconcileVippsConfirm`. For Stripe: the charge and fee entries of `BookStripeBalance` and the payout clearing entry of `ClearStripePayouts`.
- Each path marks its source row with a guarded update first, then posts. If the post fails, it unlinks the row and deletes the draft (`unwindVippsPosting`), so the charge returns to Tildel. A path that books inside a transaction holding a lock (the Vipps faktura assign, the legacy settlement confirm, the order-linked Vipps charge, the Vipps payout clearing, every Stripe row) has nothing to unwind: the rollback is the cleanup. The confirm's guarded link of each Vipps row (`journal_entry_id IS NULL`) refuses a row booked meanwhile (`ErrVippsRowAlreadyBooked`) and rolls the whole settlement back.
- A Stripe row whose booking date falls in a `closed` or `locked` period, or in no period, is left `unbooked` and reported as deferred (`period_closed`, `no_period`); the next pass retries it. It never becomes a draft. The automatic Stripe booking pass and the payout clearing (sweep and the BRY-465 manual clearing alike, through `existingPeriodIn`) never create a fiscal period, since no person decided to open the year. A manual Stripe row assign (BRY-466) may, through `resolvePeriodIn`, like a manual bank assign: a person chose to book on the card payment's date. So do the legacy Vipps settlement confirm and the order-linked Vipps charge, which resolve the period on their lock transaction. The other Vipps per-charge paths still auto-create one through `resolvePeriod`.
- The legacy `ResyncVippsBilags` re-creates existing drafts and keeps them as drafts. Posting a pre-existing backlog is a separate, supervised step: `PostVippsDraftBacklog` (BRY-341), per fiscal period, preview then fresh-TOTP apply. It refuses unbalanced or orphan drafts, drafts whose source row another posted entry already booked, and drafts whose faktura another posted entry already settled. A settlement's fee and payout drafts post only when every charge of the settlement is posted (see "A charge in a cleared Vipps settlement is not unbooked on its own"). It never posts a 1500 credit that isn't tied to a faktura (BRY-370), because it may be the only record that a faktura was paid. An apply that names the ticked reclassifications (`reclassify_entry_ids` with their previewed `reclassify_targets`, BRY-398) skips every other reclassification entirely: an unticked draft is never posted on the account it is parked on, since that is the booking the treasurer did not accept. A ticked draft whose target changed since the preview (a faktura issued meanwhile) is skipped as stale, so the apply books only what the treasurer saw. Migration 000106 fills `vipps_import_rows.invoice_id` for legacy bookings where the `vipps_charge.assigned_invoice` audit row names the charge, its current entry and a still-paid faktura.
- **A charge's `invoice_id` lives and dies with its `journal_entry_id` (BRY-523).** `invoiceBookedRowSQL` reads a Vipps charge as settling a faktura while it has both. Anything that unlinks a charge from its entry therefore clears `invoice_id` in the same statement. An undo also reopens every faktura the charge recorded: `UnassignVippsCharge` for its own charge, `unassignBankRow` for the Vipps rows (charges, payouts, fees) of a legacy settlement entry (`releaseVippsRowsTx`, then `reopenInvoicePaymentTx` for each faktura), and it runs before the draft entry is deleted, because `vipps_import_rows.journal_entry_id` is ON DELETE SET NULL and the rows could no longer be found by their entry. The regenerate and resync detaches (`regenerateOneSettlement`, `ResyncVippsBilags`) clear `invoice_id` but keep `invoices.payment_id`: they re-book the same money, so the fakturas stay paid. The pre-000057 fallback of an unassign (a faktura found through its payment) is limited to a faktura this entry credited 1500 for and no other booked row records, and is skipped for an entry that has Vipps rows. The legacy confirm writes `invoice_id` outright (a charge it does not link gets NULL), so a re-run never keeps a stale one. A charge left on a voided entry with its `invoice_id` would block its faktura for every later confirm and assign. `UnassignVippsCharge` refuses a charge whose entry a bank row shares: that settlement is undone from the bank row.
- **When a 1500-parked charge may be rebooked (BRY-392).** A charge draft crediting 1500 with no `invoice_id` and no checkout order may be rebooked, released or unassigned only when `receivableChargeSettledFaktura` finds no faktura it may have paid. `payments` has no column naming a Vipps charge, so the test is a heuristic. The charge fails on a faktura marked paid for its amount (±1 kr) that no non-voided entry (draft or posted) linked through `bank_import_rows.invoice_id` or `vipps_import_rows.invoice_id` explains, where marked paid means either:
  - `payment_id` points at a `KID-avstemming` payment of that amount, and the faktura belongs to the member the payer resolves to (any pass) or carries the KID in the message — at any date — or the payment's `paid_at` is within 7 days of the charge date, for any faktura (a payer may pay a household member's faktura, and name resolution can be wrong; legacy payments carry the payout date, a few days after the charge);
  - `online_paid_at` is within 7 days of the charge date with `online_paid_provider = 'vipps'`, and the faktura total is that amount, unless a booked charge of a checkout order paying the faktura (`order_sources`) explains it. Only Vipps markers count, because only a booked Vipps charge can explain one.

  A charge that fails is refused with the faktura number and cannot be released or unassigned: `UnassignVippsCharge` runs the test on every draft with no `invoice_id` that credits 1500, whoever calls it. There is no in-app way yet to fix the faktura side (BRY-397). One that passes goes through `decideVippsCharge` like a new charge (`member_invoice` → `AssignVippsChargeToInvoice`, `price_item` → the category's account), rebooked via `applyBacklogReclass` (one transaction: `rebookVippsChargeTx` deletes the draft and posts the replacement, so a failed rebooking leaves the charge on its draft). With auto-assign off, or no rule, it is refused and listed in `releasable`. Release is the Vipps unassign with `released_from_backlog: true` (`ReleaseVippsBacklogCharge`): it also requires exactly such a draft in an open period, and is audited as `vipps_charge.unassigned` with that detail. The test does not see a faktura marked paid by a payment with another description.
- `ClosePeriod` refuses (409 `period_has_drafts`) while the period holds any draft, and lists them per source with count and total. A reference period is the exception: its drafts can never be posted, so it closes with them. `DeleteDraftJournalEntry` removes a draft that no bank or Vipps row references. Linked drafts are undone through Tildel unassign.
- Posted entries are never hard-deleted. Undoing a posted charge voids it with a reversal (`UnassignVippsCharge`, `VoidJournalEntry`). `UnassignVippsCharge` voids the entry, clears the row links, reopens the faktura and deletes a draft in one transaction (BRY-370, BRY-555): a charge booked in a closed period, or in a cleared settlement, is refused with nothing changed, and a failure anywhere rolls the whole undo back.

**Failure mode:**
- Reports and momskomp count only booked entries, so draft Vipps postings left all Vipps income and fees out of the accounts. In prod that was 869 drafts.
- Closing a period with drafts strands them, because posting into a closed period is refused.

### Booked faktura bilags are corrected, never rebuilt

**Rule (BRY-364):** a posted `invoice_sync` entry is never deleted or edited. When its revenue split is wrong, `ResplitInvoiceBilags` posts an `invoice_resplit` entry for the invoice that moves the difference between revenue accounts. The difference is the lines' expected per-account split minus what the sync entry and earlier resplits booked. The run is idempotent, a preview posts nothing, and apply is behind fresh TOTP. An invoice whose booked revenue differs from its total is skipped with a reason for manual correction. The old `RebuildInvoiceBilags` (delete and re-sync) was removed.

**Failure mode:** deleting `invoice_sync` entries also deletes voided originals whose `manual` reversals survive, so reports go negative. It also erases the audit trail that bokføringsloven expects corrections to leave.

### An auto-match posts or leaves nothing

**Rule (BRY-324):** the KID auto-match in `ImportBankRows` and in the bank sync either creates **and posts** the journal entry and links the row, or it leaves no entry at all. Posting uses the importing user (`bank_imports.imported_by`) as `posted_by`. The entry is created, the row linked with a guarded update (`kidCascadeEligibleSQL`: unbooked, undismissed, not refund-paired) and the entry posted, all in the faktura-lock transaction (BRY-370, BRY-433). A lost race or a failed post rolls all three back, so no draft or link is left to clean up. Either failure is returned in the import result's `row_errors`, never swallowed. The row stays unmatched for manual Tildel. Concurrent syncs therefore book a row once.

- **Which rows the cascade may book (BRY-382).** Only rows passing `kidCascadeEligibleSQL`: bank sync lists its candidates with it and both cascades guard the link with it, so a row the treasurer dismissed, even while a sync was waiting on the faktura lock, is never booked. Rejected-KID notices (`IsRejectedKIDDescription`) are skipped at import and sync alike.
- **The cascade locks the faktura (BRY-388).** `bookKIDCascadeMatch` takes `lockInvoiceForAssign` (cascade mode: still owed, nothing booked against it by `invoice_id`, KID or a Vipps charge) per row, in its own transaction, and holds it until the row is linked (recording `invoice_id`) and the entry posted. A faktura found settled is skipped and counted (`kid_skipped_settled`), not failed, unless the booking the cascade waited for was its own row's (then nothing is counted); a faktura voided or credited meanwhile is "no longer open", not settled. The lock is never held across a whole import. Period resolution, the entry, the link and the post all run in that transaction, which holds the period share-locked from the entry's creation to the commit, as on the manual faktura assigns.

- Every payment-match entry (KID, invoice number or counterpart, from import or sync) is sourced to its row (`source_table = 'bank_import_rows'`, `source_id` = the row) and described exactly `kidMatchDescription` (`Innbetaling KID <kid>: <row description>`, or `Innbetaling: <row description>` without a KID).
- A row linked to an unposted KID draft can only come from builds that linked and posted in separate transactions. Bank sync releases such rows (`healStrandedKIDDrafts`) once the draft is older than 15 minutes and matches them again. It recognises them only by that source and exact description, so mapping-rule drafts from `AutoMatchImport`, which may also credit 1500 but carry the row's own description and wait for a gated post, are never touched.
- Manual assignments (`AssignBankRowToInvoice`, `AssignBankRowToAccount`, `AssignBankRowsToAccountGroup`) follow the same order: guarded link (`journal_entry_id IS NULL`, not dismissed, club-scoped), then post. The faktura assigns (`AssignBankRowToInvoice`, `AssignMultipleBankRowsToInvoice`) do it all in the faktura-lock transaction, so a failed post rolls back the link and the entry. The account assigns hold no faktura lock and use separate transactions, so a failed post unlinks the row and discards the draft. Of two concurrent assigns of one row, exactly one books. A group links all its rows in one transaction or none.
- Rows that share a `journal_entry_id` were booked together (a group booking or an intra-bank transfer). Unassigning any of them releases them all and reverses the entry once.

### A transaction holding a row lock never acquires another pool connection

**Rule (BRY-433):** while a transaction holds a row lock other bookings queue on (`lockInvoiceForAssign` on a faktura), every statement of that booking runs on the lock transaction: period resolution (`resolvePeriodIn`, `existingPeriodIn`), the entry (`createJournalEntryTx`), the row link (`linkBankRowsTx`, the guarded Vipps mark), the post (`postJournalEntryTx`), the Vipps accounts lookup and `invoice_id` writes. It commits once. Nothing in that window calls a `Service` method that uses `s.db`. Work that has to update the locked row itself on the pool (`linkInvoicePayment`) runs after the commit. A charge assign that loses the guarded mark (`errChargeRaced`, in the shared `postChargeTx`) rolls back to the savepoint taken before its entry (`vipps_charge`, `stripe_charge`), so the losing draft is never committed with the transaction. The legacy Vipps confirm (`reconcileVippsConfirm`) and the order-linked Vipps charge (`AssignVippsChargeToOrder`) lock every faktura they settle first (`lockInvoicesForManualAssign`, id order), resolve the period, and book, link and post on that transaction; the confirm writes `invoice_id` on each charge it books (NULL for a charge it does not link). A Stripe booking holds its row (`FOR UPDATE`) and its order's fakturas (`FOR NO KEY UPDATE`) and runs the same way: split, guard, period, entry, mark and post all on the row's transaction. A Stripe payout clearing locks the bank row, then the payout (`FOR UPDATE`), then the payout's members (`FOR SHARE`, id order) and does its re-checks, entry, guarded links and post on that one transaction.

**Failure mode:** with N bookings queued on one faktura and a pool of N connections, the holder waits for a free connection that only the queued bookings can release, and they wait for the holder's lock. Postgres sees no cycle (the pool wait is client-side), so nothing breaks it: bank syncs and Tildel hang until their context expires. `TestConcurrentBankSyncsBookARowOnce` and the `*OnSmallPool` tests reproduce it on a two-connection pool (`testutil.WithMaxConns`).

### Rows that belong together are booked together

**Rule (BRY-380):** an unbooked bank row with a **strong** partner row (opposite sign on the same bank account within 60 days, and the same counterparty account number, the same counterparty name, or an exactly reversing amount within 14 days) cannot be booked to an account on its own unless the request says `confirm_alone: true`; assign-account answers 409 `has_partner` with the partners. Booking the pair goes through `AssignBankRowsToAccountGroup`: one entry, one bank line for the net, the net on the chosen account. A group must be on one bank account and in one open fiscal period, must not net to zero (that is a transfer), and never books to a bank account or receivables (1500). Group links lock the rows in id order, so overlapping concurrent groups queue rather than deadlock. Rows that are the club's own transfers, provisional, provider payout deposits (Vipps settlements, Stripe payouts), dismissed or refund-paired never get partners. Amounts are compared in øre. Faktura assignment is not guarded: the faktura match is its own evidence.

**Failure mode:** a buy-back payout and the overpayment the recipient returned were booked one at a time, the return as income, so revenue was overstated and the buy-back account understated by the returned amount.

**Failure mode:** before BRY-324 the importer passed the club id as `posted_by`. The users FK rejected it, and the error was swallowed. Every import-time match left an orphan draft, and the bank sync later booked the same row again, so the draft became a duplicate that would double-book the payment if posted. That left 56 in prod (230,831 kr), removed by migration `000100`.

### Postings find accounts by code; a system account's name is the club's

**Rule (BRY-377):** every posting path, report and the momskomp calculation finds an account by `code`, never by name. A treasurer may therefore rename a system (seeded) account and change its description in Kontoplan; `UpdateAccount` refuses only a change to its MVA eligibility (`ErrSystemAccountMVALocked`, 400) and the code, type, active state and deletion stay locked. An omitted or unchanged `mva_eligible` is not a change. The seed name only applies to new clubs: no migration renames an existing club's accounts.

Price items carry no account. The category map (`revenueAccountMap`, read through `PriceCategoryAccount`) gives a price item's default account, and `invoice_lines.account_id` overrides it per line. The account hints in the accounts list and the `price_item` suggestion pass name that default account, so they never claim a line override. Price items and invoice lines carry no MVA: amounts are gross.

**Failure mode:** treasurers could not recognise 3300 "Salgsinntekter" as the account slipping books to, and could not rename it because every system account was read-only.

### Bilag numbers are allocated with a retry, not a lock

**Rule (BRY-370):** a journal entry's number is `MAX(entry_number) + 1` within its club and period, read while the period is only share-locked. Two writers can read the same MAX, so the insert runs inside a savepoint: the loser hits the `(club_id, fiscal_period_id, entry_number)` unique key, rolls back to the savepoint and re-reads MAX, which by then includes the winner's committed number (`insertWithNextEntryNumber`, up to 25 attempts). Other unique violations are returned as they are.

**Failure mode:** without the retry, a bank sync and a manual void in the same period could collide on a number. The family reversal then rolled back with a 500.

### Reports count posted and voided entries

**Rule (BRY-352):** `VoidJournalEntry` sets the original to `voided` but keeps its lines, and adds a *posted* reversal. Every report and the momskomp calculation therefore select `je.status IN ('posted', 'voided')` (`bookedEntryFilter` in `sync.go`), so the original and its reversal net to zero. Only `VoidJournalEntry` sets `voided`, and only on a posted entry, so the filter means "was ever posted". Drafts are never counted. The period and status filters belong in the `WHERE` of an inner join to `journal_entries`: in the `ON` of a `LEFT JOIN` they only blank the entry columns, and `SUM(jl.*)` still covers every period and every draft on the account (the momskomp query summed lines that way).

**Failure mode:** counting only `posted` drops the original but keeps the reversal, so a voided entry shows as its own **negative**. A voided 2,500 kr faktura would push receivables and revenue down 2,500 kr instead of back to zero.

### A sent faktura has exactly one GL entry, booked at send time

**Rule (BRY-363):** sending a faktura (`HandleSendInvoice`, or `HandleCreateInvoice` with `send_email`) books it through `accounting.BookInvoice` in the same request, and voiding it (`HandleVoidInvoice`) reverses that entry through `ReverseInvoice`. Both use the same per-faktura code path as the repair sync (`bookInvoiceEntry`). A unique index (`idx_journal_entries_invoice_sync_once`, migration 000104) allows one `invoice_sync` entry per faktura; a voided entry keeps the slot, so a voided faktura is never re-booked. The email is the event that matters, so a booking failure never fails the send: it is returned as `gl_booking: {status: "failed", error}`, shown in the faktura list, logged, and picked up by **Avstem periode** (`SyncInvoices`). Voiding reverses the faktura's whole entry family, `invoice_sync` and every `invoice_resplit` correction (BRY-370), and audits `invoice.voided` with the reversal ids. If any entry of the family sits in a non-open period, the void is refused with 409 `period_closed` (credit note instead) and nothing is reversed, because the reversal would land in the closed year.

**Failure mode:** with booking only on a manual button, nothing was booked between 2026-05-14 and 2026-10-16 (13 fakturas, 84,031 kr missing from the reports). Two booking paths without the unique index could double-book a faktura on a race.

### Invoice GL sync books only sent, non-voided fakturas

**Rule (BRY-352):** `SyncInvoices` books a faktura only when `sent_at IS NOT NULL` and `status <> 'voided'`.
- A faktura voided after it was booked has its `invoice_sync` and `invoice_resplit` entries reversed on the next sync (`reverseVoidedInvoiceEntries`, within the open period being synced).
- Each line books to its own `account_id` when set. Otherwise it uses the account of the category stored on the line at issue (`finance.LineCategorySQL`: the line's `category`, then its price item's current category only for a line that never stored one), and failing that 3900 (see *Revenue accounts resolve the same on every payment path* and *Invoice line snapshots are immutable*).
- Signs drive the sides, so a credit note books DR revenue / CR 1500. A faktura that nets to zero books its lines without a 1500 line (a fully exempt faktura: CR revenue / DR the exemption expense account); one with no non-zero line is skipped with a reason.
- `SyncPayments` never books a payment that settles an invoice (`invoices.payment_id`). The bank or Vipps reconciliation that created it already booked DR bank / CR 1500.

**Failure mode:**
- Drafts and voided fakturas inflate receivables and revenue.
- Re-booking invoice-settling payments as DR bank / CR revenue doubles both (all 219 completed prod payments in 2026 were invoice-linked).
- Skipped items with no reason hide missing accounts or bad data.

### Bank rows with booked journals require cascade on reassign

**Rule:** A `bank_import_rows.journal_entry_id` that is not NULL means the row has been booked. Reassigning the parent `bank_imports.bank_account_code` must cascade through `journal_lines` to update the booked account. `HandleReassignBankImport` does this in a single transaction; closed/locked/voided journals refuse the cascade.

**Failure mode:** ledger says money is in account A, bank statement says it's in account B. Reconciliation breaks silently.

### Invoice PDFs are retained for 5 years

**Rule:** Bokføringsloven §13 requires invoice documents to be retained for 5 years in the form the recipient was shown. `regenerateOnePDF` archives `invoices.pdf_data` into `invoice_pdf_archive` *before* overwriting, inside the same transaction. If the archive INSERT fails, the transaction rolls back and the original PDF stays in place.

**Failure mode:** legal exposure on a member dispute. No way to prove what the recipient was actually shown.

### Invoices snapshot the member's identity at issue

**Rule:** Every invoice stores `member_name` / `member_email` captured when it is created (historical rows are backfilled). Display and PDF-regeneration paths read the snapshot first — `COALESCE(NULLIF(recipient_org_name,''), NULLIF(member_name,''), users.full_name, …)` — so anonymizing or deleting the member never rewrites the name/email on their past invoices.

**Failure mode:** a member is anonymized and all their historical invoices suddenly read "Deleted User", breaking the bokføringsloven §13 requirement that the record show who was billed.

### A member with in-window financial records is deactivated, never erased

**Rule:** "Removing" a member sets `users.deactivated_at` (reversible; hides them from active lists and member counts, blocks login, drops sessions) — it does *not* delete the row or scrub PII. Their name/email/address are erased only after their most recent invoice clears the retention window (1 January of the record's year + 6), by the daily sweep `accounting.PurgeExpiredMemberPII` or a manual erase. `HandleDeleteUser` always anonymises in place and never deletes the row (BRD-10): invoices, orders, audit actors, deletion requests and journal authors reference it with no `ON DELETE` cascade, and payments cascade from it, so a delete either fails or takes financial rows with it. Whether an admin erase should wait for the retention window is BRY-538. `accounting.MemberFinancialRetention` is the single source of truth for eligibility — never hand-roll the date math or the `deactivated_at IS NULL` list filter. Processing a GDPR deletion request deactivates the member in both outcomes (identity erased now or deferred) through `revokeMemberAccess`, which also drops sessions, passkeys, TOTP, all magic links for the email, the durable pay link and the member's developer tokens; an immediately erased row keeps `deactivated_at` and its `@deleted.local` email, which the sweep skips. `HandleDeleteUser` calls the same step before it anonymises the row, so an admin delete leaves no live session, passkey or token either. Every erasure writes a per-member `<uuid>` + `accounting.ErasedEmailSuffix` address, never a shared constant: `users` is `UNIQUE (club_id, email)`, and a shared value would make the second erasure in a club fail forever (the sweep skips the legacy `deleted@deleted`).

**Failure mode:** either an erase/GDPR action destroys records the club must keep for 5 years (FK violation or lost history), or a member's PII lingers indefinitely past the point erasure is legally required.

### Sent fakturas keep their issue-time kontonummer

**Rule:** A sent faktura's PDF is whatever bytes are stored in `invoices.pdf_data` at delivery time. Switching the club's `is_default_for_invoices` bank account does NOT retroactively change the kontonummer on already-sent PDFs. To correct a batch, the operator runs `Regenerer PDF` from the Sent tab, which archives the original and rebuilds with the current default.

**Failure mode:** member pays the wrong account. Or worse, an auditor finds two versions of the same invoice with different kontonr and the audit trail can't explain why.

### Revenue accounts resolve the same on every payment path

**Rule (BRY-384):** A category resolves to its revenue account through one map, `revenueAccountMap` (`revenue_accounts.go`), on every path: invoice sync, Vipps per-charge, Vipps auto-assign, order split and the price hints. Revenue nothing names an account for lands on `fallbackRevenueCode` (3900): an unmapped category, an invoice residual (total ≠ line sum), a faktura with no lines and a line with neither an account nor a category. On a faktura line the category is the one stored on the line at issue, not the price item's current one. Paths that book without a human (Vipps auto-assign) or show a default (price hints) use `RevenueAccount`, which reports an unknown category as unknown, so it is never auto-booked or hinted.

**Failure mode:** before BRY-384 invoice sync fell back to 3100 and Vipps to 3900, so the same price item booked to different accounts depending on how it was paid, and unexplained invoice money was mixed into membership dues. Entries booked to 3100 that way were not rebooked.

### Vipps cascade lands on 3900, never 2900

**Rule:** Unmatched Vipps `belastning` lines route to `fallbackRevenueCode = "3900"` (Andre inntekter). The legacy `vippsClearingAccountCode = "2900"` is kept as a Go constant for backwards-compatible reports but no new lines route there.

**Failure mode:** 2900 (Annen kortsiktig gjeld) implies "we owe the payer money," which is wrong for revenue we just haven't classified yet. Treasurer's balance sheet lies.

### A posted charge on 3900 may be reclassified, and only as a reverse-and-repost of its own entry

**Rule (BRY-557):** a posted Vipps charge whose entry is exactly DR clearing / CR 3900 (`fallbackRevenueCode`) may have its revenue moved to a price item's account by `ApplyVippsFallbackReclass`, and only when all of these hold under the charge row's lock, re-read inside the transaction:
- the club has `vipps_auto_assign` on (it is refused otherwise: the club's opt-in and tie category decide which price item a charge belongs to);
- the charge is a `belastning` with no `invoice_id`, no checkout order (`orders.vipps_reference`) and no dismissal, and its entry is posted, in an **open** period, sourced to that row, and shared with no bank row (a legacy settlement entry is undone from its bank row);
- `decideVippsCharge` gives a `price_item` rule whose account is not 3900 itself and is active, and `receivableChargeSettledFaktura` finds no faktura the charge may already have paid (reclassifying it would bury a double count);
- the caller named the entry with the account the preview showed, and the charge is still proposed with that account.

A payer with one matching open faktura (`member_invoice`) is never reclassified here: that move changes a faktura, not just revenue, so it is listed `needs_tildel` and handled by hand (undo the booking, assign in Tildel).

**How:** the entry is voided (`voidJournalEntryTx`, so a closed or locked period refuses it under the period lock) and a new posted entry DR clearing / CR target on the same date and period replaces it, in one transaction per charge. The helper relinks the row with its guarded mark, which must affect one row, and the rule is recorded in the same transaction. The original stays voided with its reversal, and the replacement's description names the voided bilag; the batch audit row lists every pair, with the reversal. Nothing is edited in place (see "Posted journal entries cannot be edited"). The clearing account, the payout's fee entry and bank entry are not touched, so a cleared settlement stays cleared and the trial balance moves only from 3900 to the category. The transaction locks the charge row first (so a charge already moved reads as moved, not as an error), then the helper takes the settlement's payout rows and the entry, in that order, and nothing runs on the pool while they are held (see "A transaction holding a row lock never acquires another pool connection"); the decision, which reads on the pool, runs just before the transaction and is not trusted across it.

**Failure mode:** `UnassignVippsCharge` is refused for a charge in a cleared settlement (see "A charge in a cleared Vipps settlement is not unbooked on its own"), which is why the reclass is a repost; without that refusal it would put the charge back in Tildel and leave the payout cleared against an unbooked charge; editing the credit line in place would break the posted-entry rule; reclassifying a charge that already paid a faktura would hide a double count behind a revenue account; applying a preview the caller never saw would move charges the treasurer did not agree to.

### Vipps row amount signs

**Rule:** `vipps_import_rows.amount` is positive for `belastning` (customer paid us) and negative for `fee` (Vipps took their cut). The fee branch flips the sign for the DR line.

**Failure mode:** bilag doesn't balance, reconciliation 500s.

## Auth

### Recovery codes are bcrypt-hashed and single-use

**Rule:** `totp_recovery_codes.code_hash` is bcrypt; `used_at` is monotonic. Consumption is irreversible — there's no "un-use" path. Re-issuing recovery codes wipes the unused ones.

**Failure mode:** a leaked code that's already been used grants admin access. Or a "convenience" code-reuse feature creates a permanent bypass.

### TOTP enrollment requires QR scan + confirm

**Rule:** The TOTP secret is persisted only after the user confirms a code derived from it. The QR-scan step shows the secret; the confirm step proves the secret was registered with an authenticator. Both steps are required — never persist a secret without confirmation.

**Failure mode:** user thinks they enrolled, can't verify, is locked out. Or worse: secret leaked from logs while the user never actually scanned it.

### Replacing a second factor requires a fresh step-up

**Rule:** a user who already has a second factor (TOTP or passkey) can only add, replace or remove a factor after a fresh step-up. TOTP `setup`/`confirm` sit behind `RequireFreshTOTPIfEnrolled`; passkey register/delete sit behind `RequireFreshTOTPDefault`. Only a user with **no** factor may enroll on a plain session.

**Failure mode:** enrollment stamps the session as stepped-up. If replacing a factor needed only a session cookie, a stolen cookie could enroll the attacker's own secret and then pass every admin and fresh gate (BRY-298).

### Anything that can post a journal entry is treasurer/admin with fresh TOTP

**Rule (BRY-370):** every accounting route that can create or post a journal entry — manual entries, post, void, delete draft, the GL syncs (payments, invoices, resplit, Vipps drafts), bank and Vipps imports, bank sync, Vipps resync and the bank-row Vipps reconcile confirm — goes through `moneyGate` in `cmd/api/main.go`: `RequireRole("treasurer", "admin")` plus `RequireFreshTOTPDefault()`. The refund button's `POST /admin/orders/{orderID}/refund` has the same gate (`OrderRefundHandler.Mount`): it moves money, and the booking it leads to posts entries. Previews stay read-only and ungated. The SPA calls `ensureFreshTotp()` when the button is clicked.

**Failure mode:** with only the accounting-router role check, a board member with a stale session could post or void entries, import statements that auto-book, or run syncs that book a whole period.

### Board-facing member data lives under `/admin`

**Rule (BRY-477):** a route that returns members' contact details or changes who is offered a slip is mounted in the `/admin` group, so it inherits `RequireAdminTOTP` (the 12-hour step-up). The waiting list's admin side is `/admin/waiting-list` (`WaitingListHandler.MountAdminRoutes`): the list takes the step-up alone, and enroll, offer and reorder add `RequireFreshTOTPDefault()`, like slip assignment. The member routes (`/waiting-list/join`, `me`, `portal`, `withdraw`, `{entryID}/accept`, `decline`) stay outside it. `TestWaitingListAdminRouteGates` pins every route's gate.

**Failure mode:** the admin routes sat under `/waiting-list` behind a role check only, so a board member whose step-up had lapsed still read every entry's name, email and phone and could change queue positions with a stale session.

### The club always keeps an active admin

**Rule (BRD-9, BRY-535):** nothing removes the last active admin of a club: not a delete, a deactivation, a role change that drops `admin`, nor processing that admin's GDPR deletion. An active admin holds the `admin` role and has `deactivated_at IS NULL`. Each such path takes `lockClubAdmins` (a per-club `pg_advisory_xact_lock`) before any row lock and checks `ensureNotLastActiveAdmin` under it; a refusal is 409 `last_admin` and writes nothing. A member who holds `admin`, and the grant of the role, can only be changed by an admin (403 `admin_required`) even though the board reaches `/admin/users` writes: that covers the profile and email (`PATCH`; the email is a login credential, so a board edit would be an account takeover), slips, deactivate, reactivate and roles; `DELETE /admin/users/{id}` is `RequireRole("admin")`, and boats, TOTP, passkeys and CSV are admin-only at the route. A new path that takes a `{userID}` the board can reach, deactivates a user or edits `user_roles` must call the same guards (`requireAdminForAdminTarget`, `checkAdminTarget`, `lockClubAdmins`).

**Failure mode:** a board member with a fresh TOTP deleted or deactivated an admin, and since BRY-525 a delete also removes the admin's passkeys, TOTP and tokens; for the club's only admin nobody could undo it and recovery needed SQL. Two admins removed at once, each seeing the other still present, would do the same.

### An erased member's identity does not stay in the audit log

**Rule (BRD-11, BRY-536):** audit rows about a member hold ids (`resource_id`, `user_id`), never a name, email, phone or address. Every path that erases a member's identity (`HandleDeleteUser`, an immediate `HandleProcessDeletion`, the purge sweep) calls `audit.ScrubMemberPII` in the same transaction, which removes `audit.MemberPIIKeys` from the details of the member's rows and keeps the rest. A new audit write about a member stores ids only; a new identity key joins `MemberPIIKeys`. `audit_log` is append-only by convention (nothing in the database enforces it), and the scrub is its one sanctioned `UPDATE`.

**Failure mode:** `delete_user` stored `old_email` and `old_full_name`, and `user.deactivated` stored both too, so a member erased for GDPR stayed named in the log indefinitely.

### The member directory always lists the board, and never the erased

**Rule (BRD-12, BRY-545):** `HandleGetDirectory` (`directoryQuery`) lists every active member who holds a role in `roles.Board` with name and email, whatever their `hide_in_directory`; only the phone follows it. Other members who set it are left out. `admin` is not a board role. Deactivated rows and rows whose email ends in `accounting.ErasedEmailSuffix` are never listed. The response carries no field saying a member hid themselves. A new member-facing list of members' contact details decides explicitly whether the board exception applies and reuses `roles.Board`; it never keeps a second board list. The harbour map occupant deliberately keeps honouring the flag for board members too.

**Failure mode:** a board member who ticked "hide me" vanished from the directory, so members had nobody to contact; the opposite slip, a second hand-written role list, drops a role such as vice chair or deputy from the directory or lists a former board member's contact details.

### Board viewing never widens a write

**Rule (BRY-372):** every board role and admin (`roles.CanViewAdmin`) may read every admin page except Developer and Site. Reads open through `middleware.RequireRoleOrBoardRead(<write roles>)`, which admits viewers only on `GET`/`HEAD` and applies `RequireRole(<write roles>)` to every other method, so a surface's write roles are the ones it had before. A handler mounted on `GET` behind it must not write, mint a credential or send anything; such a `GET` keeps its own `RequireRole` (the pay-link endpoints do). In the SPA, write controls on viewable pages hide behind `useCan()`.

**Failure mode:** swapping a group's `RequireRole("board", …)` for a plain viewer check would hand `chair`, `secretary` or `deputy` every `POST`/`PUT`/`DELETE` that relied on the group gate (account create, rules, momskomp save, slip edits). The read helper exists so opening reads cannot do that.

### `totp_verified_at` is the source of truth for step-up freshness

**Rule:** Both `RequireFreshTOTP` and the SPA's countdown logic compute "is this fresh?" from `sessions.totp_verified_at`. Client-side timers are advisory only. The backend always reverifies on every gated request.

**Failure mode:** client clock skew lets a stale session bypass step-up. Or a tampered client gets to claim freshness it didn't earn.

### TOTP middleware runs after AuthenticateSession

**Rule:** `RequireFreshTOTP` and `RequireAdminTOTP` both read `SessionInfo` from the request context, which `AuthenticateSession` populates. Reversing the order produces nil-pointer dereferences in dev and silent admin-bypass in prod (since the gate runs against an empty session).

**Failure mode:** a confused middleware chain admits a request that shouldn't have been admitted.

### The client IP is `r.RemoteAddr`, set only from a trusted proxy

**Rule:** `middleware.ClientIP` rewrites `r.RemoteAddr` from `X-Forwarded-For`, and only when the immediate peer is in `TRUSTED_PROXY_CIDRS` (default loopback). It walks the header from the right and takes the first address that isn't a trusted proxy; otherwise `RemoteAddr` is the peer's IP. Either way it is a bare IP with no port. Handlers, rate-limit keys, sessions and audit logs read `r.RemoteAddr` and never a forwarding header. `True-Client-IP` and `X-Real-IP` are never believed: reverse proxies pass them through from the client unchanged.

**Failure mode:** a client sets its own IP with a header. It gets around the per-IP rate limits on login and magic-link requests, and forges the IP in sessions and audit logs. chi's `RealIP` had this hole (BRY-423).

### Outbound fetches of user-supplied URLs check the dialled IP

**Rule:** a server-side fetch of a URL a user supplied (today: the inbox image proxy, `HandleProxyImage`) refuses non-public addresses in `net.Dialer.Control`, which receives the resolved `ip:port` of every connection attempt — the first request, each redirect hop, and each Happy-Eyeballs fallback. A `LookupHost` check before the request is only a fast 403, never the guard. `isPrivateIP` is the one definition of "non-public": anything not global unicast, RFC 1918 / ULA, loopback, link-local, CGNAT `100.64.0.0/10`, `0.0.0.0/8`, `192.0.0.0/24`, `198.18.0.0/15`, `240.0.0.0/4` and NAT64 `64:ff9b::/96`, with IPv4-mapped IPv6 unmapped first; an unparseable address counts as non-public. The client's Transport has no `Proxy`, because through a proxy Control would vet the proxy's address instead of the target's.

**Failure mode:** a hostname that resolves to a public IP at check time and to `127.0.0.1` or `169.254.169.254` at dial time (DNS rebinding), or a redirect to an internal host, makes the server fetch internal services for the caller. Checking in `DialContext` does not help: the Transport passes it `host:port` with the name, not the IP.

### The session cookie's Secure flag follows `FRONTEND_URL`

**Rule:** `SetSessionCookie` and `ClearSessionCookie` take `Secure` from `cookieSecure(cfg)` (`FRONTEND_URL` starts with `https://`), never from `r.TLS` or `X-Forwarded-Proto`, and both set the same `Secure`/`HttpOnly`/`SameSite=Lax`.

**Failure mode:** behind the TLS-terminating proxy `r.TLS` is nil and whether `X-Forwarded-Proto` is trustworthy depends on the proxy, so the session cookie can be issued without `Secure` and leak over a plain-http request.

## Invoicing

### `invoices.kid_number` is unique per club

**Rule:** `idx_invoices_kid` enforces `UNIQUE (club_id, kid_number) WHERE kid_number <> ''` (migration 059). KID generation reserves the next sequence number atomically before issuing. The KID encodes club + sequence + check digit.
- **`''` means "no KID", not a key.** Imported fakturas and bank rows without a KID all carry it, and it isn't unique. Any join or match on `kid_number` must require it non-empty on the side it keys on. `backfillUnlinkedPayments` does (BRY-415).
- **A bank row's KID is what the payer typed, so it isn't proof of the faktura.** A row already assigned (`bank_import_rows.invoice_id`) is that faktura's payment. The backfill skips a row assigned to another faktura, e.g. a member paying this year's dues with last year's KID.
- **The backfill trusts only a posted CR 1500 booking (BRY-417).** A voided entry stays on `bank_import_rows.journal_entry_id`, and import auto-match links rows to drafts, so the row's entry must be `posted` and credit 1500 before either backfill pass marks a faktura paid.
- Two `NOT EXISTS (… bir.kid_number = i.kid_number …)` checks still compare empty KIDs: the name matcher (`banksync.go`, `findInvoiceByCounterpartAndAmount`) and the invoice-number match in `kid_cascade.go`. For an imported faktura they find any booked KID-less row, so those matchers never pick an imported faktura. That is conservative, and it is kept on purpose: booking CR 1500 for an imported faktura needs its receivable in the GL first. The lock they feed (`lockKIDCascade`) now refuses such a faktura too, with `ErrImportedNoOpeningBalance` (BRY-386), so it is a second guard, not the only one. Relax both SELECTs together, and only once the opening balance exists.

**Failure mode:** two invoices with the same KID — bank can't tell them apart, reconciliation pairs the wrong one. Joining on an empty KID did the same thing at scale: the bank-sync backfill marked 140 imported fakturas paid, several of them by a single bank row (BRY-415).

### `invoices.payment_id` is set only when a payment row exists

**Rule:** Either both `invoices.payment_id IS NOT NULL` and the referenced `payments.id` exists, or both are NULL. Never write `payment_id` pointing at a non-existent UUID, and never delete a `payments` row that any `invoices.payment_id` references.

**Failure mode:** dangling foreign key. Dashboard says paid; member says they didn't pay; nobody can explain the discrepancy.

### Settled means one thing, defined once

**Rule (BRY-325):** whether an invoice still needs paying is decided only through `internal/finance/settled.go`:
- **`SettledForMemberSQL`** returns true for `payment_id IS NOT NULL OR online_paid_at IS NOT NULL OR status = 'voided'`, or when a live credit note credits the invoice (`CreditedSQL`, BRY-342).
- **`OwedByMemberSQL`** is `IsDebtSQL` (a positive total) and not settled for the member. It answers "is the member chased for this?" and is used by reminders (both enqueue *and* the worker's send-time check), KID reissue, the member payables page and "unpaid" filter, checkout totals, the Vipps-blocked check, the open-faktura lookup of Vipps and bank auto-assign (`decideMemberInvoice`), and the Økonomi overview's overdue figures.
- **`SettledForGLSQL`** returns true for `payment_id IS NOT NULL`. It is used where the receivable must actually be cleared: reconciliation and bookkeeping.
- **Automatic matching of incoming money** to a faktura (bank KID and invoice-number lookups at import and in the bank sync, the counterpart-name match, the Vipps member match, bank auto-assign) uses `OwedByMemberSQL` (BRY-370). Money for a voided, Vipps-captured, credited or paid faktura is an overpayment a human must see, so the row stays in Tildel.
- **`OpenReceivableSQL`** (a debt, not voided, no `payment_id`, not credited) is the one exception: ePayment order reconciliation books the capture of a faktura that the webhook already marked `online_paid_at`, so it must not treat that flag as settled. The faktura suggestions for a *manual* assignment use it too (inside `assignableInvoiceSQL`), for the same reason: the charge being assigned is usually the payment that set `online_paid_at`. `vipps_paid_at` is the legacy Vipps-only copy of the marker: it is still written alongside `online_paid_at` and nothing reads it (BRY-450 drops it).

Voiding an invoice that is settled for the member (paid, or captured via Vipps) is refused with 409, because money arrived and it needs a refund or credit note instead. A credited faktura is refused with `code: credited` and the credit note's number (unlink first). The void's UPDATE repeats every check in its WHERE clause, so a payment or credit link that lands mid-request returns 409 `changed` and nothing is audited or reversed.

**Failure mode:**
- Settlement lags the Vipps capture by days. A check on `payment_id` alone chases members who already paid through the pay link. The reminder worker did exactly that at send time until BRY-325.
- A voided paid invoice hides received money that nothing is owed against.

### A credit note never asks for payment

**Rule (BRY-534):** a credit note (an invoice with a negative total, in the same number series as fakturas) is never presented as something to pay. Its PDF is a Kreditnota with no kontonummer, KID, forfallsdato or "Beløp å betale": `Invoice.CreditNote` is set by `HandleCreateInvoice` from the total it computes and by `loadStoredInvoicePDF` from the stored total, and `GeneratePDF` treats any negative line total as a credit note regardless. Its email is `email.CreditNoteBody`, with no payment details or pay link. Reminders, KID reissue, the payables page, pay links and bank-assignment lists exclude it through `finance.IsDebtSQL` ([Settled means one thing](#settled-means-one-thing-defined-once)). A new surface that lists or prints an invoice's payment details must handle a negative total the same way.

The debit faktura a failed card refund issues (`refund_documents.kind = 'refail_invoice'`) is settled in the same transaction, so it asks for nothing either: `Invoice.Settled` is set by `loadStoredInvoicePDF` from `refundRefailInvoiceSQL` (the refund document, never from the faktura merely being paid, because a paid ordinary faktura printed again keeps its payment block), and `GeneratePDF` then keeps the Faktura heading and the number and date rows but shows "Status: Betalt" and "Ingen betaling kreves. Fakturaen er allerede betalt." in place of kontonummer, KID, forfallsdato and "Beløp å betale". A credit note or zero-total faktura is rendered as such whatever `Settled` says. `InvoiceHandler.invoiceMessage` sends `email.RefundDocumentBody` for it (so a manual resend, the only send a faktura issued already sent allows, never carries a KID or pay link; the caller reads the marker with the faktura, so a failed read fails the request instead of sending the ordinary email), and its `payment_id` keeps it out of `finance.OwedByMemberSQL`, so reminders, overdue lists, payables and pay-link totals skip it. A new surface that prints or mails an invoice's payment details checks both rules.

**Failure mode:** a refund's credit note went out headed "Faktura" with "Beløp å betale: kr -5.00", a KID and "Vennligst betal kr -5.00 …", inviting the payer to pay a document that returns money; the settled faktura of a failed refund carried a kontonummer, KID and "Vennligst betal … innen <dato>" under an email saying nothing was to be paid, so a payer who opened the PDF could pay twice (BRY-541).

### Voided invoices stay in the table

**Rule:** `invoices.status = 'voided'` is terminal. Voided rows are excluded from receivables totals but remain in the table for audit. Never DELETE a voided invoice.

**Failure mode:** lost paper trail when an auditor asks why invoice #87 was voided.

### Invoice line snapshots are immutable

**Rule:** `invoice_lines.description`, `unit_price`, `line_total`, `category` are denormalized from `price_items` at issue time. Updating `price_items.amount` does NOT rewrite existing `invoice_lines`. Historical fakturas reflect the prices that were in effect when they were issued.

**Rule (BRY-389):** an issued faktura books by the category stored on its lines, never the price item's current category. Every line with a price item stores its category (CHECK `invoice_lines_price_item_category`, migration 000111), exemption lines included. Readers of an issued line's category use `finance.LineCategorySQL` (`COALESCE(il.category, pi.category)`); the item's category is only the fallback for lines written before the constraint. Paths that price a **new** faktura or charge (single and bulk creation, Vipps per-charge matching, the price hints) read the price item, since that is the category at issue. `invoices.category` (used for `payment_type`) is likewise stored at issue and must not be switched to the item's.

**Failure mode:** a price-list correction silently changes amounts on already-issued invoices. Treasurer's totals start drifting. Re-categorising a price item would move an old faktura's revenue to another account on the next resync or resplit.

### A faktura and its lines are written together

**Rule (BRY-389):** single (`HandleCreateInvoice`) and bulk (`createBulkInvoice`) creation insert the `invoices` row and all its `invoice_lines` in one transaction. A line the database refuses fails that faktura: the single request returns 500, and the bulk run reports that member under `skipped` (`create failed: …`) and carries on with the rest. The S3 PDF upload, the email, the GL booking and the audit rows run only after the commit; the upload's `pdf_data` wipe runs on its own connection and would not see an uncommitted faktura.

**Failure mode:** before BRY-389 a failed line insert was only logged, leaving a faktura whose `total_amount` disagreed with its lines; the GL sync then booked the difference to 3900 as a residual.

### A referenced price item is archived, never deleted

**Rule (BRY-360):** `HandleDelete` on `/admin/pricing/{id}` hard-deletes a price item only when no `invoice_lines`, `invoices`, `order_lines` or `harbor_payment_targets` row references it. Otherwise it returns 409 `price_item_in_use`, and the SPA offers to archive it instead (`is_active = false`). Archived items are excluded from the faktura pickers, bulk invoicing, the public price list, the QR checkout catalogue, and the public QR target lookup (`loadQRTarget`). The short-address resolver (`HandleShortCodeRedirect`, `GET /q/{code}`) applies the same filter, so a typed address never leads to a target the token page would refuse. A printed poster for an archived item therefore stops taking payments.

**Failure mode:** `order_lines.price_item_id` and `invoices.price_item_id` are `ON DELETE SET NULL`. A delete that succeeded would silently strip the category from historical orders and invoices, and with it the revenue-account mapping used by GL sync and reconciliation. The other two FKs fail the delete, which used to surface only as a generic 500.

### Bulk-reminder queue is durable, throttled, and retried

**Rule:** `HandleBulkSendReminder` validates rows synchronously and enqueues each eligible reminder as an `invoice_reminder` row in the shared `deliveries` table (the same durable queue broadcasts use). The delivery worker drains it on a background context at `cfg.BulkSendThrottle` (default 1s) per send, retries transient SMTP failures up to a cap, and survives restarts (a boot sweep re-claims rows orphaned mid-send). Enqueue is idempotent per invoice: an invoice that already has a non-failed reminder queued is skipped (surfaced to the operator as "already queued"), so a re-run or double click can't double-send.

**Failure mode:** a deploy or crash during a 100-row send no longer loses the un-drained tail — the worker resumes on restart. Per-row `invoice.reminded` audit rows still reflect progress on the Sent tab's "Sist purring" column. Reminders whose invoice was paid or deleted between enqueue and send are treated as terminal no-ops (marked sent, not retried).

### Online payment is offered per the tri-state rule (override, else amount cap)

**Rule (BRY-283):** whether online payment (any provider) is offered for an invoice is the single expression `onlinePaymentAllowedExpr` (in `order_pay.go`):
- `invoices.online_payment_opt_in IS TRUE` (On) → **always** offered, even above the cap;
- `... IS FALSE` (Off) → **never**;
- `... IS NULL` (Auto) → offered iff `clubs.online_max_amount IS NULL` (no cap) or `total_amount <= online_max_amount`.

The legacy `invoices.vipps_payment_link_opt_in` and `clubs.vipps_max_amount` are still written with the same values by every writer (settings save, `PATCH /invoices/{id}/online-payment`, the reminder batch) and read by nothing; BRY-450 drops them.

So the amount cap is a **default**, not a hard ceiling — the per-invoice override wins either way. It is enforced at **both** points, because `orders.token`s are permanent and one exists for every sent faktura: at **issuance** in `ensureFakturaOrderToken` (returns `""` when not allowed, before the token-reuse lookup — so faktura/reminder emails, the admin copy-link, and the payables page all go KID-only) and at **mint** in `mintOrderPayment` (returns `errOnlinePaymentBlocked` via `orderHasOnlineBlockedSource` — so a link already in an inbox, or issued before the cap/override changed, can't be charged). The reminder batch's `vipps_payment_link` persists On/Off onto the reminded invoices (it sets the same column), so it too is honored at the member's eventual click.

**Failure mode:** enforcing at issuance alone would leave every large invoice already emailed fully Vipps-payable. Not-allowed invoices simply never get an `orders`/`order_sources` row minted, which is safe — the webhook keys off `payment_attempts` and reconciliation off `orders.vipps_reference`, both created only on mint.

### A role exemption is an offsetting line, booked gross

**Rule (BRY-351):** a club may exempt a board role (`roles.Board`, the one canonical list) from a price item or a whole price category (`price_exemptions`). Nothing is exempt by default. When a faktura is generated, bulk or single, for a member who holds an exempting role, the item stays on the faktura at full price and an offsetting negative line follows it:
- The offset line carries the item's `price_item_id` and `category`, its `exemption_role` and `account_id` = the club's `exemption_expense_account`. The bulk per-line duplicate check filters `exemption_role IS NULL`, so it still sees only the real line. GL booking honours `account_id` over the category, so the faktura books **gross**: CR the item's revenue, DR the expense account. The waived revenue is never netted away.
- Exemptions apply only while the expense account resolves to an active `expense` account. Otherwise nothing is exempted and the run returns a warning, so a misconfiguration bills in full rather than booking to the wrong account.
- Roles are read when the faktura is generated. Removing a role makes the next run bill normally; existing fakturas are not touched.
- The bulk preview (`preview: true`) lists every match with a `key`; `skip_exemptions` takes those keys and bills the unticked ones in full. The key is `<user_id>:<price_item_id>`, plus `:<boat_id>` on a boat-bound line, so one boat of a multi-boat member can be unticked on its own. A single faktura can opt out with `skip_exemptions: true`.
- A bulk run reads the exemption config (rules and expense account) **once, at its start**. A settings change saved while a run is in progress takes effect from the next run; the running batch keeps applying the snapshot it started with.
- Exemptions only offset positive lines. A credit note (negative total) and any line with `quantity × unit_price ≤ 0` get no offset, which would otherwise be positive and cancel the credit.
- The per-item overview reports `billed` gross and the exemption lines separately as `exempted`; outstanding is `billed − exempted − received`, and outstanding counts only fakturas members still owe.
- The member portal reads `owed` (`OwedByMemberSQL`): a 0 kr faktura shows as nothing to pay, never unpaid or overdue, and its KID is hidden.
- A faktura whose total is 0 is **settled on issue**: `IsDebtSQL` is `total_amount > 0`, so it is never owed, overdue, reminded or on the payables page, and `onlinePaymentAllowedExpr` never offers online payment (`total_amount <= 0 → false`). It still gets a KID (the column is NOT NULL and unique), but the PDF and email hide it and say nothing is due. Its GL entry has no 1500 line.
- Settings writes (`PUT /settings/economy/exemptions`) are treasurer/admin with fresh TOTP and audited as `pricing.exemptions_updated`.

**Failure mode:** without the offset line, exempt members were billed and then manually credited or waived off-book, so the waived amount disappeared from revenue and expense alike. Netting the item price to zero instead would hide what the exemption costs the club.

### A credit note is never a debt, and a credit link never posts

**Rule (BRY-342):** an invoice with a negative total is a credit note. It is never overdue, never reminded and never on the payables page (`OwedByMemberSQL`). A credit note settles the faktura it credits only through an explicit link, `invoices.credits_invoice_id`, set by an admin (`POST …/credit-link`, fresh TOTP). Nothing pairs them automatically, because several open fakturas can share a payer and amount.
- The link is refused unless both invoices are live and issued (sent or imported), have the same payer (member or billing recipient), and the credit equals the faktura's total. Partial credits are refused, because every "amount owed" path would have to net them.
- **Different payers (BRY-393).** The payer check is relaxed only when the credit note has neither `user_id` nor `recipient_id` (imported history), or the request carries `confirm_other_member: true`, which the UI sends only after asking. This is safe because the link only sets `credits_invoice_id`: it posts nothing and unlinking reverses it. The amount check is never relaxed. The manual search (`GET …/credit-candidates?any=1&q=`) drops the payer and amount predicates but keeps every target rule (club, open, positive, issued or imported, not credited) and marks `same_amount` / `same_payer` per row.
- A faktura is credited by at most one live credit note (`idx_invoices_credits_once`). The link re-checks inside its transaction, after locking, and maps the unique violation to 409 `already_credited`, so two concurrent links settle once.
- **The link never posts to the GL.** A booked credit note's own entry (DR revenue / CR 1500) already offsets the faktura's receivable, and imported history has no bookings on either side. A pair where only one side is booked is refused (`booking_mismatch`), with one exception: a booked Brygge credit note may settle an *imported*, unbooked faktura. The imported receivable lives in the opening balance on 1500, so the credit note's own CR 1500 is what clears it; posting anything at link time would clear it twice.
- That exception holds only once the receivable is actually on 1500: a posted `opening_balance` entry (source added in 000107, BRY-370) that debits 1500, dated **on or after the faktura's issue date** (an earlier opening balance can't contain it) and on or before the credit note. Without one the link is refused with `booking_mismatch` naming the missing opening balance, because the credit note's CR 1500 would otherwise drive 1500 negative. The check is `finance.ImportedReceivableOpenSQL` with the credit note's issue date as the booking date, the same predicate every payment path uses (below), so the two rules can't drift.
- **Nothing writes `source = 'opening_balance'` yet.** The journal API always books `manual`, so until the cutover import in BRY-365 posts the opening balance with that source, the exception never applies and every booked-credit-note-against-imported-faktura link is refused.
- The opening receivable is computed **at the cutover date**: every imported faktura still owed on that date, including ones a later Brygge credit note credits. Leaving the credited ones out (because they look settled today) double-counts the credit: its CR 1500 then clears a receivable that was never opened.
- A faktura that was already paid when it was credited makes the credit note **credit owed to the member** (refund or carry-forward). It is shown as such, never as overdue.
- A linked credit note can't be voided until the link is undone, so a void can't silently reopen the faktura.

**Failure mode:** before BRY-342, 19 imported credit notes (−27,700 kr) counted as overdue debts. Five open pairs each showed both halves as overdue, even though they net to zero.

### Imported fakturas are read-only

**Rule (BRY-396):** a faktura with `import_source` set is the previous system's record. No endpoint changes it except two:
- **Refused** with 409 `{code: "imported"}`: delete, void (checked before the idempotent "already voided" answer, since an imported row keeps whatever status it had there) and send. Delete and void repeat the guard in their write's WHERE.
- **Skipped** by the bulk actions: regenerate PDF and reissue KID. A Brygge PDF or KID must never replace the original, and members may still pay with the old KID.
- **Already excluded because `sent_at` is NULL:** resend, reminders, the invoice GL sync and the resplit. Don't rely on that when adding a path: imported rows have `sent_at` NULL only because the import doesn't know the send date.
- **Allowed:** credit links (the opening-balance rule above), the online-payment preference, reading the PDF, and payments, which are guarded as follows.
- **Payments credit 1500 only once the receivable is in the GL (BRY-386).** `finance.ImportedReceivableOpenSQL(alias, bookingDate)` is true for a Brygge faktura, or for an imported one with a posted `opening_balance` entry debiting 1500 dated on or after its issue date and on or before the booking date, or with its own posted `invoice_sync` entry. Every path that would credit 1500 for a faktura checks it with the payment's own booking date: manual bank Tildel (row date; multi-row: the **earliest** row, since each row is booked on its own date), the KID cascade lock (row date), manual Vipps assign and order-linked Vipps charges (charge date), the legacy Vipps member match and its confirm (charge date; the confirm re-checks every linked faktura instead of trusting the preview). A refusal is `accounting.ErrImportedNoOpeningBalance`: nothing is booked and the row stays in Tildel; the handlers answer 409 `{code: "imported_no_opening_balance"}`. Checkout gates on the same predicate with `CURRENT_DATE`: no Vipps pay token on the payables page, 409 on the staff pay link, and `orderHasOnlineBlockedSource` stops an order minted earlier. Auto-assign refuses imported fakturas outright. A `lockInvoiceForAssign` call in `lockManual` or `lockKIDCascade` mode without a booking date is refused as a caller bug.
- **Paid status at the cutover comes from the previous system, not from bank matching.** The cutover is the start of the club's first Brygge year, and the opening-balance entry is dated on it. Whether an imported faktura was still owed on that date is decided by the previous system's open-items list (kundereskontro) at the cutover, and the 1500 line of the opening balance must equal that list's total. No matcher or backfill may infer it: imported fakturas have no KID and share amounts, so a row's amount or KID is not proof (BRY-415, BRY-417). Only payments dated after the cutover are booked in Brygge, through the guard above. The pre-cutover year's books of record stay in the previous system; its Brygge period is a reference year ("A reference period books only costs and carries nothing forward", BRY-418).

**Failure mode:** before BRY-396 only the UI hid delete and void on the Importert tab, so a direct API call could delete or void the previous system's record. Before BRY-415 the bank-sync backfill marked imported fakturas paid by any booked bank row of the same amount and an empty KID.

### Only the payment provider can mark an order paid

**Rule:** an order (or the invoice behind it) becomes paid only from evidence that money moved: a payment provider's signature-verified webhook, which calls `orderSettlement.markAttemptCaptured` (`handlers/order_settle.go`), or reconciliation against a settlement or bank row. No HTTP route, public or admin, sets `orders.status = 'paid'` or `invoices.online_paid_at`/`vipps_paid_at`/`payment_id` from a caller's say-so, and a new provider's webhook goes through `orderSettlement` rather than writing that state itself (see [../payments.md](../payments.md)).

**Failure mode:** a "confirm" endpoint that flips status on request lets anyone holding an order id mark it paid with no money received. That is what the pre-BRY-259 `POST /orders/{id}/confirm` stub did; it was removed in BRY-306.

### A payment attempt that is not needed is never captured

**Rule (BRY-441):** an order can carry several `payment_attempts`; the newest one the provider created (it has a `provider_reference`) is its current one, so a row whose provider call never returned can't shadow a real payment. Settlement works per attempt (`orderSettlement` in `handlers/order_settle.go`):
- An **authorization** is decided in one transaction holding the order row (`authorizeAttempt`): a replay for an attempt already `captured` or `cancelled` is skipped; an authorization for an order already paid or refunded, or while **another attempt of the order is `authorized` or `captured`**, is marked `cancelled` in that transaction and then voided through the provider's `payments.Canceller`, best-effort (an authorization whose void fails lapses at the provider). It is never captured. Otherwise the attempt becomes `authorized` and is captured, including an older attempt on a pending order: the payer finished it. So of two authorizations arriving together only the first is captured. The trade-off: if that first capture then fails at the provider, the second payer's authorization was already voided and they retry. A failed capture returns the attempt to `created`, and a terminal event moves an authorized attempt to `failed`, so a stuck authorization never blocks a fresh attempt. If the decision itself fails (database error) nothing is captured or voided and the error is returned, so the webhook answers 5xx and the provider delivers the event again (see the next invariant).
- **Stripe** maps onto the same decision: sessions are created with manual capture, so `checkout.session.completed` is an authorization, never a capture. Its amount and currency must equal the attempt's (otherwise it is voided and the attempt `failed`) before `authorizeAttempt` decides; Brygge then captures the PaymentIntent (key `capture2-<attempt id>`; a key Stripe refuses is not a failed capture — the PaymentIntent is re-read and, still authorized, captured under a derived key, never voided) or voids it. A capture that fails while the PaymentIntent is still authorized voids it and fails the attempt. `payment_intent.succeeded` is the capture event that settles an attempt whose capture answer was lost, only when the full amount was received, and Brygge's own voids (`payment_intent.canceled`) never fail an attempt already `captured` or `cancelled`.
- A **capture** marks the attempt `captured` and pays the order from `pending` or `failed` (a capture means money was taken; coming from `failed` is logged as a warning), with `paid_at` and the faktura marker both set to the provider's capture time, all in one transaction (`settleCapture`) that takes the order row first. If another attempt already paid the order, the order is left as it is and the double payment is logged at error level, once, for a refund.
- A **terminal event** (cancelled, aborted, expired, terminated) marks the attempt `failed`, and fails the order only if the attempt is the order's current one and the order is still pending.
- The mint writes the attempt's outcome (reference, or `failed`) with a context detached from the payer's request, so a payer closing the tab mid-call can't strand an attempt or lose a reference to a payment the provider created.

**Failure mode:** with one reference per order, a payer who re-clicked the pay link and then completed the earlier Vipps window was charged and never matched; and capturing every authorization would charge twice a payer who completed two windows.

### A webhook never acknowledges an event whose lookup or settlement failed

**Rule (BRY-452, BRY-512):** a payment webhook answers 200 for an event only when it was stored and either fully handled or genuinely not Brygge's. A database error anywhere in handling it answers 5xx, so the provider delivers it again; it is never read as "not our payment" or as "done".
- **Lookups.** The club (`resolveClub`, `firstClub`), the attempt (`attemptByReference`, `attemptByID`, through `scanAttempt`) and the placement of a dispute or refund (`claimAttempt`, `paymentFromCharge`, `intentPayment.unplaced()`, which also covers Stripe being unreachable): any error other than "no row" fails the event, and only "no row" means ignore.
- **The authorization decision.** `authorizeAttempt` returns its error (and answers `authSkip`, never `authCapture`), so nothing is captured or voided without the order row lock and the recorded decision. A capture on a failed decision could take a duplicate payment that can then only be refunded; leaving the authorization undecided costs a retry, and it lapses at the provider if none comes.
- **The settlement writes.** `markAttemptCaptured`, `markAttemptFailed`, `releaseAuthorization` and `payOrder` / `markInvoicesPaidOnline` (inside `settleCapture`) return their errors up through `dispatch`. A capture's attempt, order and faktura-marker writes share one transaction, so a failure leaves them all undone; `markAttemptFailed` is two guarded writes that the redelivery repeats.
- **Not an error:** a guarded write that changes no row (another delivery already did it, the order is already paid or refunded), a reference that is not ours, an amount or currency mismatch (voided and failed, deterministic), a provider call that fails (capture, void, lookup: handled by the release / void-and-fail paths) and the descriptive best-effort writes (guest name and email, card brand and wallet, the double-payment diagnostic), which are logged only.

A new provider's webhook uses the same split.

**Why a retry is safe.** The event store inserts once (`ON CONFLICT DO NOTHING`) and dispatch runs on every delivery. After a capture that succeeded at the provider but whose settlement failed, the attempt is still `authorized` and the order unpaid (the transaction rolled back), so the redelivery decides capture again and calls the provider under the same key: Stripe `capture2-<attempt id>` replays the first answer, or, past the key's lifetime or on `idempotency_error`, `CapturePaymentIntent` re-reads the PaymentIntent and returns it when already `succeeded` (it captures again, under a derived key, only when the PaymentIntent is still `requires_capture`, i.e. nothing was taken). Vipps settles on CAPTURED, never on AUTHORIZED, so its CAPTURED redelivery only repeats the guarded writes; a redelivered AUTHORIZED repeats the capture under the stable key `capture-<reference>`. Once the settlement commits the attempt is `captured` and every later delivery is a skip. A sibling authorization arriving in between sees the first attempt as `authorized` and is voided. If the order is moved to `refunded` before the redelivery, the redelivery decides `authCancelOrderSettled` and marks the attempt `cancelled` (the void of a captured payment fails and is logged); a later `payment_intent.succeeded` repairs the attempt to `captured`.

**Lock order.** `settleCapture` locks the order's fakturas first (`FOR NO KEY UPDATE`, id order), then the order, then the attempt, matching the Stripe refund booking (`lockInvoicesTx`, then `markOrderRefundedTx` / `restoreRecollectTx`); the authorization decision and the refund request take order then attempt and no faktura. Taking the order first in `settleCapture` would deadlock with a refund booking. The writes that record the outcome of a capture, void or release run on a context detached from the request (`settleContext`, 15 s), so a provider timeout or disconnect after the money moved cannot roll back a healthy settlement.

**Alerting.** Every 5xx a payment webhook handler writes goes through its `internalError`, which counts it in `brygge_payment_webhook_failure_total{provider,event_type}`; a new 5xx path must answer through it, or the PaymentWebhookFailing alert will not see it. Panics (the router's `Recoverer`) and a handler slower than the provider's timeout (Vipps: 10 s) are not counted. An attempt left `authorized` is PaymentAttemptStuckAuthorized ([runbook](../otel/alerts-runbook.md#paymentattemptstuckauthorized)). Provider retry windows: [payments.md](../payments.md#webhook-retry-windows).

**Retry cost.** Only database errors (and context cancellation) are 5xx, so a deterministic problem cannot cause a retry storm; a statement that keeps failing for good is retried at the provider's backoff pace and shows up as an error log per delivery, which is the point: it used to be a silently unpaid order.

**Failure mode:** a transient database error during a lookup was read as an unknown reference, and one during the decision or a settlement write was logged and answered 200; the provider never sent the event again, so a captured payment stayed unpaid on the order, a duplicate payment was captured, or a refund or dispute went unrecorded, until someone noticed.

### How a payment was made never decides whether it was made

**Rule (BRY-469):** the card brand and wallet of a Stripe payment (`payment_attempts.card_brand` / `card_wallet`) are descriptive and best-effort. They are written only after settlement (`orderSettlement.recordAttemptCard`, and the Stripe balance sync), each write guarded by `card_brand IS NULL` and only logged on failure. Reading them must never fail the call that carries them: `stripe.Client.CapturePaymentIntent` treats a 2xx body it cannot decode as a successful capture (nil PaymentIntent), and `ChargeRef` / `PaymentMethodDetails` decode an unexpected shape as empty rather than failing the PaymentIntent or balance page around them.

**Failure mode:** a capture whose answer fails to decode reported as failed sends the webhook into `afterFailedCapture`, and a PaymentIntent lookup failing on the charge it expands releases a captured attempt instead of settling it — money taken, order left unpaid, over a field that only labels the overview.

### An order's payment group comes only from `paymentfilters`, and a price item is in at most one group

**Rule (BRY-522, PAY-15):** the filter group of an order (the `kind` on the Payments page, the `kind` filter, and the group the SMS alerts of BRY-521 route by) is decided by `internal/paymentfilters` and nowhere else: the overview joins `paymentfilters.OrderGroupLateralSQL`, single orders call `paymentfilters.ClassifyOrder`. The rule is the enabled group with the lowest position among the groups that hold one of the order's **order lines**' price items and the faktura built-in when the order has an `order_sources` row, else the `other` built-in, which is never matched. A `kind` filter stays in that SQL, before `LIMIT`, bound as a `text[]`. A price item is in at most one group: `payment_filter_group_items.price_item_id` is the primary key, and a move is `ON CONFLICT (price_item_id) DO UPDATE`. Every write of the groups takes `paymentfilters.Lock` (a per-club advisory lock) and `EnsureBuiltins` first, so two admins serialise and a club without rows gets its built-ins on its first write; a GET only reads and synthesises them.

A new group is created just before the faktura built-in and the positions are renumbered under the same lock, so it ranks above Faktura like the seeded groups. A price item can be on an order line when its category is offered by the checkout, an active QR poster sells it, or an order line has it (`paymentfilters.ListPriceItems`, from data); only an item that is none of these is billed on fakturas only.

**Failure mode:** a second copy of the rule (an SMS alert that classifies on its own) tells the harbor master a "Slipping" payment came in that the Payments page shows under Annet. An item in two groups made the chip an order was filed under depend on which group sorted first, so filtering by the second group missed it. Two admins moving the same item or sorting at once interleaved and left gaps or an order nobody chose. An item that only a faktura bills can never put an order in a group, since the classifier sees only order lines; treating whole categories as such was wrong (a `membership` item can be a checkout add-on and a QR poster can sell any item), so reachability is read from data. An order that pays a faktura is Faktura unless one of its order lines holds an item of a group that ranks above it. A group created below Faktura silently lost to it on a faktura checkout with that group's add-on, while the migration-seeded ones won.

## Sessions

### Sliding idle window vs absolute cap

**Rule:** Sessions have a 12-hour sliding idle window and a 7-day absolute cap (`sessionIdleWindow`, `sessionAbsoluteCap` in `internal/auth/session.go`). The cookie MaxAge tracks the absolute cap. `ValidateSession` enforces both bounds; the idle extension is throttled (`sessionExtendThreshold`).

**Failure mode:** sessions that live forever, or sessions that get killed without warning before the user's done.

## Deploy

### No migration runs without a pre-deploy snapshot

**Rule:** `nix run .#deploy` (and so `just deploy`) takes a fresh `pg_dump` on the host via `brygge-pre-deploy-backup.service` before deploy-rs activates the new system, which is when migrations run. If the snapshot fails, or no dump newer than this deploy appears, the deploy aborts. `SKIP_BACKUP=1` is the only bypass and is announced. The snapshot directory is created by tmpfiles on the host, and pre-created by the deploy script for hosts whose config predates that rule. The unit's `ProtectSystem=strict` + `ReadWritePaths` fails with exit 226 when the path is missing.

**Failure mode:** a deploy script that swallows the backup error ("skipped (service not found on host)") ran every migration with no rollback point while the operator believed one existed (BRY-304). A system rollback does not undo a migration.

### Backups are dumped with the server's own Postgres major version

**Rule:** `nix/backup.nix` takes `pg_dump` from `config.services.postgresql.package`, never an unpinned `pkgs.postgresql`. A dump has to be restorable with the server's own `pg_restore`.

**Failure mode:** the backup scripts used `pkgs.postgresql`, which follows nixpkgs (17 by October 2026) while the server ran 16. Every nightly and pre-deploy dump was written in archive format 1.16, which the server's `pg_restore` 16 rejects ("unsupported version (1.16) in file header"). A disaster restore on the host would have failed. Found by `migrate-check-prod` on 2026-10-16.

## Config

### Env vars are trimmed at the boundary

**Rule:** `cleanBaseURL` and friends in `internal/config` strip surrounding quotes, whitespace, and trailing slashes from string env vars before storing them. Magic-link URL generation depends on this — a trailing quote in `FRONTEND_URL` produced broken links in production until a regression test got added.

**Failure mode:** silent breakage of any feature that concatenates URLs.

### `TOTP_ENCRYPTION_KEY` rotation is destructive

**Rule:** The 32-byte hex-encoded key encrypts every TOTP secret in the DB. Rotating it without a re-encrypt migration makes every existing enrollment unrecoverable.

**Failure mode:** every admin gets locked out of 2FA. Manual DB intervention required to recover.

### `audit_log.resource_id` is TEXT, not UUID

**Rule:** `audit_log.resource_id` is a `TEXT` column even though every callsite passes a UUID. When joining `audit_log` against a UUID column (e.g. `invoices.id`), explicitly cast — `resource_id = invoices.id::text` — or Postgres returns `ERROR: operator does not exist: text = uuid`.

**Failure mode:** the query throws 500 the first time it runs against a non-empty audit log. The `last_notified_at` subquery on `HandleListInvoices` got bitten by this in commit `b8573c4`; fix in the follow-up.

### The system resolver forwards the tailnet zone to MagicDNS

**Rule (BRY-402):** any change to the host's resolver (`services.unbound`, `networking.nameservers`, resolvconf, the tailnet client's DNS flags) must keep `clubConfig.tailnetDomain` forwarded to `100.100.100.100`, exempt from DNSSEC validation, with every other name still recursing locally. `OTLP_ENDPOINT` is a fully qualified tailnet name and nothing else resolves it. See [otel/local-collector.md § Name resolution](../otel/local-collector.md#name-resolution).

**Failure mode:** with `unbound` recursing from the root and openresolv putting it first in `/etc/resolv.conf`, the tailnet name came back NXDOMAIN and glibc never asked MagicDNS. The collector logged `no children to pick from` on every export, nothing left the host for over a month, and its stack-trace log spam (~150k journal entries a day) cut journal retention from a month to ~5 days.

## Mail

### Stalwart's local TOML shadows DB settings; never set `config.local-keys`

**Rule (BRY-400):** a key set in `services.stalwart.settings` (`nix/host.nix`) shadows the same key in Stalwart's DB at boot and on reload, so mail settings that must hold — `auth.dkim.sign`, `auth.arc.seal`, `report.*.sign`, `sieve.trusted.sign`, which all name the DB-held signature `mail` — live in `host.nix`, not the admin UI. Never set `config.local-keys`: it replaces Stalwart's whole default list of local keys instead of adding to it.

**Failure mode:** with `auth.dkim.sign` unset, Stalwart 0.15 signs with `rsa-<domain>` / `ed25519-<domain>`, which don't exist, logs `DKIM signer not found`, and sends every message unsigned — DMARC then passes on SPF alone and receivers rate-limit the domain. See [mail/setup.md § How signing is selected](../mail/setup.md#how-signing-is-selected).

### Every reader of the mail certificate is in its `reloadServices`

**Rule (BRY-410):** any service that reads `/var/lib/acme/mail.<domain>/` must be listed in `security.acme.certs."mail.<domain>".reloadServices` (`nix/host.nix`). Today that is Caddy (reloads; with `services.caddy.enableReload` at its default its NixOS `ExecReload` is `caddy reload --force`) and Stalwart (no reload, so it restarts).

**Failure mode:** a reader that isn't listed keeps serving the old certificate after renewal until something restarts it, and clients see an expired certificate on that port. In October 2026 the renewed cert sat on disk while Caddy and Stalwart served the old one. See [mail/setup.md § Certificate lifecycle](../mail/setup.md#certificate-lifecycle).

### A principal's description is display text; ownership markers live in `urls`

**Rule (BRY-406):** every Stalwart principal Brygge provisions (`stalwart-mailbox-config` in `nix/host.nix`, `UserProvisioner` in `backend/internal/mail`) carries only a plain label in `description` — the mailbox's `display_name`, `System postmaster`, `Brygge user`. The ownership marker goes in the principal's `urls` (`urn:brygge:managed-by:brygge-tf` / `urn:brygge:managed-by:brygge-user`), and user principals add `urn:brygge:user:<user uuid>` as a non-PII correlator; never a personal email. The sender name of a shared mailbox has one source, `mail.SenderName`, used by the app's From header, the SPA's `from_name` and the reconciler's Identity sync.

**Failure mode:** Stalwart copies the description into the account's default JMAP Identity name once, on the first `Identity/get`. A marker in the description became the From name recipients saw (`"<club> (managed_by=brygge-tf)"`) for mail sent by a session logged in as the shared principal. See [mail/inbox.md § Operational gotchas](../mail/inbox.md#operational-gotchas).

### App SMTP mail's envelope sender is the bounce mailbox, never `relay@`

**Rule (BRY-404):** Stalwart rewrites the envelope sender of the `relay` login (`session.mail.rewrite` in `nix/host.nix`) to the bounce mailbox — the single `type = "shared"` `board_mailboxes` entry with `receives_bounces`, else `postmaster@<domain>` (`nix/mail-bounce.nix`, whose module assertions reject two flagged entries or a flagged list). `session.auth.must-match-sender` is relaxed only for `relay` sending as exactly that address; every other login must still send as its own address. `postmaster` is a list whose `admin_email` member is set through `externalMembers` — `members` takes principal names, and a list with no resolvable member silently discards mail.

**Failure mode:** `relay@` has quota 1, so with relay@ as the envelope sender every DSN failed "over quota" and was dropped as a double bounce — delivery failures of app mail were invisible. See [mail/setup.md § Where bounces for app mail go](../mail/setup.md#where-bounces-for-app-mail-go).

### A public route that sends mail never lets the visitor choose From or To

**Rule (BRY-475):** `POST /contact` (`handlers/contact.go`) sends to a club-configured address (`contactRecipient`: `secretary_email`, else `chairman_email`) from the app's own sender; the visitor's address is only the `Reply-To` header, and it is a bare mailbox that passed `parseBareEmail`. The visitor's subject (which reaches the Subject header) and name (body only) go through `cleanSingleLine`, which turns CR, LF and every other control character into a space; the subject is also cut to 60 runes in `email.ContactSubject` because the Q-encoded header is not folded and a long run of four-byte characters would pass the 998-character line limit. The route has its own per-IP limiter, and a failed send answers 502 and logs without the submitter's text.

**Failure mode:** a visitor-controlled From spoofs the club's domain and fails DMARC for the whole domain; an unstripped CR/LF in the subject injects headers (extra Bcc recipients, so the club's mailbox relays spam); a "received" answer for a message that was only logged loses every enquiry without anyone knowing.

## Developer DB query (DIL-365)

### Query role is default-deny: masked views + a non-PII allowlist

**Rule:** `brygge_dev_ro` reads only (a) the PII-masking `dev_masked.*` views and (b) an explicit allowlist of base tables with no person-identifying free text (migrations `000095`, narrowed by `000097`). Free text counts as PII even on accounting tables, because bank-import entries copy the payer's name into descriptions (BRY-336). Everything else — `audit_log`, credential tables, and any newly-added table — is denied until explicitly classified. The full deny/allow/mask classification is the source of truth in [`../security/dev-query.md`](../security/dev-query.md), not `accounting/purge.go`. Identity, credential and free-text columns in the masked views are `NULL`, never partial-masked (a partial value plus the opaque id is a reversible membership oracle in a small club); correlation keys pass through verbatim. Because the role can never read raw PII, a full-SQL audit of its queries contains no PII by construction.

**Failure mode:** a new table auto-granted to the role (the pre-BRY-286 default-allow) silently exposes PII/secrets; a leaked session enumerates or erases its own `audit_log` evidence and the blast radius becomes unbounded.

### Name tokens are keyed, function-free, and only from names the agent can't write

**Rule:** the dev-query role sees names only as keyed HMAC pair tokens (BRY-343).
- **The key:** `dev_private.token_key` is never granted to `brygge_dev_ro`. Views read it through a scalar subquery, never through a function or an IMMUTABLE accessor, and no function that reaches `dev_private` may be executable by the role.
- **What gets tokenised:** only names the agent has no way to write. Data from public, unauthenticated inputs (such as `orders.guest_name` from the QR pay endpoint) is never tokenised.
- **Granularity:** tokens cover unordered word pairs, never single words.

**Failure mode:** a readable key, or any callable tokeniser, lets the role compute the token for a guessed name and confirm who someone is. A tokenised public input does the same by another route: submit a name, then read its token back. Single-word tokens re-identify people by frequency (a few common local surnames).

### Developer tokens are hashed, scoped and role-less

**Rule:** developer bearer tokens (BRY-115) are stored only as `sha256(token)`, and the plaintext is returned once at mint. `devtoken.Authenticate` admits a token only while its minter is active (`deactivated_at IS NULL`, same club) and still holds `devtoken.MinterRole` (`admin`, the role the mint routes require), so deactivation or demotion cuts access on the next request; a DB error refuses the request (BRY-540). Keep `MinterRole` and the `RequireRole` on `/admin/dev/tokens` in step. `RequireDevToken` is the **only** middleware on `POST /api/v1/dev/query` and is mounted on no other route. It ignores cookies and injects claims with **no roles**, so a token can never satisfy `RequireRole` or reach a session route. The route exists only when `DEV_QUERY_TOKENS_ENABLED=true`. `developer_tokens` is never added to the `brygge_dev_ro` allowlist.

**Failure mode:** a token mounted on a broader route, or carrying the creator's roles, turns a short-lived read credential into an admin session that bypasses TOTP. A plaintext token at rest, or a readable `developer_tokens` table, turns one DB read into token theft. An `Authenticate` that checks only expiry and the revoked flag lets a deactivated or demoted admin's token keep reading masked data for up to its 7-day TTL.

### Query role is a real privilege boundary, not `SET ROLE`

**Rule:** the `/admin/dev/query` endpoint runs on a dedicated pool that
*authenticates as* `brygge_dev_ro` (a `LOGIN` role, `DEV_QUERY_DATABASE_URL`),
never via `SET ROLE` on the `brygge` connection. `brygge_dev_ro` is **not** a
member of `brygge`, so a session has no higher role to return to. The role's
read-only / timeout / `search_path` GUCs are pinned with `ALTER ROLE`.

**Failure mode:** `SET ROLE` is reversible by the session user —
`SELECT set_config('role','none',true), query_to_xml('select … from users', …)`
resets to the owning superuser and runs arbitrary SQL via SPI, so `SET ROLE`
was never a boundary (BRY-285). Granting `brygge_dev_ro` membership to `brygge`
re-opens the same hole.

## When to add a new invariant

When you fix a bug that traces back to "we didn't explicitly say X must hold," add an invariant here. The doc is append-only — invariants don't get retired, they get tightened.

The format is:

```markdown
### One-line statement

**Rule:** Concrete description of what the code does to enforce it. Name the enforcing function/middleware/index so the next person knows where to look.

**Failure mode:** What goes wrong if you violate it. Specific symptom > abstract concern.
```

Keep failure modes specific — "data corruption" is too abstract for an agent to recognize. "Two invoices with the same KID; bank can't tell them apart" is concrete enough that pattern-matching it during review actually catches the bug.
