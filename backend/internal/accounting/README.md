# `accounting/` — GL, bank import, Vipps reconciliation, faktura sync

The double-entry GL plus everything that posts to it: bank statement parsing, KID matching, Vipps payout reconciliation, the Stripe balance mirror, faktura booking at send/void time (with a repair sync), momskompensasjon reports, kontoplan seeding.

## The Vipps reconciliation cascade

When a bank row matching `Utb. NNN Vippsnr MMM` arrives, the reconciliation pulls the matching payout + all `belastning` + `fee` rows from the same booking date and proposes a balanced bilag. For each belastning, the classification cascade runs:

1. **Member + matching open invoice** → CR 1500 receivables + `LinkedInvoiceID` (so confirm calls `linkInvoicePayment` after posting and back-links `invoices.payment_id`). `findOpenInvoiceForMember` never offers an imported faktura whose receivable isn't in the GL by the charge date, and `ReconcileVippsConfirm` re-checks every `LinkedInvoiceID` the same way rather than trusting the preview (`ErrImportedNoOpeningBalance`, BRY-386)
2. **Amount → price-article** (`matchVippsAmountToPriceArticle`) → CR the category's account from `RevenueAccountOrFallback`, only for a single-unit match (an exact price, or one night/day/hour); an amount that fits only as N nights falls through. The legacy human preview therefore shows no multi-unit suggestion either
3. **Member resolved, no clear classification** → CR 1500 receivables (treasurer reconciles manually)
4. **Fallback** → CR 3900 `fallbackRevenueCode` (Andre inntekter)

**Order-linked charges (per-charge model, BRY-337).** An ePayment charge (faktura pay link, QR checkout) carries our merchant reference (`chk-…`) as the row's `order_id`. `AutoReconcileOrderCharges` books it from the order itself, with no amount or name guessing: DR clearing / CR 1500 for each faktura in `order_sources` (with the `linkInvoicePayment` back-link), and CR the category revenue account for each catalog line (`resolveOrderChargeSplit`). It refuses if the order total and the charge differ, if a faktura on the order is already paid, voided, credited, a credit note or has a booked row recorded against it, or if one is imported without its receivable in the GL by the charge date (`ErrImportedNoOpeningBalance`); those are reported in `skipped_details`. `AssignVippsChargeToOrder` books in one transaction that resolves the split, locks the order's fakturas in id order (`lockInvoicesForManualAssign`: `lockInvoicesTx`, then `lockInvoiceForAssign` in `lockManual` mode per faktura, dated by the charge), then runs `checkOrderChargeSplit` (`charge_posting.go`, which Stripe charges go through too) and the posting on that transaction; the payment back-links run after the commit. It takes no order or attempt lock, so the fakturas-first order of the settle paths holds. It runs from **Synk Vipps**, an operator Report API sync, and CSV upload. The nightly Report sync only repairs row types, because journal entries need a human `created_by`. Like every Vipps posting, the entry is posted on creation (BRY-339).

**Auto-assign (per-charge model, BRY-340).** After order-linked charges, `AutoAssignVippsCharges` (`vipps_auto_assign.go`) books the rest of the queue when the outcome is unambiguous and the club has opted in (`clubs.vipps_auto_assign`):
1. `member_invoice`: a strong member match (`resolveCustomerToMemberPass` up to `memberPassFirstLast`; a name two members share is never strong) where `decideMemberInvoice` (`auto_assign_member.go`) finds the member's single open faktura — issued by the charge date, nothing booked against it, not imported, total equal to the øre — goes through `AssignVippsChargeToInvoice`.
2. `price_item`: `priceArticleCandidates` in one category, or a cross-category tie resolved by `clubs.vipps_auto_assign_tie_category` (only when every match is a per-night/day/hour price; an exact one-off price in any tied category leaves it manual), and the chosen category has a single-unit candidate (multiplier 1), goes through `CreateVippsChargeBilag` to `RevenueAccount(category)`; a category the map does not know is left for review, never booked to the fallback. Members-only items also need a strong member match. The candidates are shared with the Lag bilag suggestions (`priceItemAccountSuggestions`), but auto-assign additionally requires a single-unit candidate: an amount that fits only as several nights (2,700 = 9 × 300) is left with the reason `amount only fits as several nights (9x …)`, so the tie rule only ever settles single-unit amounts. The suggestions keep the multiple, scored `svak`.

Everything else stays in Tildel; the result reports `assigned` and `needs_review`. It runs where `AutoReconcileOrderCharges` runs. `UnassignVippsCharge` undoes any charge booking in one transaction: it voids a posted entry (or deletes a draft), clears the row and reopens the faktura recorded in `vipps_import_rows.invoice_id`; a closed period or a failed void rolls all of it back. A posted booking whose settlement has a posted clearing is refused (`ChargeInClearedSettlementError`, 409 `charge_in_cleared_settlement`): angre the settlement's deposit first (see "Common misses").

**Payout clearing (per-charge model, BRY-340).** `ClearReadyVippsPayouts` (`vipps_payout_sweep.go`) runs Stage 2 without a human: every unbooked, undismissed bank row matching `Utb. NNN Vippsnr MMM` goes through `ClearVippsPayout`, which posts the fee entry (DR 7700 / CR clearing) and the bank entry (DR bank / CR clearing) once no `belastning` with the payout's MSN + booking date is still unbooked and undismissed. It runs at the end of `BankSync`, after auto-assign in every Vipps path that has an acting user (CSV upload, operator Report API sync, **Synk Vipps**), and after a `PostVippsDraftBacklog` apply. The result splits settlements into `cleared`, `waiting` (charges not posted: in Tildel, a draft or a voided entry), `skipped` (a deposit naming an unimported or already-cleared settlement, two settlements on one MSN + booking date, or an imported payout with no open deposit carrying its reference) and `failed` (deposit ≠ net payout to the øre, a period that is not open, a concurrent clear), each with a Norwegian reason; unknown errors get a generic reason and are logged. Already-linked deposits are never candidates, so a re-run is a no-op. Sync and import paths call `ClearReadyVippsPayoutsReported`, so a sweep failure lands in the result's `error` instead of failing work already done. On the legacy model the sweep returns empty; `syncVippsReconciliations` owns those payouts. The manual `POST /bank-rows/{rowID}/clear-vipps-payout` stays for a single row. A clearing is one transaction holding the settlement's payout rows `FOR UPDATE` (`lockSettlementPayoutsTx`), so it posts the fee and bank entries together or not at all, and a concurrent unbook or rebook of one of its charges queues on the same lock. It counts a charge as booked only when its entry is posted.

⚠️ **Never route to 2900.** The `vippsClearingAccountCode = "2900"` constant exists only for backwards-compat with legacy reports. New lines must land on 3900 — see [`../../../docs/developer/reference/invariants.md`](../../../docs/developer/reference/invariants.md).

## The Stripe balance pipeline

Card payments reach the books from Stripe's balance, not from the webhook: the webhook settles orders, the balance says what money moved. Three steps: ingest, the charge, fee and refund postings, and payout matching and clearing. Refunds and disputes are booked by the same pass (see "Card refunds" and "Card disputes" below).

**Ingest (`stripe_balance_sync.go`).** `SyncStripeBalance` reads the club's whole balance listing (`GET /v1/balance_transactions`, `expand[]=data.source`, 50 per page) from a cursor, then stores it oldest first. The cursor is the watermark in `stripe_sync_state` less three days, else the club's first Stripe payment attempt, else 30 days back. The watermark (the newest listed `created`) moves only after a run whose listing completed and whose rows and payouts were all stored; a failed page or row means the next run reads the same range again. Stored rows never move it, since a payout's members can be older than anything listed. Each transaction is upserted on `(club_id, balance_transaction_id)` with Stripe's `type` (`stripe_type`) and `fee_details`, and classified once:

| Reporting category | Status | How |
|---|---|---|
| `charge` | `unbooked` | `source.metadata.attempt_id` (else the PaymentIntent's metadata) names a `stripe` attempt of the club whose `round(amount * 100)` and currency equal the charge's; `attempt_id` and `order_id` are set |
| `charge` | `needs_review` | `no_attempt`, `amount_mismatch` or `currency`; a matched attempt is still recorded |
| `fee`, `payout`, `payout_reversal` | `unbooked` | — |
| `refund`, `refund_failure` | `unbooked` | `refund_request_key` from the source's `metadata.refund_request_key` (a UUID), for the pass to find the request |
| `dispute`, `dispute_reversal` | `unbooked` | — (the pass links the charge, `origin_txn_id`, when it books the row) |
| `other_adjustment` | `needs_review` | `unsupported_category` |
| anything else | `needs_review` | stored as `other_adjustment`, `unsupported_category` |
| any, not NOK | `needs_review` | `currency` |

A stored row is reclassified only while it is `needs_review` for an ingest reason (a failed PaymentIntent lookup is retried that way); `unbooked`, `booked` and `dismissed` rows, and rows held by the booking pass or by a person (`stripeHeldReviewReasons`: the pass's charge and refund reasons and `unassigned`), are skipped before any Stripe call, and the upsert's guard excludes the same list. Every payout named by a `payout` / `payout_reversal` row, every `pending` / `in_transit` payout and every paid automatic payout whose members were never listed is then refreshed (`GET /v1/payouts/{id}`) and upserted into `stripe_payouts`; its status never moves back. For an automatic payout, `GET /v1/balance_transactions?payout=` lists what it paid out, once: members not seen yet are inserted (classified the same way), all get `payout_id`, and `members_listed_at` records that membership is known (a payout's members are fixed when Stripe creates it). A manual payout is recorded without members, since Stripe cannot list them. A `failed` or `canceled` payout releases its members (`payout_id` → NULL) unless it is already cleared in the books. The payout's own rows keep their link. Per-row failures land in the result's `errors`; only a failed list call fails the sync.

Triggers: the nightly job in `cmd/api/main.go` (at startup and every 24 h, when Stripe and accounting are on), `POST /accounting/stripe/sync` (treasurer/admin with fresh TOTP, audited `accounting.stripe_balance_synced`) and the `payout.paid` / `payout.failed` / `payout.canceled` webhooks (`IngestStripePayout` for that payout, in the background after the event is answered, bounded at 2 minutes). Only the endpoint books (below): journal entries need a human `created_by`, so the cron and the webhooks only ingest.

Concurrency: one Stripe ingest or booking pass runs per club at a time (`Service.stripeSync`, in process). The nightly job and the webhook wait for it; the endpoint uses `TrySyncAndBookStripeBalance` and answers 409 instead of queueing. Every ingest write is still one upsert or guarded update outside a transaction, with no database lock held across a Stripe call, so a second API process stays correct, only duplicating work.

**Charge and fee postings (`stripe_postings.go`).** `BookStripeBalance(ctx, clubID, actorID)` books every ready row oldest first (`created_at`): `unbooked` charges with an order, fees, refunds, refund failures, disputes and dispute reversals, in NOK, plus charges, refunds and disputes the booking pass itself held for review on a reason it retries (`stripeBookingReviewReasons`, never `unassigned`). Oldest first means a charge books before a refund of it in the same run. Each row is booked in its own transaction: lock the row (`FOR UPDATE`), then the fakturas its order settles (`FOR NO KEY UPDATE`, in id order, as `lockInvoiceForAssign` does), check, create, mark with `UPDATE … SET journal_entry_id, status = 'booked' WHERE … journal_entry_id IS NULL AND status = 'unbooked'`, post, commit; `linkInvoicePayment` runs after the commit. A lost mark or a failed post rolls the whole row back, so nothing is left to unwind, and every statement runs on that transaction (`existingPeriodIn`, `stripeAccountsIn`, `resolveOrderChargeSplitByOrderID`, `checkOrderChargeSplit`, `postChargeTx`).

| Row | Entry (`source = 'stripe'`, `source_table = 'stripe_balance_transactions'`) |
|---|---|
| charge | "Kortbetaling ordre <first 8 of order id>": DR `stripe_clearing_account` (1580) `amount_ore`; CR 1500 per faktura in `order_sources`, CR the category revenue account per order line (fallback 3900); DR `payment_fee_account` (7700) / CR 1580 `fee_ore` (omitted when 0) |
| fee, amount < 0 | "Stripe-gebyr <stripe_type>": DR 7700 / CR 1580 \|amount\| |
| fee, amount > 0 (a fee Stripe returned) | DR 1580 / CR 7700 |
| payout (`source_table = 'bank_import_rows'`, `source_id` = the deposit; `stripe_payout_clearing.go`) | "Stripe-utbetaling (ankomst dd.mm.yyyy)", on the bank date: DR the import's bank account (1920 by default) / CR 1580, the payout amount |

- **Booking date.** `created_at` converted to `time.Local` (`stripeBookingDate`). The API process runs with the host's zone, which the NixOS host sets to the club's timezone (`time.timeZone` in `nix/host.nix`), so a payment just after midnight lands on the payer's day. A host in another zone books on that zone's day.
- **Closed or missing period.** The period is looked up with `existingPeriodIn`: Stripe booking never creates a fiscal year (the Vipps order path, through `resolvePeriod`, still does). A booking date in a `closed` or `locked` period, or in no period at all, leaves the row `unbooked`: it is listed in the result's `deferred` (reason `period_closed` or `no_period`) and logged, and the next pass retries it. No draft is ever created.
- **Held for review.** A charge whose split `checkOrderChargeSplit` refuses goes to `needs_review` with `split_mismatch`, `receivable_not_open` or `imported_no_opening_balance`, and no entry. Ingest never reclassifies those rows; the booking pass retries them, so an opening balance posted later (or a corrected order) books the charge on the next run. The result's `needs_review` therefore re-counts every held charge on each pass, and each pass briefly locks the fakturas of every held charge while it re-checks them.
- **Never** writes `orders.status`, `online_paid_at` or a faktura's paid state; the only faktura write is `linkInvoicePayment` after the commit.

Actor paths: the sync endpoint (ingest, then booking, then the payout sweep, as the caller; the response is the ingest result plus `booking` and `payouts`, and the audit row carries both counts), `BankSync` (last pass, `stripe_booking` and `stripe_payouts`) and `ImportBankRows` (after auto-assign, as the importing user; both reimports too). The bank paths call `BookStripeBalanceReported`, which books and then sweeps in one hold of the club's slot, never fails the bank work (a failure sets `error`), returns nil results when nothing waited, and stands aside with `busy` (and no sweep) while a Stripe sync holds the slot instead of waiting for it. `GET /accounting/stripe/review` (`ListStripeReview`) lists every row in review with its reason; the UI reads the paged `GET /accounting/stripe/transactions` below instead.

**Manual actions (`stripe_manual.go`, `stripe_unassign.go`).** A person settles what the pipeline leaves in `needs_review`, and undoes a booking. Which actions a row allows is decided on the server (`stripeAllowedActions`), returned per row as `allowed_actions` by `GET /accounting/stripe/transactions?status=needs_review|dismissed|booked&limit=&offset=` (every accounting role; `shared.PaginatedResponse`, newest first, amounts in kr; a booked row also carries `journal_entry_id`, `journal_entry_number`, `journal_entry_description`, `journal_entry_status` and `invoice_numbers`, the fakturas it settles) and re-checked under the row's lock by every action:

| Row | Allowed |
|---|---|
| charge, `no_attempt` / `amount_mismatch` / `split_mismatch` | `assign_invoice`, `assign_account`, `dismiss` |
| charge, `receivable_not_open` / `imported_no_opening_balance` | `assign_account`, `dismiss` |
| any row not in NOK, or `review_reason = currency` | `dismiss` |
| dispute / dispute reversal, `dispute_account_missing` | `dismiss` (the pass retries it) |
| refund / refund failure, `refund_unlinked`, `refund_origin_dismissed`, `refund_split`, `refund_failure_settled`, `refund_failure_reissued` | `assign_account`, `dismiss` |
| refund / refund failure / dispute / dispute reversal, `refund_legacy` | `rebook`, `dismiss` |
| refund / refund failure, `refund_charge_unbooked` | `dismiss` (the pass retries it) |
| `other_adjustment`, `unsupported_category` | `assign_account`, `dismiss` |
| `dismissed` | `undismiss`, unless its payout is cleared in the books |
| `booked` charge, fee or adjustment whose entry is its own | `unassign`, unless its payout is cleared in the books |
| charge held as `unassigned` | `rebook` (with an order), `assign_invoice`, `assign_account`, `dismiss` |
| fee, refund, refund failure, dispute or dispute reversal held as `unassigned` | `rebook`, `assign_account`, `dismiss` |
| other row held as `unassigned` | `assign_account` (an adjustment), `dismiss` |
| `unbooked`, payout rows, fee rows in review otherwise | nothing (the booking pass and the payout clearing own them) |

- **Assign to faktura** (`POST …/transactions/{txnID}/assign-invoice {invoice_id}`, `AssignStripeTxnToInvoice`): one transaction locks the row, then the faktura (`lockInvoiceForAssign`, `lockManual`, the row's booking date); the charge must equal the faktura total to the øre (else `amount_mismatch`: book it to an account); a card charge takes exactly what was asked, and the candidate list below is exact too, so server and UI agree. "Kortbetaling: faktura <nr>": DR `stripe_clearing_account` / CR 1500 the charge, DR payment fee / CR clearing the fee (omitted at 0), through `chargePosting` / `postChargeTx` with a manual mark that also sets `invoice_id` in the same guarded statement (`status IN ('unbooked', 'needs_review')`), `linkInvoicePayment` after the commit. `GET …/transactions/{txnID}/potential-invoices?q=` lists the assignable fakturas (`assignableInvoiceSQL`) of exactly the charge's amount (`potentialInvoicesByAmount`, the bank-row query without a bank payer to resolve). A credited faktura is refused as `invoice_credited` (`ErrInvoiceCredited`) and a credit note as `invoice_not_debt` (`ErrInvoiceNotDebt`); voided stays `invoice_settled`.
- **Assign to account** (`…/assign-account {account_code, note}`, `AssignStripeTxnToAccount`): "Kortbetaling — <note>" (a charge) or "Stripe-justering — <note>" (anything else; the Stripe id when there is no note). Money in: DR clearing / CR the account; money out: DR the account / CR clearing; the fee DR fee / CR clearing (reversed for a negative fee), so clearing keeps the row's net. The account must be active and not 1500, 2900, the Stripe or Vipps clearing account, 19xx or a bank account the club imports to or has in `club_bank_accounts` (`invalid_account`); `GET /accounting/stripe/assignable-accounts` lists the rest.
- **Dismiss / undismiss** (`…/dismiss {reason, note}`, `…/undismiss`): reasons `booked_manually`, `test_transaction`, `unidentifiable`, `refund_or_credit`, `duplicate` (`IsValidStripeDismissReason`; never the bank-only reasons), stored with the note as `<reason>: <note>` in `dismissed_reason`; the review reason stays. Nothing is posted, but the payout that carried the row counts it as done and still takes its net off clearing, so 1580 is off by that net until it is booked another way (use `booked_manually` after a ledger entry). Dismissing twice changes nothing. Undismiss returns the row to `needs_review` with its reason (`unbooked` without one, for the next booking pass) and is refused (`payout_cleared`) once the payout is cleared, since that clearing counted the row as done. Ingest leaves dismissed rows alone, so a re-sync never undoes a dismissal.
- **Shared.** Every action needs the money gate (treasurer/admin + fresh TOTP), runs in the club's Stripe slot with the manual clearing's bounded wait (409 `busy`), and in one transaction that does everything through it. A refusal is `*StripeTxnRefusal` → 409 with `code` (`not_allowed`, `amount_mismatch`, `invoice_settled`, `invoice_credited`, `invoice_not_debt`, `period_closed`, `already_booked`, `payout_cleared`, `invalid_reason`, `invalid_account`, `use_bank_unassign`, `refund_booked`, `credit_note_issued`, `faktura_settled_since`) and a Norwegian `reason`. Unlike the booking pass, a manual booking may open the fiscal year (`resolvePeriodIn`): a person chose to book on that date. The two manual Stripe paths differ here on purpose: manual payout clearing (`ClearStripePayoutManually`) shares the sweep's transaction and its `existingPeriodIn`, and books on the bank date of a deposit that is already in the books, so its year exists unless something is wrong; a manual row assign books on the card payment's own date, which can precede the first bank import of a year. A row whose payout is cleared in the books is never assigned (and never undismissed): that clearing already took its net off clearing, so a booking would add it a second time (`payout_cleared`); it may only be dismissed. A manually booked row keeps its `review_reason`, which marks it as booked by hand (see "Already booked" below). Audited `stripe_txn.assigned_invoice`, `stripe_txn.assigned_account`, `stripe_txn.dismissed`, `stripe_txn.undismissed`, `stripe_txn.unassigned`, `stripe_txn.rebooked` (resource `stripe_balance_transaction`). The faktura assign's `linkInvoicePayment` runs after its commit but inside the slot, so an unassign never runs between the two.
- **Unassign** (`POST …/transactions/{txnID}/unassign`, `UnassignStripeTxn`): any booked row whose entry is sourced to it (a charge or fee the pass booked, a manual assign). One transaction locks the row, then the fakturas the entry settled (`stripeSettledInvoiceSQL`: `invoice_id`, plus the order's `order_sources` fakturas only for a row the pass booked, i.e. `review_reason` NULL), voids the entry (`voidJournalEntryTx`, reversal in its own period), reopens each faktura with `reopenInvoicePaymentTx` (the bank and Vipps unassigns' helper: `payment_id` cleared, the payment deleted) and sets the row `needs_review` / `unassigned` with no entry and no `invoice_id`. `online_paid_at` is left: the money did arrive, and the marker keeps the faktura off bank and Vipps matching while the row is held. Refused: `use_bank_unassign` (a payout row: undo its deposit in Tildel), `payout_cleared` (undo the payout's deposit first), `period_closed` (the entry's period), `not_allowed` (not booked, or the entry is not the row's), `refund_booked` (a charge with a booked refund: undo the refund first). An entry voided already is tolerated (no second reversal; `already_voided`). Refunds and refund failures follow their own rules (`stripe_refund_unassign.go`, "Card refunds" below).
- **Held rows.** `unassigned` is a hold: ingest skips it and the booking pass never retries it, so nothing books the row again without a person. **Rebook** (`…/rebook`, `RebookStripeTxn`) puts a held charge with an order, a held fee, refund or dispute, or a refund or dispute held as `refund_legacy`, back to `unbooked` (guarded update) and runs the booking pass on that row at once in the same hold of the slot; it answers the outcome (`booked`, `needs_review` with the pass's reason, `deferred`, `failed`). A held row can also be assigned or dismissed like any row in review; booked by hand, it keeps `unassigned` as its manual-booking marker.
- **Never in the ledger.** `POST /accounting/journal/{entryID}/void` goes through `VoidLedgerEntry`, which refuses an entry with `source_table = 'stripe_balance_transactions'` (409 `stripe_entry`, pointing to the Stripe row): a ledger void would leave the row booked and its fakturas paid. It likewise refuses an entry a bank row or a Stripe payout points at (409 `bank_entry`: payout clearings and every Tildel booking are undone with `UnassignBankRow`); Vipps charge entries are refused only once the charge's settlement is cleared (409 `charge_in_cleared_settlement`); otherwise `UnassignVippsCharge` sends order-booked Vipps charges there.
- **Unbooked rows that will not book.** An `unbooked` row gets no manual action: it is the booking pass's. A charge whose booking fails outright (its order gone, the clearing or fee account missing or inactive in the chart, a database error) stays `unbooked`, and every pass reports it in the result's `errors` (`<balance transaction id>: <cause>`; the Synk Stripe, bank sync and bank import results show the count, and the log has the text), while its payout waits ("kortbetaling venter på bokføring"). Resolve the cause (add or reactivate the account, `stripe_clearing_account` / `payment_fee_account` in economy settings) and run Synk Stripe again. A deferral for a missing or closed period is not an error: it is listed in `deferred` and books once the year is opened. A charge whose order cannot be fixed has no in-app path yet; file it rather than editing the row by hand.

**Payout matching and clearing (`stripe_payout_clearing.go`).** `ClearStripePayouts(ctx, clubID, actorID)` first plans without writing (`planStripePayouts`), then clears what is ready, one payout per transaction. The result splits payouts into `cleared`, `waiting`, `skipped` and `failed`, each with a Norwegian reason, like the Vipps sweep.

- **Candidates.** Payouts that are `paid`, in NOK and not cleared (`journal_entry_id`, `bank_row_id` NULL). Deposits are incoming bank rows that are unbooked, undismissed, not refund-paired, not provisional and not a Vipps settlement, whose description or counterpart matches the club's `stripe_payout_descriptor` (`providerPayouts`, in Go). Every such deposit is read, so one no payout matches is reported (`skipped`, "ingen Stripe-utbetaling …") instead of waiting in Tildel unexplained.
- **Match.** Same amount to the øre, bank date from one day before Stripe's `arrival_date` to three days after. Only one-to-one pairs go on: a payout two deposits fit is `skipped` ("flere bankrader passer"), a deposit two payouts fit skips both ("flere Stripe-utbetalinger passer"). Manual payouts take part in the matching, then are `skipped` ("manuell utbetaling – avstem manuelt"). A payout with no deposit yet is `waiting` with the amount and window it looks for.
- **Readiness.** Members listed (`members_listed_at`, else `waiting`, "kjør Synk Stripe"); members (rows with its `payout_id` other than `payout` / `payout_reversal`) summing by `net_ore` to the payout (else `skipped`); every member `booked` or `dismissed` (else `waiting`, listing card payments, fees, refunds/disputes and other rows still open); the bank date's period existing and open (`existingPeriodIn`, else `waiting`).
- **Clearing.** One transaction: lock the bank row, then the payout, then the members `FOR SHARE`; re-check the match and readiness; create the entry; link the bank row (`auto_matched = true`) and the payout with guarded updates; mark the payout's own `payout` balance row `booked` with the entry (it is Stripe moving the money out of the balance, so the clearing is its booking; it never blocks a clearing); post; commit. Everything runs on the transaction. A clearing that finds the row or payout taken reports nothing, as the Vipps sweep does with a concurrent clear. After the commit the 1580 movements of the members' entries and the clearing are summed, and a non-zero remainder (a dismissed member) is logged as a warning.
- **Tildel.** The unmatched list marks each payout deposit `provider_payout` (`vipps` / `stripe`, with `vipps_payout` kept) and, for Stripe, `provider_payout_reason`: what the next sweep would say (`stripePayoutRowReasons`, or "klar – avstemmes ved neste synk"), and `provider_payout_by_hand` when no sweep will clear it (`skipped`: manual, ambiguous, members not adding up, no payout). An undismissed Stripe deposit offers no faktura or account suggestions and no selection: a faktura assign would credit 1500 a second time and the payout would never clear, and the single-row account picker offers only revenue accounts. The four manual assigns refuse it on the server as well (409 `provider_payout`, Vipps settlements too). A by-hand row offers **Avstem mot Stripe-utbetaling** (the manual clearing below; a fresh TOTP is asked for before the picker opens) and, for a deposit that is not a payout at all, **Avvis** (preset to `internal_transfer`).
- **Manual clearing (`stripe_payout_manual.go`).** `ClearStripePayoutManually(ctx, clubID, actorID, payoutRowID, bankRowID)` books the pair a person picked with the sweep's own transaction (`clearStripePayout`, `manualStripeClear`), dropping only what served to find the pair: an automatic payout, the date window, and members adding up to the payout. It is the escape hatch for a manual payout and for a payout carrying a failed payout's funds (BRY-460), whose members do not net to it. Still required: an eligible deposit carrying the descriptor (re-checked under the lock), the amount to the øre, a paid uncleared NOK payout, every member booked or dismissed, an existing open period. So that "every member booked" is not vacuous, an automatic payout needs its members listed, and a manual payout needs every balance row that could have funded it (no `payout_id`, available by its arrival) booked or dismissed (`countOpenUnlinkedStripeRows`, `FOR SHARE` in the transaction). Refusals are `*StripeClearRefusal` with a code (`not_stripe_deposit`, `bank_row_not_eligible`, `amount_mismatch`, `payout_not_clearable`, `members_open` with the open count, `members_not_listed`, `balance_open` with the open count, `no_period`, `period_closed`); it waits up to `manualClearSlotWait` (5 s) for the club's Stripe slot, then returns `ErrStripeSyncBusy`. The result carries the members' net and the clearing account remainder (`clearing_balance_ore`), non-zero when the members do not net to the payout and omitted for a payout without members. The picker's list carries `open_balance` per manual payout. The deposit is linked with `auto_matched = false`. API: `GET /accounting/stripe/payouts?cleared=false` (every accounting role) and `POST /accounting/stripe/payouts/{payoutID}/clear` `{bank_row_id}` (money gate), audited `stripe_payout.cleared`.
- **Skipped deposits repeat.** A Stripe deposit no payout matches, or one matched to a manual payout, is reported `skipped` on every sweep until it is cleared (by hand, above) or dismissed.
- **Unassign releases the payout.** `UnassignBankRow` on a cleared deposit voids the clearing entry and, in the same transaction (`releaseStripePayoutTx`), sets the payout's `bank_row_id` / `journal_entry_id` back to NULL and its own `payout` balance row back to `unbooked`, so the next sweep clears it again with a new entry (or reports why not).

## Card refunds

`stripe_refunds.go`, `refund_credit_note.go`, `stripe_refund_unassign.go` (BRY-446; decisions ACC-1, ACC-2, ACC-5, ACC-8, ACC-9 in [`docs/adr/accounting.md`](../../../docs/adr/accounting.md)). A refund or refund failure is booked by the booking pass once Stripe's balance lists it, in the row's transaction: lock the row, find what it books against (a refund's charge by `charge_id`, a refund failure's refund by the refund id) and record it in `origin_txn_id`, lock that row (`FOR UPDATE`, read in a second statement), then the charge, then the fakturas in id order. Everything runs on the transaction, documents included; each case runs under a savepoint, so one that cannot divide the refund exactly rolls back and holds the row as `refund_split`.

| The charge the refund books against | What is booked |
|---|---|
| not stored yet | held, `refund_unlinked` (retried) |
| dismissed | held, `refund_origin_dismissed` |
| booked from its order by the pass, or assigned to a faktura by hand | credit notes, or a recollect (below); "Kortrefusjon …": DR 1500 / CR 1580, fee lines if any |
| booked to an account by hand | "Kortrefusjon …": DR that account (the charge entry's credit line) / CR 1580 |
| held as `receivable_not_open`, `amount_mismatch` or `no_attempt`, and this refund returns all of it (a duplicate capture) | the pair: the charge "Dobbel kortbetaling …" DR 1580 / CR `stripe_suspense_account` (default 2900) with its fee, on its own date; the refund DR suspense / CR 1580. The charge keeps its review reason, so it settles nothing. Audited `stripe_txn.duplicate_refunded` |
| unbooked, or held for anything else | held, `refund_charge_unbooked` (retried) |

- **Targets.** The fakturas `stripeSettledInvoiceSQL` names for the charge (read before anything is detached), plus, for a charge the pass booked from its order, the order's catalogue lines as one target. They must add up to the charge and none may be voided or credited by hand since, else `refund_split`.
- **The request.** The refund's `payment_refunds` row (written by the refund button, `POST /admin/orders/{orderID}/refund`, and kept current by the refund webhook; see [`docs/developer/payments.md`](../../../docs/developer/payments.md#refunds)) is found by Stripe's refund id, else by the request key (`refund_request_key`); a refund with none (a Dashboard refund before its webhook) gets one made from the row (`created_by` NULL, reason "Stripe Dashboard"), when the charge names its attempt. Its `outcome` decides a full refund: NULL or `credit` credits, `recollect` collects again.
- **Credit** (a partial refund, or a full one with `credit`): `allocateRefund` divides the refund over the targets, in proportion for a partial (the remainder on the last) and as each target's uncredited rest for the refund that completes the charge, so partials add up to each total to the øre. Each target gets a credit note (`issueRefundCreditNoteTx`): the faktura's lines (or the order's) with each exemption folded into its item line (fully exempt pairs drop out), negated and scaled to its share (remainder on the largest line), sub-described "Kreditnota for faktura <nr> – refusjon kortbetaling <dato>", to the same payer (a guest's name and email; no email means PDF only), issued and due on the refund's booking date, marked sent, booked through `bookInvoiceEntryTx` (DR revenue / CR 1500) and queued for delivery. A `refund_documents` row (`credit`) links it to the faktura. The faktura keeps its payment and online marker; `finance.CreditedSQL` reads it as credited once its refund credit notes add up to its total. A full refund turns the order `refunded` (a booking the order paid for would be cancelled here; no checkout creates one, BRY-499).
- **Recollect** (a full refund with `recollect`, only with no earlier credit for these fakturas and no catalogue lines, else `refund_split`): no credit note. Each faktura's payment is unlinked (`reopenInvoicePaymentTx`), its online marker cleared and its `order_sources` row to the refunded order deleted (`detached_order_id` on its `recollect` document; only for a charge the pass booked from its order, so a faktura on another order keeps that link, and the order is refunded only in that case); the charge gets `recollected_at`, so it settles nothing any more; the order turns `refunded`. The faktura is an ordinary open faktura: reminders, a new pay link (a new order) and bank KID matching all apply.
- **Refund failure** (the money came back): the refund's entry mirrored, "Mislykket kortrefusjon …" DR 1580 / CR the account the refund debited, and by the refund's documents: per `credit` document a new debit faktura (`issueRefailInvoiceTx`: the credit note's lines with the sign flipped, "Ny faktura etter mislykket refusjon <dato>"), booked, settled in the same transaction (`linkInvoicePaymentIn`) and recorded as `refail_invoice`, the order back to `paid`; per `recollect` document the faktura settled again if it is still open (payment linked, online marker restored, the unpaid replacement order failed, the charge no longer recollected), else the failure waits as `refund_failure_settled`; a `credit` document whose faktura was issued again with "Ny faktura" (`reissued_as_invoice_id` set, new faktura not voided) holds the failure as `refund_failure_reissued` with nothing written, since the debit faktura would bill the payer twice. Credit notes are never voided (ACC-9). A failure of a duplicate pair or an account booking is the mirror alone. `refunded_ore` on the charge goes back down (only for refunds the pass booked).
- **Delivery.** Every document is queued in the booking transaction as a `deliveries` row (kind `invoice_refund_document`, email empty for none); the delivery worker (`handlers.RefundDocumentSender`) renders and stores its PDF and emails it after the commit, never under the pass's locks or the Stripe slot. The worker and this sender are registered whether or not SMTP is configured (the worker rule: a kind's rows are only created where its sender exists); without SMTP the row is done once the PDF exists, so enabling mail later never sends old credit notes. A send that keeps failing is a `failed` delivery row.
- **Unassign.** A refund that issued credit notes, or a failure that issued a debit faktura, is refused (`credit_note_issued`); a charge with a booked refund is refused (`refund_booked`); a refund with a booked failure is refused (`not_allowed`). A pair or account refund is undone by voiding its entry. A recollect refund is undone only while every faktura it reopened is still open (`faktura_settled_since`), and undoing it settles them again as a failure would (payment and online marker restored, the replacement order failed, the faktura's `order_sources` link moved back to the refunded order, which is paid again) and deletes its documents. A refund failure and its unassign move `refunded_ore` only if the refund itself counted in it (the pass booked it, `review_reason` NULL).
- **Audit.** `stripe_txn.refund_booked` per refund or failure, `invoice.refund_credit_issued` per credit note, after the commit, as the pass's acting user.
- **Ny faktura** (`refund_reissue.go`, BRY-498, ACC-8). After a refund credited a faktura in full the treasurer collects again with `Service.ReissueAfterRefund`: it locks the credited faktura (`FOR NO KEY UPDATE`), refuses (`ReissueRefusal`) when `ReissueEligible` fails (credit documents equal the total and no `refail_invoice`; the list's `can_reissue` uses the same function) with `not_refunded`, or when `reissued_as_invoice_id` names a faktura that is not voided with `already_reissued`, then creates a draft with the lines as issued (quantity and unit price kept; `foldExemptions` folds an exemption into its item, which becomes one unit of the net, and an exemption with no item is not copied), to the member as they are now (`useCurrentPayerTx`: current name and email, an organisation's recipient address kept), through `CreateInvoiceTx` (so under the numbering lock), and records it in `reissued_as_invoice_id`, all in one transaction. Sending and booking it is the handler's: the same path as a faktura made by hand (`InvoiceHandler.emailNewInvoice`). The credit notes are untouched. `finance.CreditedSQL` still reads the credited faktura as credited; the new one is an ordinary open faktura.

## Card disputes

`stripe_disputes.go` (BRY-446; decisions ACC-4 and ACC-5 in [`docs/adr/accounting.md`](../../../docs/adr/accounting.md)). A dispute is the card network taking a payment back from the Stripe balance, so the booking pass books the withdrawal as a loss when the balance lists it, and reverses it when Stripe gives the money back. `dispute` and `dispute_reversal` rows in NOK are ingested `unbooked` (other currencies are `currency`, dismiss only) and booked in the row's own transaction:

| Row | Entry (`source = 'stripe'`) |
|---|---|
| `dispute` | "Kortbetalingstvist …": DR the dispute account \|amount\| / CR 1580; DR 7700 / CR 1580 the dispute fee (`fee_ore`, omitted at 0) |
| `dispute_reversal` | "Kortbetalingstvist vunnet …": DR 1580 / CR the dispute account \|amount\|; the fee mirrored, only when Stripe returned one (a negative `fee_ore`: DR 1580 / CR 7700) |

- **The dispute account** is `clubs.stripe_dispute_account`, else 7830 "Tap på fordringer" (`stripeDisputeAccountCode`; in the default kontoplan and added to existing charts by migration 000120). It has no settings screen yet: it is set in the database, like `stripe_suspense_account`. An account that does not exist in the club's chart or is inactive holds the row as `dispute_account_missing`: retried by every pass (and left alone by ingest), only dismissable by hand. Add or reactivate the account and the next pass books it.
- **Direction and nothing.** The side follows the sign of the amount (negative: DR the dispute account / CR clearing; positive: the mirror), whatever the category's name. A dispute with a positive amount, or a reversal with a negative one, is held as `dispute_direction` (not retried; `assign_account`, `dismiss`). A row with no amount and no fee is marked `booked` with no entry, once, instead of failing every pass.
- **No booked charge is needed.** The charge row (same `charge_id`) is linked in `origin_txn_id` when it exists, for information only, and is not locked. The faktura, the order and `refunded_ore` are never touched: the member did pay, and whether to invoice again after a lost dispute is a board decision (ACC-4). A refund of a charge that was disputed books as any refund does.
- **Legacy rows.** Disputes held as `refund_legacy` by migration 000119 are handed back to the pass by migration 000120 (NOK, no entry, not dismissed, and not in a payout already cleared in the books); one left in `refund_legacy` can be rebooked or dismissed by hand. An unassigned dispute is rebooked, assigned to an account or dismissed like a fee.
- **Payout clearing** waits for an unbooked dispute ("tvist venter på bokføring") or one in review ("tvist til gjennomgang").
- **The webhook is a separate path.** `charge.dispute.*` events keep `payment_disputes` (the provider's state: status, deadline, the attempt) up to date and email `clubs.treasurer_email` once; booking never reads that table and the webhook never books. `payments.OpenDisputeForAttempt` is what a refund asks before it calls Stripe. See [`docs/developer/payments.md`](../../../docs/developer/payments.md).
- **Audit.** `stripe_txn.dispute_booked` per dispute or reversal, after the commit, as the pass's acting user.

## The bank-row KID matching cascade

When a bank import lands or `BankSync` runs (after provisional rows are refreshed or superseded; see Common misses):

1. Candidates are incoming rows passing `kidCascadeEligibleSQL` (unbooked, undismissed, not refund-paired; `kid_cascade.go`). Bank sync lists them with it; an import only sees its fresh inserts. Rejected-KID notices (`IsRejectedKIDDescription`, "ble ikke akseptert": the money never arrived) are skipped at import and sync alike and stay in Tildel. Extract KID from `bir.kid_number` (CSV column) or fall back to `ExtractKIDFromDescription`
2. Match invoice by KID among fakturas still owed (`finance.OwedByMemberSQL`: not voided, paid, Vipps-captured or credited); tiebreak by checking no other matched row already used the same KID. Any amount books: a partial KID payment marks the faktura paid (`linkInvoicePayment` records the faktura total), and a second payment with the same KID finds no owed faktura and is left in Tildel
3. If no KID match, try `ExtractInvoiceNumberFromDescription` + amount within 0.005
4. Only while `clubs.bank_auto_assign` is off: `findInvoiceByCounterpartAndAmount`, the member whose normalized full name equals the counterpart with exactly one owed faktura of that amount. With the switch on this step is skipped and the auto-assign rule below replaces it
5. If matched, `bookKIDCascadeMatch` books the row in a transaction of its own: lock the faktura (`lockInvoiceForAssign` in `lockKIDCascade` mode, which re-checks it is still owed and has nothing booked against it, by `invoice_id` or KID or a Vipps charge), create a balanced bilag (DR bank, CR receivables), link the row with an update guarded on `kidCascadeEligibleSQL` that records `invoice_id`, post, release the lock, and call `linkInvoicePayment` to back-link `invoices.payment_id`. Under the lock the row is re-checked first: if the booking it waited for was this row's own (a second sync, or an import during a sync), it is `errKIDRowTaken` and nothing is reported. A faktura found paid or booked under the lock is `errInvoiceSettled`: the row stays in Tildel and is counted in `KIDSkippedSettled` (on import also a `row_errors` entry). One voided or credited meanwhile is `errInvoiceNotOpen` (import: `row_errors` "faktura no longer open"; not counted). An imported faktura whose receivable isn't in the GL by the row date is `ErrImportedNoOpeningBalance`: the row stays in Tildel, not counted as settled (import: `row_errors` with the opening-balance message; sync: logged). The SELECTs above never offer an imported faktura today (empty KID), so this is a second guard. A period closed mid-run (`ErrPeriodClosed` from create or post) is reported like any closed period. Create, link and post share the lock transaction, so a lost link or a failed post rolls all of it back. A row `auto_matched` to an unposted draft can only come from builds that linked and posted separately; `BankSync` first releases such rows (KID drafts with a CR 1500 line, older than 15 minutes, clearing `invoice_id` too) so they match again
6. After the cascade, the backfill passes (`backfillUnlinkedPayments` by KID, `backfillInvoiceNumberPayments` by "Faktura NN") set `payment_id` on a faktura whose payment is booked but was never linked. They trust a row only when its entry is **posted** and has a **CR 1500** line. Voided entries keep `bank_import_rows.journal_entry_id`, and import auto-match links rows to drafts, so neither counts as payment. The KID pass also needs a non-empty KID and skips a row assigned to another faktura; the invoice-number pass reads a row's text only while `bank_import_rows.invoice_id` is NULL, so a row recorded against faktura B never pays faktura A because its description names A (BRY-415, BRY-417, BRY-523)

**Bank auto-assign (BRY-366).** After the cascade, `AutoAssignBankDeposits` (`bank_auto_assign.go`) runs at the end of `ImportBankRows` and as pass 4c of `BankSync` (before the Vipps payout sweep), club-wide, when the club has opted in (`clubs.bank_auto_assign`). A KID-less incoming row in an open period is booked to a faktura only when its payer (`Fra:` name, else counterpart) is not the club, resolves through `resolveStrongMember`, `decideMemberInvoice` settles it, it has no strong partner, and no other row in the run reaches the same faktura. Every other row is counted by reason in `by_reason`. Booking goes through `assignBankRowToInvoice` with `assignOpts{auto: true}`: the faktura is locked by `lockInvoiceForAssign` (`FOR NO KEY UPDATE`, so writes that only reference the faktura by foreign key don't queue behind it), which the manual, split-payment and Vipps assigns also take, and re-checked in a fresh statement, the entry is posted at once and records `invoice_id`, and `auto_matched` stays false. Booked imports get their `matched_count` recounted. Results ride on `ImportResult.AutoAssign` / `BankSyncResult.AutoAssign` (nil when off); hooks call `AutoAssignBankDepositsReported`, so a failure sets `error` instead of failing the import or sync. `PreviewBankAutoAssign` runs the same decisions as a dry run.

## Helper functions worth knowing

- `Service.linkInvoicePayment(ctx, clubID, invoiceID, paidAt)` — idempotent. Skips org-recipient invoices (no `user_id`), skips already-paid invoices, maps `invoices.category` → `payment_type`. Call after any GL posting that should also mark the invoice paid.
- `Service.matchVippsAmountToPriceArticle(ctx, clubID, amount)` — returns `(accountCode, label)` when exactly one active price-item matches the amount and matches it as a single unit. Its callers (the legacy cascade and resync) book without a human, so a match that needs a multiple is no match. `priceArticleCandidates` itself also returns integer multiples (2-60×) of per-time units, for suggestions.
- `referenceDateSQL(clubExpr, dateExpr)` — SQL predicate: the date falls in one of the club's reference years. Every queue, count and automatic pass that works on rows by date adds `NOT referenceDateSQL(...)`; the arguments must be table-qualified (`bank_import_rows.club_id`, not `club_id`), or the subquery resolves them to the fiscal period's own column and the predicate is always true. `notReferenceEntrySQL(je)` is the same for a journal entry (its period or its date), for passes that delete a draft and rebook it. `periodIsReferenceIn(ctx, q, clubID, periodID)` is the Go twin for a path that holds a period id; `bankAccountCodesIn` lists the club's bank GL codes (shared by the Stripe account exclusions and the expense-shape rule).
- `Service.resolvePeriod(ctx, clubID, date, override)` — always use this for "which fiscal period does this date land in?" Auto-creates a calendar-year period on demand (`ON CONFLICT DO NOTHING`, so a concurrent create neither fails nor aborts a transaction); respects `closed`/`locked` status. Inside a lock transaction use `resolvePeriodIn(ctx, tx, …)`.
- `Service.resolveCustomerToMember(ctx, clubID, customerName, message)` — fuzzy member match for Vipps payer names. KID-in-message first (it beats a taught alias; a KID and an alias naming different members are `memberPassConflict`, no member, and the charge stays for a human), then the alias, then normalized full-name, first+last (only when exactly one member carries the name), unique-last-name. `normalizeName` handles æøå + diacritics + hyphens + case. The name passes live in `matchMemberName` (`auto_assign_member.go`) over a member list loaded once (`loadMemberCands`).

## Invariants

- `posted` journal entries are immutable: the only write is `VoidJournalEntry` (original marked `voided` + a posted balanced reversal); never updated or deleted
- Every provider posting (Vipps charge, order split, auto-assign, fee, payout, legacy confirm; Stripe charge and fee) is posted on creation; a failed post unlinks its rows and discards the draft, except in a transaction holding a lock (a faktura assign, the legacy settlement confirm, the order-linked Vipps charge, a Stripe row), where it rolls back with the transaction
- A per-charge Vipps payout clears automatically (bank sync, Vipps sync, backlog apply) once every charge of its settlement is booked or dismissed; fee rows and the bank row are each linked with a guarded update, and a lost race unwinds instead of booking the fee twice
- `ClosePeriod` refuses while the period holds drafts (409 `period_has_drafts`, listed per source), except a reference period, whose drafts can never post; `DeleteDraftJournalEntry` removes an unlinked draft
- A reference period (`fiscal_periods.reference_only`) takes only expense-shaped entries (every line a cost or bank account, at least one cost line), and so does any entry dated in one: `createJournalEntryTx`, `postJournalEntryTx` and `voidJournalEntryTx` refuse the rest with `ErrReferencePeriod` (409 `reference_period`). Every GL write reaches that guard; `TestJournalWritesOnlyThroughTheGuard` keeps it so
- `closed`/`locked` fiscal periods reject create, post **and void** (`ErrPeriodClosed` → 409 `period_closed`); a void is refused, never moved to a later period. Writers hold the period `FOR SHARE`; `ClosePeriod` takes it `FOR UPDATE` before counting drafts
- Every function acting on a request id takes the club id and filters on it; a foreign id is not found (404)
- `UnassignBankRow`: one tx voids the posted entries (`voidJournalEntryTx`, so a closed period rolls it all back), clears the rows (incl. a transfer's other row), deletes drafts and reopens the faktura; retry-safe. For a row with no `invoice_id` (assigned before migration 000057) it recovers the faktura from the payment only when the entry credits receivables (1500); an account booking never reopens a faktura that happens to be paid the same day for the same amount
- Vipps belastning amounts are positive; fees are negative
- The Stripe sync watermark (`stripe_sync_state`) moves only after a complete, error-free run; nothing else (stored rows, payout ingests) sets the cursor
- The Stripe balance ingest posts nothing and never changes a `stripe_balance_transactions` row that is `unbooked`, `booked` or `dismissed`; only `needs_review` rows held for an ingest reason are reclassified, never those the booking pass or a person holds (`stripeHeldReviewReasons`). Stripe amounts are integer øre, signed as Stripe signs them (charges positive, fees, refunds and payouts negative)
- A Stripe row is booked (and marked `booked`) in one transaction that locks it, so two passes or two processes book it once; a closed period leaves it `unbooked` for the next pass, never a draft
- A Stripe row in review is booked or dismissed by a person only as `stripeAllowedActions` allows, in the club's Stripe slot and one transaction locking the row (then the faktura); a hand-booked row keeps its `review_reason`, a faktura assign records `invoice_id`, and a dismissed row's net stays off the clearing account's books until booked another way
- A card refund is booked only by the booking pass, against its charge (`origin_txn_id`), locking the refund, then the charge, then the fakturas; a refund credit note is issued, booked and queued for delivery in that transaction, linked through `refund_documents` (never `credits_invoice_id`), and never voided, linked or unlinked by hand; a refund failure issues a new debit faktura instead
- Every faktura is numbered through `NextInvoiceNumberTx` under the club's advisory lock; `(club_id, invoice_number)` is unique
- A Stripe entry is undone only from its row (`UnassignStripeTxn`; the ledger void refuses it, 409 `stripe_entry`, as it refuses a bank-linked entry, 409 `bank_entry`), in one transaction locking the row, then its fakturas, then the entry; the row is then held (`unassigned`), which neither ingest nor the booking pass ever touches
- A Stripe payout's deposit is booked (DR bank / CR Stripe clearing) only once its one matching deposit is found (or a person picked it) and every member is booked or dismissed, in one transaction locking the bank row, then the payout; a provider payout deposit is never booked by a mapping rule, auto-assign, a price-item suggestion or a manual assign (`providerPayouts`, `refuseProviderPayouts`)
- Bank rows with `journal_entry_id IS NOT NULL` cannot be reassigned without cascading `journal_lines`
- Reports and momskomp count `posted` **and** `voided` entries (`bookedEntryFilter`), so a void and its reversal net to zero
- KID auto-match (import and bank sync) posts as the importing user or discards its draft — never leaves an orphan; failures surface as `row_errors`. It never books a dismissed, refund-paired or rejected-KID row, and locks the faktura per row across link + post
- Payment-match entries are sourced to their row and described by `kidMatchDescription`; bank sync's stranded-draft heal keys on exactly that, never on mapping-rule drafts
- Manual bank-row assigns link the row (guarded) before posting; bilag numbers retry on a unique-key collision instead of failing
- **A charge in a cleared settlement is not unbooked on its own (BRY-555, ACC-11).** A posted charge is one DR on the clearing account (2900) that the settlement's fee and payout credits net against. `UnassignVippsCharge` and `VoidLedgerEntry` (on a charge entry) call `clearedSettlementOfChargeTx` (`vipps_cleared_settlement.go`), which locks the settlement's payout rows `FOR UPDATE` and reports the settlement when `postedSettlementClearing` holds (payout row or deposit on a **posted** entry); the refusal is `*ChargeInClearedSettlementError` (`ErrVippsChargeInClearedSettlement`; handlers: 409 `charge_in_cleared_settlement` with `settlement_number`, `msn`, `bank_row_id`). The way through is Angre of that deposit (`UnassignBankRow`: voids the payout entry, releases the deposit and payout row, keeps the fee entry), offered in the SPA as "Angre innbetalingen" (`ClearedSettlementRefusal.vue`); the sweep then clears the settlement again with a new payout entry. To change only what a charge books, use `rebookVippsChargeTx` (`vipps_rebook.go`): void or delete the old entry, post the replacement with the same clearing debit, relink, in the caller's transaction, payout clearing untouched. Only a posted entry is guarded; a draft is not in the ledger. `VoidLedgerEntry` on a charge entry releases the charge to the Vipps queue and reopens the fakturas it settled (`invoice_id` and its order's sources) in the same transaction, and refuses a settlement's fee or payout entry (`VippsSettlementEntryError`, 409 `vipps_settlement_entry`). A charge counts as booked for the clearing (`chargePostedSQL`) only when its entry is posted, and `PostVippsDraftBacklog` posts a settlement's fee and payout drafts only when all its charges are posted. A new path that unlinks a charge from a posted entry must take the same check in the same transaction as the unlink. `ClearVippsPayout` must stay one transaction that locks the payout rows first, or the check races it.
- A manual assign (bank row, split-payment, Stripe, Vipps) of a **credited** faktura is refused under the lock as `ErrInvoiceCredited` (`finance.CreditedSQL`, BRY-508), and of a **credit note** as `ErrInvoiceNotDebt`: the handlers answer 409 `{code: "invoice_credited"}` / `{code: "invoice_not_debt"}` (`invoiceNotAssignableConflict`), the Stripe assign the same codes in its refusal. A **voided** faktura is refused as `ErrInvoiceVoided` (409 `invoice_voided` on the bank, Vipps charge and legacy confirm routes; the Stripe assign keeps `invoice_settled`). The legacy `ReconcileVippsConfirm` locks and re-checks every faktura its lines link inside its booking transaction, in `lockManual` mode (voided, credit note, credited, paid, a booked row recorded against it, imported without an opening balance; `lockInvoicesForManualAssign`, each dated by its charge, else the bank row), and records the faktura on each charge's `invoice_id` in the same commit. It is the booking step of the settlement reconcile: the Vipps settlement's bank deposit becomes one entry (DR bank, CR per charge, DR fee), reached from `POST …/bank-rows/{rowID}/reconcile-vipps/confirm` (`HandleVippsReconcileConfirm`, the bank import view's Vipps reconcile), bank sync's Vipps pass and the backlog resync (`ResyncVippsBilags`, drafts with `post=false`). It refuses a faktura linked from more than one line, or credited above its total plus 1 kr (`ErrSettlementInvoiceOverpaid`, 409 `settlement_invoice_overpaid`), and a faktura-linked line that names no charge. It refuses a Vipps row that is already booked (`ErrVippsRowAlreadyBooked`, 409 `vipps_row_booked`). Undoing it is `UnassignBankRow` on the deposit, which releases the bank row, every Vipps row (charges, payouts, fees) and every faktura the charges recorded (`releaseVippsRowsTx`, also for a draft settlement) and reports the reopened fakturas and released rows to the audit; `UnassignVippsCharge` refuses a charge that shares its entry with a bank row (`ErrVippsChargeInSettlement`, 409 `charge_in_settlement`). A payment credits 1500 for an imported faktura only when `finance.ImportedReceivableOpenSQL` holds at its booking date (an opening balance on 1500 dated between the faktura and the payment, or the faktura's own `invoice_sync`). `lockInvoiceForAssign` checks it in `lockManual` and `lockKIDCascade` mode, which therefore need `invoiceLockOpts.bookingDate` (row date; multi-row: the earliest row; Vipps: the charge date); a zero date is refused. Refusal is `ErrImportedNoOpeningBalance`, mapped to 409 `imported_no_opening_balance` (BRY-386)
- A payer alias taught from Tildel is saved in the faktura-lock tx before the row is linked and posted; a payer that is another member's name or alias is `ErrAliasConflict` with nothing booked unless overridden
- Bank auto-assign books only on opt-in, never creates a fiscal period, never targets an imported faktura, and locks the faktura across link + post; while it is off the cascade's name+amount step still runs
- Matching incoming money to a faktura uses `finance.OwedByMemberSQL`; only ePayment order reconciliation and the manual-assign suggestion lists (`assignableInvoiceSQL`) use `finance.OpenReceivableSQL` (they book or offer captures the webhook already flagged)
- A role-exemption line books to its own `account_id` (the club's exemption expense account), so an exempt item books gross: CR revenue, DR expense. A zero-total faktura books with no 1500 line
- A faktura line without its own `account_id` books by the category stored on the line at issue (`finance.LineCategorySQL` in `invoiceRevenueCredits`), so re-categorising a price item never moves an issued faktura's revenue on a resync or resplit. `invoices.category` (mapped to `payment_type` by `linkInvoicePayment`) is likewise stored at issue; never switch either to the price item's current category
- A faktura is booked when sent and reversed when voided (`BookInvoice` / `ReverseInvoice`, which reverses the whole `invoice_sync` + `invoice_resplit` family or nothing); `SyncInvoices` only repairs what was missed. At most one `invoice_sync` entry per faktura (unique index). `SyncPayments` skips invoice-settling payments

Full list: [`../../../docs/developer/reference/invariants.md`](../../../docs/developer/reference/invariants.md).

## Common misses

- **A dispute books without a charge, a refund needs one.** `bookStripeDisputeTx` only looks the charge up for `origin_txn_id`; do not make it wait for the charge or lock it, since a dispute's money has left the balance whether or not Brygge stored the charge. The loss goes to the club's dispute account, never to 1500: the faktura stays paid.
- **Arkivref dedup.** `ImportBankRows` skips an incoming row whose bank reference another row already carries, before the hash insert. A provisional in-flight row (bare `Overførsel` on the export day) and its settled row usually share that reference, so the settled text would never land. The one exception is `refreshProvisionalByReference`, which updates the provisional row in place; keep its conditions narrow (see [invariants](../../../docs/developer/reference/invariants.md#a-provisional-bank-row-gives-way-to-its-settled-row)).
- **The statement's last day is `bank_imports.period_to`, not the latest surviving row.** An overwrite reimport deletes some of an older import's rows; deriving "the export day" from what survives turns a bare mid-statement row into a provisional one. Reimport paths record the full statement with `recordStatementPeriod` before importing a subset.
- **Rows booked together share one `journal_entry_id`.** A group booking (`AssignBankRowsToAccountGroup`, BRY-380) links 2–5 rows on one bank account to a single entry with one bank line for their net, and an intra-bank transfer links its two rows to one entry. Never assume one row per entry: unassign, reimport and reports must treat every row pointing at the entry as one booking (`UnassignBankRow` already releases them all).
- **A provider payout deposit has one booking test.** `providerPayouts` (`provider_payout.go`) decides, for every path that books or suggests bank rows on other evidence, whether a bank row is a Vipps settlement or a Stripe payout (the Vipps payout sweep and the Tildel `vipps` filter keep their own Vipps literals). A new such path must ask it, never its own `ILIKE '%stripe%'`, and never evaluate the Stripe descriptor in SQL: it is an RE2 pattern, and Postgres reads regular expressions differently. A new path that books a bank row a person names calls `refuseProviderPayouts` before taking any lock, on the assign's connection (its transaction where it has one), as the four manual assigns do.
- **Tildel has one row set, and the counts come from it.** `tildelScope` (`bank_row_queue.go`) is what the Tildel tab lists: the club's bank rows with no journal entry and, unless the `dismissed` kind is asked for, no `dismissed_at`, narrowed by kind and year. `ListUnmatchedBankRows`, `CountUnmatchedBankRows` (the sidebar and tab badge, and the number a board task reports) and `CountUnmatchedBankRowsByYear` (the year dropdown) all build their WHERE from it; a new filter or exclusion goes there, never into one consumer. What it deliberately leaves in: provider payout deposits (listed with `provider_payout`, because a person clears a Stripe one by hand and a Vipps one is a visible auto-clearing item) and provisional rows. What it leaves out without a clause of its own: refund-paired rows (pairing journals both) and pending refunds (dismissed, so they belong to the refund tab). That makes the Tildel count and `CountPendingRefunds` disjoint, so a badge may add them. Hiding payout deposits from the badge would take a Go filter, not SQL (`loadProviderPayouts` + `providerPayouts.is`), and the tab would have to hide them too, or the two disagree again. The Tildel tab also lists unreconciled Vipps charges (`ListUnreconciledVippsCharges`) when the club is on the per-charge model; the count does not include them.
- **Partner suggestions have one source.** `loadPartnerRows` + `scorePartner` feed `/partners`, the list's `partner_hint` and the 409 `has_partner` guard on assign-account; change the signals there, never in one consumer, or the list badge and the guard disagree. A known counterparty account number decides whether a row is the club's own transfer; the club-name test applies only when no account is known, because an inbound row's Motpart is often the club's own account label. Group refusals are exported sentinels (`ErrGroup*`); a group never books to a bank account or to receivables (1500).
- **Account suggestions for incoming money start from price items.** `rankAccountSuggestions` serves bank rows (`/bank-rows/{id}/suggestions`) and Vipps charges (`/vipps-charges/{id}/suggestions`). Its first pass reuses `priceArticleCandidates`, the same amount match auto-assign uses, and `priceItemAccountSuggestions` owns the rule (sannsynleg when every fitting item points at one account, else svak; members-only items need a known payer). Change the amount match in `priceArticleCandidates`, never in a consumer, or suggestions and auto-assign disagree. Members-only items are ignored entirely for an unknown payer, tooltip included. A provider payout deposit (Vipps settlement or Stripe payout, `providerPayouts`) gets no price_item pass (its amount is a sum of charges), and the description hints (`outgoingHints`, all expense accounts) run only for outgoing amounts, so a payer's message such as "Strøm" never offers an expense account for money coming in. A charge id that is not the club's, or is not a uuid, answers 404 (`ErrVippsChargeNotFound`; `vippsChargeIDParam` in the handler). Every list that offers fakturas for a manual assign (`potentialInvoicesByAmount`, `rankIncomingInvoices`, the `suggestion_count` of the Tildel and Vipps queues) filters on `assignableInvoiceSQL` (`bank_row_reconcile.go`): `finance.OpenReceivableSQL` (so a credited, voided, paid or credit-note faktura is never offered; `online_paid_at` is deliberately not a condition, because a Vipps charge is usually the payment that set it) and `NOT invoiceBookedRowSQL`. It must never offer less than `lockManual` accepts; the lock stays the authority. Imported fakturas without an opening balance are deliberately still offered: the assign is refused with the wait-for-the-opening-balance message, and hiding them would make the deposit look orphaned. `/vipps-charges/{id}/potential-invoices` is amount-only: `PotentialInvoicesForVippsCharge` calls `potentialInvoicesByAmount` directly, never `PotentialInvoicesForRow`, whose payer resolution loads a `bank_import_rows` row a charge does not have. A new price-item category needs an entry in `PriceItemCategories` and a mapping, or its items drop out of the hints.
- **"Already booked" has one definition.** A Stripe row settles a faktura only while `stripeChargeSettlesSQL` holds (a booked charge, not recollected); every Stripe clause uses it. `invoiceBookedRowSQL` (`auto_assign_member.go`) is true when a booked bank row, Vipps charge or Stripe balance transaction records the faktura (`invoice_id`; on a Stripe row only the manual faktura assign sets it), or a booked order-linked charge pays it through `order_sources` (a Stripe row by `order_id`, a Vipps row by `orders.vipps_reference`). The Stripe order clause counts only rows with `review_reason` NULL, i.e. booked by the booking pass from the order: a row a person booked keeps its review reason and may have gone to an account or another faktura, so its order's fakturas stay open. `lockInvoiceForAssign` refuses such a faktura (`errInvoiceHasBookedRow`) and `invoiceAlreadyBookedSQL` (auto-assign, KID cascade lock) adds the KID-matched bank row to it. The order clause matters between an order charge's commit and its `linkInvoicePayment`: without it a bank or Vipps assign in that window credits 1500 a second time. A new "is this faktura booked" check uses these, never its own EXISTS. The order clause reaches `order_sources` by its unique `invoice_id` index, and migration 000122 adds partial indexes for the Stripe and Vipps clauses (`idx_stripe_bt_settling_invoice`, `idx_stripe_bt_settling_order`, `idx_vipps_import_rows_booked_invoice`, `idx_vipps_import_rows_booked_order`).
- **Every path that settles a faktura takes its lock.** `lockInvoiceForAssign` serialises the manual bank assigns, the split-payment assign, the Vipps assign, both auto-assign rules and the KID cascade on one faktura. The legacy Vipps confirm and the order-linked Vipps charge lock all their fakturas at once in id order (`lockInvoicesForManualAssign`) before checking any. The Stripe charge booking locks every faktura of its order the same way (`lockSplitInvoicesTx`). A new settle path must take it too, record the faktura on its row (`invoice_id`) while the lock is held so the others see the booking, hold it per row, never across a whole import, and pass the date its entry is booked on as `bookingDate`, or an imported faktura is checked against the wrong date.
- **A lock holder never touches `s.db`.** Between `lockInvoiceForAssign` and its commit, every statement goes through the lock `tx`: use the `Tx`/`In` variants (`resolvePeriodIn`, `existingPeriodIn`, `createJournalEntryTx`, `postJournalEntryTx`, `linkAndPostBankRowsTx`, `postVippsChargeTx`, `postChargeTx`), never `CreateJournalEntry`, `PostJournalEntry`, `resolvePeriod`, `discardDraft` or any other pool-backed helper. A pool call there deadlocks once the pool is full of bookings queued on the same faktura, and Postgres can't see that cycle (invariants.md "A transaction holding a row lock never acquires another pool connection"). There is no compensating unlink or discard in these paths: the rollback is the cleanup. A `Tx` helper that can lose a race the caller survives (`errChargeRaced`) must roll its own writes back to a savepoint, or the caller's commit keeps them. Concurrency tests for these paths use `testutil.WithMaxConns(2)`, so a regression hangs in CI instead of only under load. Also read anything that must reflect the winner of the lock in a statement *after* the locking one: under READ COMMITTED, a statement that waited for the lock still evaluates its subqueries against its start snapshot.
- **Payer aliases have two sources and one store.** `vipps_customer_aliases` is taught from the Vipps queue (`UpsertCustomerAlias`, which refuses a user outside the club) and from Tildel's faktura assigns (`teachPayerAlias`, BRY-383), and both auto-assign rules read it through `aliasMember` first. A taught name must be the name the rules resolve: use `bankRowPayer` for a bank row, never the bare counterpart. The conflict test (`payerResolution.conflictsWith`) counts *any* member whose own name it is, not only a unique match, and the state read (`bankRowPayerState`, `taken` plus `payer_resolves_here`) must agree with it, or the box shows checked for a name the server then refuses. Removing an alias stays in the Vipps queue.
- **Imported fakturas are never settled by inference.** They carry `kid_number = ''` and have no GL receivable until the cutover's `opening_balance` entry is posted. Their paid status at the cutover comes from the previous system's open-items list, not from any matcher here; a new matcher or backfill that joins on KID or amount must require a non-empty KID and a posted CR 1500 booking (BRY-415, BRY-417), and must go through the `ImportedReceivableOpenSQL` guard. See invariants.md "Imported fakturas are read-only" and the operator workflow in [`docs/user/migrating-from-previous-system.md`](../../../docs/user/migrating-from-previous-system.md).
- **Provisional rows are not matchable money.** Never book a bare `Overførsel` from an export's last day against a Vipps payout or a faktura by amount. The settled row arrives with the next export and would become an unbooked duplicate. `SupersedeProvisionalBankRows` dismisses the provisional row once the settled one is imported under another reference.
